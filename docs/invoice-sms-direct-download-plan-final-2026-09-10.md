**1. 最终业务方案**

管理员在“组织管理 → 短信服务 → 电子发票已开具”启用“发票短信通知”。财务或管理员随后上传并成功登记电子发票，系统自动向该订单购票人的手机号发送开具成功短信，包含当前文件的免登录领取链接。

文件继续保存在私有存储中；持有领取链接的人可在 30 天内读取这一份文件。PDF 通过本站直接返回，支持预览的浏览器可直接打开，其他终端下载或交给阅读器处理。后台显示发送进度、送达结果、失败原因，并提供补发和撤销链接功能。

本期发票开具成功、文件更新和再次发送均只走短信，不发送邮件，也不在短信失败时转发邮件。现有邮箱作为开票联系资料保留，界面说明改为“开票联系邮箱”，删除这些交付入口中“重新发送至邮箱”的承诺。开票资料提醒、订单访问恢复等独立业务维持原来的渠道语义，本期不改造其通知策略。

首版范围：单张登记、批量导入、替换/恢复文件、手动补发、开关控制、短信回执、免登录文件访问。首版不接税务自动开票，不进行 OFD 转 PDF，不自动补发历史发票，不新增邮箱交付或多渠道选择。

**3. 开关位置、权限和生效规则**

复用现有 `templates.invoiceReady.enabled` 作为唯一发票业务开关，在原场景中明确命名为“发票短信通知”。组织级总短信服务开关仍是已有前置条件。本期不增加大会级第二个开关。

开关为组织级，对组织内全部大会生效。只有具备 `org.settings.manage` 的管理员可以配置、发送测试和启停；财务按现有 `event.read + org.invoice.manage` 权限上传和补发，并可在发票详情查看功能状态，无权修改组织短信凭据。

首次上线新模式默认关闭。旧配置中的 enabled=true 不直接授权新的 PDF 文件交付：迁移将发票场景归为旧模板模式并关闭此场景，原 CODE 作为旧配置保留。验证码、支付和其他短信场景保持原配置。

开关旁固定说明：

> 开启后，本组织发票上传并登记成功时，自动向购票人发送短信。关闭后停止后续发送，已发送的有效发票链接仍可使用。重新开启不会自动补发历史发票。

| 状态或动作 | 行为 |
| --- | --- |
| 功能关闭 | 正常上传、登记、个人中心下载；记录“未发送：发票短信通知已关闭”，不创建发送任务和公网领取凭证 |
| 关闭时配置和测试 | 允许保存发票模板、发送明确的内部测试短信；测试使用样例文件，不触发真实发票通知 |
| 尝试开启 | 校验总短信服务、凭据、签名、新模板参数模式、同一配置的测试送达及文件入口可达性；不满足时返回具体原因，开关保持关闭 |
| 功能开启 | 后续登记成功的文件自动入队；已开具旧记录可以由有权用户显式补发 |
| 关闭开关 | 保存成功后新任务无法取得发送许可，未开始的旧任务作废；已经取得许可并处于发送中的请求可能仍被渠道受理 |
| 关闭后再开启 | 分配新的启用批次，旧批次任务继续失效；不扫历史发票补发 |
| 更换模板、签名、密钥或固定领取域名 | 当前发票验证证据失效，业务场景关闭并更新批次；重新测试并手动开启 |
| 总短信服务关闭 | 发票新发送被阻止，当前批次待发任务失效；总开关再次打开也不复活旧任务 |

开关变化以数据库提交为生效点。界面可显示“已关闭，仍有 N 条发送中或待回执”。渠道已经开始处理的消息无法由本系统保证撤回；关闭后仍持续查回执。

内部配置保存 `deliveryMode=direct_file_v1`、`activationRevision`、`enabledAt`、`verifiedFingerprint`、`testDeliveryId` 及当前配置版本；这些是系统维护字段，不增加用户填写项目。配置指纹包含账号/密钥版本、签名、模板 CODE、参数模式和固定公网 origin。单纯启停不抹掉同指纹的成功验证。

配置接口采用 `expectedUpdatedAt` 乐观锁，过时保存返回 409。组织配置行在写事务中锁定；测试或回执只能条件更新当前指纹对应的验证字段，不得恢复开关或覆盖其他模板。

配置契约允许“总短信服务已配置并开启、业务场景全部暂关”，解除现有“总开关开启必须至少一个场景开启”的保存限制，使管理员能够完成先配置、再测试、最后启用。正式发送仍逐场景校验开关。运行时 origin 与已验证指纹不一致时，以条件更新持久化关闭发票场景并更新批次，不能仅在内存中暂时跳过发送。

**4. 从上传到手机打开的完整流程**

```text
管理员保存发票模板 -> 关闭状态下测试 -> 收到回执、验证样例 PDF -> 打开启用开关
                                                                    |
用户提交开票资料 -> 财务审核、开票 -> 上传 PDF/OFD -> API 校验文件与订单
                                                                    |
                       同一事务：文件登记 + 已开具 + 短信计划/未发送原因
                                                                    |
                             现有 Outbox -> Worker 再核对开关/批次/版本
                                                                    |
                                      生成专属领取凭证 -> 阿里云短信
                                                                    |
          后台短信状态 <- 回执查询                    用户点击短信链接
                                                                    |
                                     本站校验凭证 -> 私有存储 -> PDF
```

1. 用户仍按当前表单提交公司全称、税号和开票联系邮箱，不增加手机号填写步骤。
2. 财务或管理员上传已经开具的 PDF/OFD。文件存在、大小、声明媒体类型、文件签名、摘要和存储范围校验沿用现有代码。当前文件上限 20 MiB。
3. 在数据库事务内保持订单、票证、发票的既有锁顺序，核对净支付额、退款互斥、状态和版本。事务同时登记文件并标记 `issued`。
4. 根据当时的开关、配置资格和收件人，创建唯一的短信交付记录与 `InvoiceSmsDeliveryRequested` 事件；不能发送时保存具体原因。通知渠道故障不会撤销已经提交的开票事务。
5. Worker 取得任务后再次检查开关、启用批次、文件版本和接收人。符合条件才生成或重用领取凭证，取得发送许可后调用阿里云。
6. 手机收到成功通知。用户打开链接无需登录或验证码；服务器直接返回当前 PDF 文件。
7. 后台记录渠道受理与送达结果。用户原有个人中心下载能力独立可用。

首次上传、批量导入、文件替换及作废后的恢复，均采用上述流程。批次中每条申请独立提交；成功记录进入通知流程，失败记录不发送。取消选择文件、仅上传对象但未登记、校验失败或事务回滚均不产生短信。

**5. 接收人、补发与重复控制**

现代订单按购票人归属解析手机号：优先读取同组织、处于 active 状态且已验证的购票账号 `mobileE164`。账号记录经查询确认已删除时，仅在订单购票人快照能确定原购票人且号码有效时回退快照；数据库查询失败进入重试，不当作账号不存在。账号明确停用、组织不匹配或身份冲突时停止发送并提示处理。

真正的历史订单，即购票人 ID、购买意图和快照中的购票身份都为空时，允许沿用原报名手机号。现代订单不回退参会人号码。发票资料里的自由填写 mobile 不作为短信接收源。

入队保存收件人快照与来源。Worker 发送前重算归属；号码或身份变化时取消原任务，显示“接收人已变化，请核对后重新发送”，不静默改投。重新补发使用当前已验证购票人号码，撤销旧接收人关联凭证。后台补发界面显示脱敏接收号码，不提供随意输入其他号码的捷径。

原后台 `/send` 和用户个人中心 `/invoice/send` 均改为短信补发语义，统一校验：开关开启、可用模板、当前有效文件、购票人归属、可发送手机号、发票和退款状态、队列去重与持久化频控。发票邮件为空不再阻止短信补发。用户只可操作本人作为购票人的订单。

- 首次自动通知以“发票申请 + 完整文件版本 + 自动发送”唯一去重。同一上传请求和同一事件重复执行只产生一次有效发送。
- 人工补发通过 Idempotency-Key 形成新的请求键。已有当前版本的排队、发送中或待回执任务时返回原任务，不再入队。
- 普通补发统一执行每申请 10 分钟冷却，从最近一次有效入队时间起算；人工补发每申请滚动 24 小时最多 5 次，前后台共同计数。上传新文件形成新的自动通知版本，不受旧文件的普通补发冷却阻止。
- 自动任务超过文件登记时间 24 小时尚未开始发送时，终止为“积压任务已过期，请人工补发”，避免突然送达很久以前的成功通知。
- 结果未知或已受理但未收到送达终态时继续查询，不按网络错误直接重发。超过 30 分钟仍不能确认时展示“需要核对渠道结果”。具备财务管理权限的后台用户可选择“仍重新发送”，明确查看可能重复提醒的提示并填写原因；普通用户没有该例外按钮。例外补发同样计入冷却、人工次数和审计，原任务继续只查结果。
- 本期不提供历史发票一键群发。打开功能和重新启用均不会批量重放历史任务。

**6. 短信状态、开关竞态与故障**

| 后台展示 | 含义和后续动作 |
| --- | --- |
| 未发送 | 功能关闭、没有手机号、模板未就绪等明确原因 |
| 排队中 / 重试等待 | 已持久化，尚未开始一次渠道请求 |
| 发送中 | 已取得发送许可，可能正在进入渠道 |
| 已受理，待送达回执 | 阿里云返回受理成功；继续查回执 |
| 已送达 | 收到渠道送达结果 |
| 结果待确认 | 超时或断网，渠道是否受理尚不明确，继续查单 |
| 发送失败 | 渠道明确拒绝或回执失败；显示经脱敏的错误原因 |
| 已取消 | 开关批次失效、文件更新、收件人变化或积压超时 |

使用 `notification_deliveries` 的短信记录作为事实来源；发票详情增加 `smsNotification`，包含接收人掩码、来源、状态、原因、时间、链接有效期、允许操作及下次可补发时间。现有四值 `deliveryStatus` 保留兼容：无任务/取消对应 not_sent，未完成对应 queued，明确失败对应 failed，渠道受理/送达对应 sent；页面以新增状态显示真实含义，不用 sent 宣称送达。

回执更新短信记录，不改变发票资料的 `updatedAt`，避免财务正在编辑时被后台回执频繁触发版本冲突。兼容汇总字段写入不更新资料版本；业务变更仍使用既有乐观锁。

发送资格和发送许可在短数据库事务内检查并保存，外部短信网络调用在事务提交之后执行。遵循“订单/票证 → 发票/文件 → 组织短信配置 → 通知记录”的锁顺序。配置保存仅锁组织配置，不持有该锁反向锁订单；队列失效按 activationRevision 判断，无需在关闭接口里逐单加锁。

开关关闭与任务发送竞争时，以发送许可事务和关闭事务的先后为边界：关闭先提交的任务无法获准；已经获准的任务可能仍被受理。Worker 崩溃、租约超时后，已进入 sending 的任务按未知结果查询，不能直接重新调用 SendSms。

阿里云 SendSms 不承诺幂等，OutId 用于关联和查询。系统不宣称渠道“严格只送一次”。[SendSms 官方文档](https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms)

复用现有任务队列和回执查询，明确未进入渠道的临时故障最多 5 次尝试（首次加 4 次重试），重试间隔 30/60/120/240 秒；明确配置错误立即结束为失败；结果未知只查询。接收回执后以条件更新维护状态，不用迟到的中间回执覆盖 delivered。已确认的终态保持记录，例外补发是另一条交付记录。

为批量导入增加该组织发票短信每秒最多一次发送许可，使用现有 Redis 原子限流。先取得限流配额，再进入数据库发送许可事务；限流任务延后调度，释放 Worker 槽位，不占着工作线程等待。该限制不改变验证码、支付等其他短信任务。首版不新增服务或可配置限流面板。

组织总服务或发票开关关闭后继续核对已经发送中的任务。短信配置缺失时，新发票生产通知明确失败或未发送，不进入本地通知收集器并标记成功。开发与测试只使用显式配置的本地替身。

**7. 免登录文件访问与撤销**

正式用户地址为 `${PUBLIC_ORIGIN}/invoice/file/:token`，网关映射至 API 的 `GET/HEAD /api/v1/invoice-files/:token`，沿用当前 API 的 api/v1 全局前缀，直接流式返回文件，无站外 302 跳转。系统只使用部署配置的可信 origin，不采用请求 Host 或任意前端传入域名生成短信。

- 令牌为 24 位密码学安全随机英文字母和数字，首位为字母，约 142 位随机强度；数据库唯一约束处理极小概率碰撞。
- 每份凭证关联组织、大会、订单、发票、完整文件版本和交付接收人标识，仅授权读取该文件，不授予订单查看或发票编辑权限。
- 有效期固定从首次准备实际发送时开始计算 30 天。队列重试和重复点击不延长有效期；同文件同接收人正常补发重用尚未到期凭证，过期才生成新的 30 天凭证。
- `invoice_document_access_links` 保存 tokenHash、使用现有通知密钥加密的 sealedToken、绑定信息、expiresAt、revokedAt、createdAt。原 `order_access_tokens` 继续承载原订单和补资料流程，文件凭证独立。
- 文件版本包含 documentId、storageKey、contentDigest、issuedAt。替换文件保留 documentId 时也能准确撤销旧版。
- 作废、替换、退款进入待调整/取消、主动撤销在相应数据库事务中永久设置 revokedAt；下载还实时核对状态和版本。后续恢复为 issued 也不复活旧凭证。
- 成功退款联动须同时覆盖 `apps/api/src/common/refund-workflow.service.ts` 与 `apps/api/src/common/commerce-operations.service.ts` 的人工退款路径。普通用户提出退款申请本身不撤销文件；退款已批准且正在执行、外部资金核验或权益修复时，暂停新的成功通知，并在文件访问时返回“发票处理中”。实际进入 adjustment_required 后永久撤销旧领取凭证。
- 关闭“发票短信通知”仅停止发信，不影响已经发送的有效链接。管理员另有“撤销领取链接”动作，可单独撤销；“撤销并重新发送”执行短信资格检查，发送不可用时可选择只撤销。
- PDF 返回 application/pdf、inline 和经过清理的文件名；OFD 返回实际格式并下载，不承诺浏览器可预览 OFD，不伪装成 PDF。
- 支持 HEAD、单段 Range、206/416、断点读取和手机预抓取。HEAD/Range 不消耗凭证；一个链接可重复访问。数据库事务不跨越整段文件流。
- 限制每 IP 每分钟 60 次入口请求；用手机 PDF 多段读取和共享网络场景验收，不能把正常预览当成一次性领取。
- 返回 private/no-store、noindex/nofollow/noarchive、no-referrer、nosniff。文件及错误页均无统计脚本、第三方资源或通用站点营销内容，按 `/invoice/` 敏感边界执行整页访问。
- 令牌不存在或格式错误返回不含业务资料的错误；到期/撤销显示简短失效提示及个人中心入口；存储暂时不可读返回可重试错误。页面不泄露姓名、税号、手机号或发票金额。
- 网关、外层 Nginx、API 请求日志、错误日志和追踪记录均须脱敏令牌及存储签名；普通管理列表、审计及事件 payload 不保存可用链接。下载审计只记资源 ID、时间和结果，不能以链接被访问断言本人已阅读。
- 凭证到期或撤销后清理 sealedToken，保留哈希及必要审计关联；复用 Worker 维护周期，分批处理。使用现有密钥版本管理，密钥不可解密时阻止新发送并展示原因。

持有或转发链接会传递文件读取能力；已下载到设备的文件无法远程撤回。撤销可阻止后续请求，已经开始传输的数据无法保证收回。

**8. 短信文案、模板审核和测试**

产品目标正文保持：

> 您的${eventName}电子发票已开具，请于${expiresAt}前查看并保存：https://hui.ailingdaoli.com/invoice/file/${fileToken} 请妥善保管此链接。

签名由现有阿里云配置添加。域名在模板中固定，以实际 PUBLIC_ORIGIN 为准；eventName 使用后台大会名称，按获批变量属性校验长度，超长时明确提示调整大会简称或模板，不任意拼接未审批内容。expiresAt 使用大会时区的明确日期和时间。界面展示带签名、实际参数后的完整内容及字符数，并提示最终拆分计费以渠道为准，不承诺一条短信计费。

本轮再次核对的阿里云规则包含：普通链接参数最长 8 位，限制把完整 URL 放入变量，文档类链接受限，官网加变量的地址列为不可跳转。公开文档允许提交完整场景说明申请综合评估，但不构成本方案可获批的保证。[通知短信模板规范](https://help.aliyun.com/zh/sms/user-guide/notification-template-specifications/)

**这里仍有一个外部上线条件：渠道必须接受实际发票场景、24 位文件参数和直出文件。** 用户确认可以开始实现系统能力；短信正式开启须同时满足实际模板审核与授权测试。若渠道拒绝，功能保持关闭，个人中心继续下载；本期不启用邮件回退。免登录领取页等替代体验需要再提交确认，不能通过缩短安全凭证或伪装页面绕过审核。

模板测试顺序固定为：保存新 CODE 和 direct_file_v1 参数模式 → 准备无真实客户信息的独立样例文件 → 公网 GET/HEAD 验证同一域名入口和文件格式 → 在开关关闭状态下，管理员明确确认并向内部号码发送测试 → 保存独立的短信测试交付记录 → 通过现有回执查询获得 delivered → 开关变为可开启。

测试凭证只访问样例文件，有效期 24 小时，与真实客户发票隔离；不复用真实订单作为测试样例。`example.com` 测试值在发票场景中移除。生产不允许模拟送达或手动把状态改为 delivered 来解锁功能。

每个测试结果绑定配置指纹。测试等待回执时显示进度，不把接口 accepted 显示为最终验证成功；测试过程中模板或域名变化，旧结果归档且不解锁新配置。失败或回执暂缺时保留具体原因和再次测试入口，不影响其他短信场景的既有验证。

新增 `GET /api/v1/admin/integrations/aliyun-sms/invoice-ready/tests/:deliveryId` 读取发票测试状态，使用 org.settings.manage 权限及组织范围校验，返回测试任务 ID、脱敏号码、受理/送达状态、文件入口检查和配置匹配结果，不返回真实客户文件链接。
