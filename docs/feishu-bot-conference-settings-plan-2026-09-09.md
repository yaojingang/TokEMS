# 大会配置中的飞书机器人与运营日报方案

日期：2026-09-09  
状态：设计提案，尚未实施本次增量  
核对基线：本地 main，HEAD `f44a5e1`，以及当前工作区源码  
适用范围：大会配置、组织集成、运营日报、退款与发票待办

## 1. 推荐方向

在每场大会的「大会配置」中增加「飞书机器人」，运营人员在这里完成连接、选群、预览、试发和开启日报。机器人应用凭据由组织统一保存，每场大会独立保存目标群、发送时间和启用状态。

沿用仓库已有的企业自建应用机器人、Card JSON 2.0、NestJS API、PostgreSQL 投递账本、事务 Outbox、BullMQ 与 Worker。每天默认按大会时区 09:00 推送前一完整自然日的增量数据，并附生成时的累计数据和待处理事项。

首版完成一条完整可用的日报链路：访问、报名、付款、退款申请、退款成功、发票需求与资料提交、当前待办。群内展示聚合数值，按钮进入 TokEMS 后台执行操作。飞书 CLI 用于管理员联调和诊断，生产定时发送由现有 TypeScript 客户端直接调用飞书 OpenAPI。

最小交付形态为一场大会绑定一个群、每日一次、固定指标、固定卡片。首版保留预览、试发、投递记录与失败补发，这些能力用于验证目标群和排查漏发。

## 3. 接入方式与飞书 CLI 的职责

### 3.1 选择企业自建应用机器人

选择理由：当前后端已经围绕组织凭据、机器人信息、可见群选择、消息 ID 和投递账本实现。继续完成这条路径，可让同一组织的多场大会复用应用，并由管理员选择机器人已加入的目标群。

飞书官方明确：应用机器人向群发消息需要启用机器人能力、发布应用、加入目标群并拥有发言权限；自定义群机器人使用独立 Webhook。依据：[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)、[自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)。

| 方案               | 配置成本与能力                                                                   | 本次取舍                                                             |
| ------------------ | -------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 企业自建应用机器人 | 需要企业应用发布；支持应用身份、群列表查询和统一连接管理                         | 首版采用，复用现有实现                                               |
| 群自定义 Webhook   | 群内添加即可使用，无需租户管理员审核；只能向所属群推送，没有群列表等数据访问权限 | 当企业无法安装应用时，作为单独的简化适配方案；首版不同时维护两种入口 |

**关键前提：组织能够发布并安装企业自建应用。** 如果企业策略禁止安装，当前应用机器人链路无法完成接入，转为 Webhook 的评估点是连接适配层；统计、日报界面和投递账本仍可复用。采用 Webhook 时需另外设计地址加密、固定域名验证、签名与超时语义。

### 3.2 最小权限和依赖

| 项目                                    | 用途与要求                                                 |
| --------------------------------------- | ---------------------------------------------------------- |
| 飞书 App ID、App Secret                 | 组织管理员从企业自建应用取得；通过后台录入并加密存储       |
| `im:message:send_as_bot`                | 以机器人身份发消息，选用这一项最小发送权限                 |
| `im:chat:read`                          | 查询机器人所在群列表，供管理员选择目标群                   |
| 机器人能力与应用发布                    | 飞书开放平台配置生效的前提；同时确保机器人在群内可发言     |
| `tenant_access_token`                   | 服务端按 App ID、Secret 获取并缓存，按接口返回的有效期刷新 |
| `INTEGRATION_ENCRYPTION_KEY` 及版本配置 | 复用现有组织集成加密配置，API 与 Worker 使用匹配的密钥版本 |
| `ADMIN_ORIGIN` / 部署域名解析           | 复用现有 `resolveDeploymentOrigins()` 生成可访问的后台链接 |
| PostgreSQL、Redis、Worker               | 复用现有基础设施，PostgreSQL 持久化模式为必要条件          |

获取机器人基本信息本身无需额外权限；首版无需群消息读取、通讯录、飞书任务、审批、事件订阅或卡片回调权限。依据：[机器人信息](https://open.feishu.cn/document/client-docs/bot-v3/obtain-bot-info)、[群列表](https://open.feishu.cn/document/server-docs/group/chat/list)、[应用凭证](https://open.feishu.cn/document/server-docs/authentication-management/access-token/tenant_access_token_internal)。

首版对接中国版飞书，API 域名固定 `open.feishu.cn`。国际版 Lark 使用不同域名及企业环境，作为独立适配范围，不接受任意自填 API 地址。

### 3.3 CLI 使用边界

本机已验证 `lark-cli 1.0.67` 可执行。当前可用的相关命令包括 `im +chat-list --as bot` 和 `im +messages-send --as bot`，后者提供 `--msg-type interactive`、`--content`、`--idempotency-key` 与 `--dry-run`。当前版本未注册 `schema im.messages.create`，原生接口规范通过飞书官方 Markdown 文档核实。

CLI 的职责是接入时检查应用身份、核对群列表、预览请求，以及在有明确试发授权时做联调。联调使用同一企业应用的独立 profile，避免将个人 CLI 的默认应用误认为 TokEMS 机器人。CLI 以 `--as bot` 工作，无需个人用户授权才能进行本方案的服务端机器人操作。

生产 Worker 不调用本机 CLI，不依赖个人电脑在线、个人登录态或 AI 客户端的定时任务。官方 CLI 的身份与调用方式可见 [larksuite/cli](https://github.com/larksuite/cli/blob/main/README.zh.md)。

## 4. 后台入口与页面设计

### 4.1 信息架构

- 主入口：大会工作区 → 大会配置 → 飞书机器人，路由 `/events/:eventId/settings/feishu`。
- 组织入口：管理中心 → 系统设置 → 飞书机器人，路由 `/manage/settings/feishu`，管理组织共用连接。
- 大会页直接提供组织连接组件，首次接入可在当前大会页完成。组件明确标注「本组织所有大会共用此连接」。
- 组织页只负责应用连接；目标群、日报时间、预览和发送记录保留在大会页。

视觉沿用当前后台的排版、表单边界、按钮、`SaveStatus`、`SettingsFormActions` 和状态颜色。桌面使用设置与预览两栏，下方整行展示发送记录；窄屏按连接、日报设置、预览、记录顺序排列。页面以状态和操作为主，无需额外装饰动画。

### 4.2 页面线框

### 4.3 首次连接流程

1. 引导组织管理员在飞书创建企业自建应用、开启机器人、申请两项权限并发布，群管理员将机器人加入目标群。
2. 在 TokEMS 填写 App ID、App Secret，点击「保存并校验」。服务端依次验证应用凭据、机器人状态和群列表访问能力。
3. 连接通过后显示机器人名称。群为空时提示添加机器人并刷新，保留连接成功状态。
4. 选择可见群并保存日报设置，默认每日 09:00、自动推送关闭。群名由服务端确认，后台不接受任意手输的群 ID。
5. 本地预览不发送消息。点击「发送测试日报」时展示目标群名称，并复用现有经营数据可见范围确认；测试卡片带「测试」标记。
6. 飞书返回消息 ID 后，记录当前目标群已验证。管理员点击「开启每日推送」，页面展示实际下次发送时间。

“校验连接成功”说明凭据和查询正常；“试发成功”说明飞书接口已接收消息。群成员是否阅读不作为已发送判定。

### 4.4 状态与交互规则

| 状态或操作             | 界面与系统行为                                                     |
| ---------------------- | ------------------------------------------------------------------ |
| 未配置                 | 展开接入说明及凭据表单；其他操作说明前置条件                       |
| 已连接、群为空         | 提示在飞书群中添加当前应用机器人，提供刷新按钮                     |
| 已选群、未试发         | 可保存与预览；完成试发后才能开启每日推送                           |
| 修改发送时间           | 保存成功后显示新的下一次时间，避免在当日重复发送                   |
| 修改目标群             | 保存时暂停当前大会日报并清除测试标记，新群试发通过后重新开启       |
| 修改应用凭据           | 明确影响组织共用连接；清除相关验证并暂停订阅，重新校验和试发       |
| 暂停推送               | 服务端取消未进入发送阶段的任务；已提交飞书的消息仍可能到达         |
| 群不可用或权限被撤销   | 展示原因和修复步骤，停止该连接或目标的自动投递，修复后重新验证     |
| 网络错误、限流         | 展示重试状态；永久失败与结果待确认分别处理                         |
| 结果待确认             | 提示先核对群消息，人工补发创建独立记录并带补发标记                 |
| 草稿、配置中、归档大会 | 自动推送关闭；预览和获授权的试发仍可用于验收                       |
| 已结束大会             | 保持当前订阅状态，便于处理退款和发票尾项；管理员可暂停，归档后停止 |

密钥输入为空表示保留原值；已保存密钥只显示状态和掩码。切换页面沿用未保存修改提示。每次手动发送使用独立幂等键，同次双击与请求重试复用该键。

## 5. 日报指标与统计口径

### 5.1 三个时间层次

- 昨日增量：大会时区前一日 00:00 到当日 00:00，采用左闭右开区间。
- 当前累计与待办：按生成时的数据库一致性快照统计，并显示生成时间。
- 历史投递：展示当时保存的快照。重试、补发复用当时内容；需要看最新数据时使用当前预览。

保留默认 09:00，配置取大会当前时区。修改时区后重算未来发送时间，历史日报保留原时区快照。停机跨日时按原调度日期归属报告，避免将旧任务错算成新一天。

### 5.2 昨日指标

| 群内名称            | 精确口径                                                                              | 当前能力与增量                                                               |
| ------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 访问次数            | `event_public_metric_days.pageViews`，标注系统去重访问次数                            | 复用现有采集；不标成独立访客 UV                                              |
| 新增报名记录        | 昨日创建、`supersededAt` 为空的报名记录数                                             | 复用现有口径；名称明确为记录数，避免与独立购票人数混用                       |
| 支付订单 / 收款金额 | 成功支付发生在窗口内；订单去重计数，金额以支付流水计                                  | 按 `payments.succeededAt`；金额单位分                                        |
| 新增退款申请        | 昨日 `refund_requests.createdAt` 内的申请记录数，来源包括用户与管理员；按申请 ID 去重 | 新增聚合；渠道重试和执行单不增加申请数；撤回、驳回属于后续状态               |
| 退款成功 / 退款金额 | 状态成功且可信 `refunds.succeededAt` 位于窗口内的退款流水                             | 修订旧创建时间口径；部分退款以实际成功的金额计                               |
| 净收款              | 昨日收款减昨日成功退款                                                                | 可为负值，明确为收付统计，不表述为利润                                       |
| 新增开票需求        | 昨日新建 `invoice_requests.createdAt` 的数量，含支付后创建的待补资料记录              | 使用稳定创建时间，区别于可变化的 `requestedAt`                               |
| 提交开票资料        | 窗口内从其他状态进入 `pending_review` 的 `invoice_state_logs`，按发票申请 ID 去重     | 补资料和驳回后重提均可计入当日；同日多次提交算一笔；同状态资料编辑不重复计入 |
| 新增签到            | 昨日成功核销记录数                                                                    | 沿用现有成功核销口径，仅在大会进行中和结束后展示                             |

新增开票需求和提交开票资料分别说明需求建立和进入处理队列，不能相加为总申请量。源代码依据为 `ConferenceRepository` 支付完成时创建待补资料申请，以及 `InvoiceOperationsService.applyInvoiceBuyer()` 提交资料时写入状态日志。

历史成功退款若缺少可信成功时间，不使用创建时间替代。新版快照增加质量标记 `REFUND_SUCCESS_TIME_MISSING`；无法判断缺失流水是否属于统计窗口时，昨日退款笔数、退款金额和净收款返回 null，显示「成功时间数据待核对」。累计成功退款仍可按已核实的状态和金额统计，历史日期不推算回填。上线前必须验证现行退款写入路径都保存成功时间。

### 5.3 当前累计、待办与关注项

| 分类                  | 内容与规则                                                                                           |
| --------------------- | ---------------------------------------------------------------------------------------------------- |
| 累计                  | 累计访问、当前有效报名、已确认参会、当前已支付订单、扣除成功退款后的订单净额、剩余库存；沿用后台口径 |
| 报名待审核            | 当前 `pending_review` 且未被替代的报名记录                                                           |
| 退款待审核            | `refund_requests.reviewStatus=pending_review`，按申请 ID 计数                                        |
| 退款等待资金          | 当前有效执行单 `currentAttempt=true` 且 `status=waiting_funds`，按申请 ID 计数                       |
| 退款处理中            | 当前有效执行单处于 `processing`，作为进度信息                                                        |
| 退款需关注            | 复用退款列表 `attention` 的判定，包含人工处理、已有关注原因及现有 24 小时关注规则                    |
| 发票待处理            | `pending_review`、`issue_failed`、`adjustment_required` 的并集                                       |
| 发票待补资料 / 开票中 | `awaiting_details` 与 `issuing`，作为进度信息                                                        |
| 其他关注              | 复用现有支付异常、合作咨询和低库存票种数量；低库存阈值沿用现有实现                                   |

退款“需关注”可能与“待审核”“等待资金”重叠。卡片分别显示，不合计为「待办总数」；低库存票种和申请笔数也不混合相加。后台列表与日报共享退款筛选条件，后续规则修改应同步生效。

### 5.4 数据完整性边界

- 访问统计采集未覆盖完整自然日、时区切换导致统计不完整时显示「暂无完整数据」，不可显示为零。
- 不通过第三方网站统计抓取访问量；复用大会自己的访问统计。报名、支付、后台等敏感页面继续遵守统计脚本隔离要求。
- 首版不展示 UV 和访问转化率。当前访问口径经过系统去重，缺少一致的跨环节访客定义。
- 金额按币种验证。当前主要场景为 CNY；遇到同一大会多币种时增加 `MIXED_CURRENCY` 质量标记、金额指标展示「多币种，请到后台查看」，其他数量指标继续发送，禁止直接相加。
- 数据库聚合失败时记录生成失败并重试，不以空日报替代。有效零数据日仍发送，方便确认任务正常运行。
- 预览与发送共用聚合函数；业务指标与后台口径的差异必须有名称和说明，不能用不同公式展示同名值。

## 6. 飞书卡片设计

卡片采用静态 JSON 2.0，结构为大会名称与日期、昨日新增、当前累计、待办与进度、后台操作按钮、生成时间。存在需人工处理的事项时使用橙色标题，其余沿用蓝色。标题强调大会身份，消息摘要可直接展示报名、退款和发票的关键数量。

示意内容，全部为虚构数据：

> **第二届中国 GEO & AI 营销大会｜运营日报**  
> 数据日期：2026-09-08 · Asia/Shanghai  
> **昨日新增**  
> 访问次数 1,286 · 报名记录 36 · 支付订单 28  
> 收款 ¥11,172.00 · 退款申请 3 笔  
> 退款成功 1 笔 / ¥399.00 · 净收款 ¥10,773.00  
> 新增开票需求 8 笔 · 提交开票资料 5 笔  
> **当前累计**  
> 已确认参会 268 人 · 剩余库存 232 席  
> **待办与进度**  
> 报名待审核 6 · 退款待审核 2 · 退款等待资金 1  
> 发票待处理 7 · 发票待补资料 3  
> [查看大会] [审核报名] [处理退款] [处理发票]  
> 生成于 2026-09-09 09:00，待办以此时刻为准

卡片仅包含聚合数据，不包含姓名、手机号、邮箱、退款原因、票码、发票抬头、税号或访问令牌。预览使用纯结构化渲染，转义大会名称和群名，不直接执行 Markdown 中的 HTML。

应用消息中的卡片请求体上限为 30 KB，首版设置更小的内部预算并对超长大会名称做显示限制。JSON 2.0 需要飞书 7.20 及以上客户端；真实联调需要覆盖桌面端与移动端。依据：[发送消息内容限制](https://open.feishu.cn/document/server-docs/im-v1/message/create)、[卡片 JSON 2.0](https://open.feishu.cn/document/feishu-cards/card-json-v2-structure)。

### 后台按钮的落点

| 按钮     | 路由与行为                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 查看大会 | `/events/:eventId/overview`                                                                                                                       |
| 审核报名 | `/events/:eventId/registrations?status=pending_review`，初始化并持续同步状态筛选                                                                  |
| 处理退款 | `/events/:eventId/registrations?panel=refunds&refundStatus=pending_review`，自动展开退款面板；资金或关注项可分别使用 `waiting_funds`、`attention` |
| 处理发票 | `/events/:eventId/invoices?worklist=actionable`，一次展示三类可处理状态                                                                           |

发票查询契约新增 `worklist=actionable`，服务端转成固定状态集合；与单状态 `status` 同时出现时返回参数错误。补齐前端、查询、导出和计数的一致性。报名、退款筛选只接受已有状态枚举，非法参数回落到安全默认值。

首版最多四个主按钮，监控项通过大会概览进一步查看。所有链接保留登录回跳并执行 TokEMS 权限检查，链接本身不授予业务权限。

## 7. 服务端与数据模型增量

### 7.1 数据流

```text
大会配置页 → NestJS 配置 API → PostgreSQL 组织连接与大会订阅
                                     ↓
                        Worker 每分钟扫描到期订阅
                                     ↓
                        投递账本 + 事务 Outbox
                                     ↓
                         BullMQ → 日报生成 / 发送
                                     ↓
                  业务表一致性快照 → 固定卡片 → 飞书群
                                     ↓
                            投递结果 → 后台历史
```

### 7.2 复用与新增

- 复用 `organization_integrations`、`event_feishu_digest_subscriptions`、`event_public_metric_days` 和 `feishu_digest_deliveries`，不新增服务或消息中间件。
- 扩展现有投递表，增加可空 `card_payload` JSONB，保存首次发送前生成的完整静态卡片。其数据范围仅为聚合数值和后台链接，便于逐次重试保持同一内容。
- 统计快照升级到 `metricVersion=2`。V2 新增 `daily.refundRequests`、`daily.invoiceDemands`、`daily.invoiceSubmissions`，以及退款待审核、等待资金、处理中和需关注字段；退款成功笔数及金额字段允许因质量问题为 null，并带 `qualityIssues`。
- V1/V2 契约按 `metricVersion` 区分。历史 V1 继续可查看与补发；V1 中缺失的指标展示「该版本未统计」，不默认补零。新生成日报只使用 V2。
- 对退款成功时间、退款申请创建时间和发票状态日志的聚合查询检查索引与执行计划；仅在已有索引不能支撑查询时补相应索引。首版不新增一套日报汇总数据库。

### 7.3 接口安排

以下路径均位于现有 `/api/v1/admin` 前缀下。

| 接口                                                                | 行为                                                     |
| ------------------------------------------------------------------- | -------------------------------------------------------- |
| `GET/PATCH /integrations/feishu-bot`                                | 复用组织连接读取与更新                                   |
| `POST /integrations/feishu-bot/verify`                              | 复用保存后校验                                           |
| `GET /integrations/feishu-bot/chats`                                | 复用群列表只读查询                                       |
| `POST /integrations/feishu-bot/chats/refresh`                       | 复用显式刷新并协调失效绑定                               |
| `GET/PATCH /events/:eventId/feishu-digest`                          | 复用大会订阅读取与配置                                   |
| `GET /events/:eventId/feishu-digest/preview`                        | 返回新版快照与卡片预览，不触发发送                       |
| `POST /events/:eventId/feishu-digest/send-test`                     | 复用试发和测试验证记录                                   |
| `GET /events/:eventId/feishu-digest/deliveries`                     | 首版展示最近 100 条记录，沿用当前接口限制                |
| `GET /events/:eventId/feishu-digest/deliveries/:deliveryId`         | 新增历史详情，返回版本化聚合快照、状态和可展示的卡片内容 |
| `POST /events/:eventId/feishu-digest/deliveries/:deliveryId/resend` | 复用失败或结果不确定记录的人工补发，保留原报告和原目标群 |

首版不增加任意历史日期群发接口。超过补发窗口的 `skipped` 记录展示跳过原因；补发按钮只对有快照的 `failed/unknown` 记录开放。

### 7.4 权限

首版复用现有权限体系，不增加新的权限码：

- 组织连接读取使用 `org.settings.read`，修改使用 `org.settings.manage`。
- 大会日报配置状态可以由有 `org.settings.read` 且能访问该大会的人员查看。
- 日报预览、历史详情同时要求 `org.settings.read` 与 `event.dashboard.read`。
- 选群、启停、试发、补发同时要求 `org.settings.manage` 与 `event.dashboard.read`，沿用当前写接口约束。
- 前端导航与服务端鉴权同时校验；仅有大会权限、缺少组织设置权限的运营人员首版由组织管理员代为配置。
- 报名审核、退款处理、开票权限继续在各自业务接口检查。

各查询都校验当前用户组织与目标大会范围。群消息可被群成员查看或转发，目标群应为允许获知大会聚合经营数据的运营群；试发沿用现有 `dataVisibilityConfirmed` 约束。

## 8. 调度、重复发送与故障处理

1. 沿用每分钟扫描、数据库行锁抢占、唯一去重键和事务 Outbox。同一组织、大会、报告类型、报告日期最多创建一条自动投递。
2. 正常环境下在设定分钟内开始调度，单大会以 2 分钟内送达为验收目标。遇到飞书限流或队列拥堵时展示延迟，不承诺绝对准点。
3. 首次发送前保存 `aggregate_snapshot`、`card_payload` 和内容摘要；重试使用已保存的报告日期、群、内容，不重新聚合。
4. 向飞书提交 `uuid=delivery.id`，每个投递 UUID 稳定。飞书保证相同 UUID 在一小时内至多成功发送一条消息；数据库唯一键负责跨越这一时间窗口的业务去重。依据：[消息去重参数](https://open.feishu.cn/document/server-docs/im-v1/message/create)。
5. 明确的限流等可恢复拒绝最多发送 5 次，使用现有队列指数退避；读取 `Retry-After` 时优先遵循服务端等待时间。超过去重窗口仍未完成的发送记录进入人工确认范围。
6. 网络超时、发送后的 5xx、返回成功但数据库落账失败、Worker 在发送中崩溃，都可能已经到达飞书，进入 `unknown`。首版保留人工确认机制，避免无限自动重复投递。
7. 无效凭据、机器人被移出群、群解散、发言权限被撤销等永久失败暂停对应连接或大会投递，保留记录。按照官方错误码及语义分类，避免把不同权限错误都显示为机器人退群。
8. 延续现有 12 小时迟到窗口：在窗口内补处理到期日报，超过窗口记录跳过，不把多天旧日报集中发送。恢复后继续下一次计划任务。
9. 发送前再次核对大会状态、组织连接、目标群验证与配置版本。关闭订阅、改群、轮换凭据后的旧队列任务应取消。
10. 人工补发创建关联原投递的新记录和新 UUID，卡片标明「补发」并保留原生成时间；不得悄悄发送到后来更换的新群。
11. 多大会同群发送时设置应用与群维度节流，避免与群内其他机器人共享的 5 QPS 限制冲突。外部接口故障不影响报名、支付或退款业务事务。

## 9. 配置安全、数据隔离与回滚

- 凭据使用现有组织集成加密，Secret 和 access token 不返回浏览器、不进入日志或审计载荷；错误信息采用脱敏后的业务描述。
- 群 ID、群名称、组织集成、订阅和投递账本属于运行环境数据，排除在规范大会模板、克隆大会模板和公开派生快照之外。新建大会默认关闭日报且目标群为空。
- 后台页面及业务跳转继续保持统计隔离；无需向报名或支付页面加入第三方统计代码。
- 新增 `card_payload` 采用兼容性迁移。回滚前暂停组织连接或大会订阅，停止新增发送并保留账本；V2 数据保留原样，不要求数据库覆盖恢复。
- 若回到只认识 V1 的旧程序，V2 历史详情和补发可能不可用；回滚期间保持飞书日报关闭，报名、订单等原业务不受该 JSON 增量影响。

## 11. 验收与发布

### 11.1 关键验证用例

- 正常流程：保存应用、校验、加入群、选群、预览、试发、启用、到点收到一条日报。
- 时间边界：午夜、跨月、跨年、夏令时、配置时间已过、Worker 跨日恢复、修改大会时区。
- 退款口径：昨天申请今天成功、部分退款、多次渠道重试、撤回重提、后台发起、成功时间缺失。
- 发票口径：支付后待补资料、昨天创建今天提交、驳回后重提、同日多次提交、同状态编辑。
- 数值口径：完整日零访问、不完整统计日、报名替代记录、全额退款、多币种、正常负净收款。
- 可靠性：双 Worker、重复队列、重复点击、限流、超时、发送后进程退出、成功后落账失败、停用与改群并发。
- 历史：V1/V2 均可查看；补发复用原快照和原群；无快照记录不出现可执行的补发按钮。
- 权限：跨组织和无大会权限访问拒绝；无设置管理权限不能试发；深链接登录后恢复筛选且继续检查业务权限。
- 安全：浏览器、错误响应、日志、审计和规范导出无 Secret/token；日报无用户个人资料。
- UI：桌面与 375px 窄屏可配置；长大会名和群名可阅读；切大会无旧数据闪回；真实飞书桌面端和移动端卡片可读、按钮可用。
- 运行环境：核实飞书相关迁移已应用、每日访问统计完整性、正确的后台公网域名、API 与 Worker 加密配置一致。

### 11.2 实施阶段验证命令

优先运行相关模块的定向测试，然后执行仓库检查：

- `pnpm --filter @conference/contracts test`
- `pnpm --filter @conference/database test`
- `pnpm --filter @conference/integrations test`
- `pnpm --filter @conference/api test`
- `pnpm --filter @conference/worker test`

本轮没有执行上述实现验收，命令为实施交接清单。响应式检查使用隔离浏览器环境，保持用户共享浏览器自然视口。

### 11.3 发布与撤回

默认关闭所有新订阅，先在测试群完成真实试发和一次自动调度验收，再由管理员绑定正式运营群。开启订阅是运行配置变更，直接写入持久化配置，不要求重新发布前台大会模板。

代码推送前运行 `pnpm canonical:check`；若首页文案或关联配置发生变化，先按仓库规则导出并提交规范快照。飞书集成与凭据始终排除在规范快照外。

正式发布继续执行 `docs/production-deployment-runbook.md`：通过 PR 合并、目标 SHA 的主分支 CI 与镜像证明、备份、兼容迁移、运行验证和发布记录。回退时暂停飞书推送，保留订阅、投递与业务数据。

## 12. 首版范围边界

首版完成每日聚合日报。即时退款异常提醒、每周汇总、一场大会多个群、不同群的财务数据可见范围、飞书原生任务、群内审批、事件回调和个人账号绑定均作为独立后续需求。日报投入使用后，根据实际漏看和处理时效决定是否增加即时提醒。

当前设计已覆盖本次访问、报名、退款申请和发票申请的需求；真正上线前仍需由企业管理员提供并安装应用，以及在获授权的目标群完成联调。这些接入条件不影响当前方案和本地开发交接。
