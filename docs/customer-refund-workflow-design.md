# 用户申请、管理员审核与微信原路退款：最终方案 v1.0

日期：2026-09-04。状态：用户已确认，功能已在隔离分支实现并完成本地验收。生产尚未发布，未执行真实退款。实施与验证记录见 [退款功能交付记录](refund-workflow-implementation-verification.md)。

审查依据：当前仓库提交 `c942cd793d76e8a0332b4fba339f5cfae64c9c59`、上一版方案、用户提供的页面截图及微信支付官方文档。本文覆盖并替代上一版设计；审查修订记录见第 13 节。生产商户能力仍按第 11 节验收。

## 1. 推荐范围

在个人中心的购买订单中增加「申请退款」，用户提交后由管理员审核，通过后自动向原微信支付交易申请退款。资金不足时持续调度，微信通知和主动查单共同确认结果。用户可以一直查看进度，财务可以看到待处理资金和异常。

首版包括用户申请及撤回、后台审核、微信原路退款、资金不足重试、结果同步、票务和发票联动、异常提醒。复用现有账号、订单、报名详情、微信配置、API 后台任务及通知 Worker，无需新增部署服务。

首版用户申请退还该订单全部剩余可退金额；部分退款沿用管理员入口，接入同一审批记录和渠道执行流程，并记录业务依据。用户申请的金额在提交时固定，管理员不能静默改成较小金额。异常退款交由财务在微信商户平台处理，系统核验状态和资金去向。通用售后工单、自动审核、自动向其他账户转账和用户填写其他收款账户留在本轮范围之外。

最小可独立交付版本也要包含上述资金闭环；单独上线申请按钮会累积无法完成的退款。内部可拆分兼容的开发提交，对用户开放时整体验收。

## 2. 实施前已核对的基础事实

- 当前页面和提交接口均主动拒绝微信退款：`AdminRegistrationOperationsService.refundCapability`、`CommerceOperationsService.refundOrder`。
- 当前 `refunds.status` 默认 `succeeded`；通用退款路径直接更新订单、报名、票券和发票。微信执行必须改为明确记录状态，不能沿用默认成功。
- 现有 `WeChatPayService` 已有签名、应答验签、通知解密、持久化通知恢复和后台查单结构。底层请求当前把渠道错误归并为通用业务异常；本次需要保留结构化错误码。支付通知解析器仅处理支付事件，退款需独立解析器。
- 用户订单权限已有购买人判断 `customerCanManageOrder`；持有参会资格的代购受益人不会自动获得订单管理权。
- 当前订单和票券分别对报名记录有唯一约束。核销服务端持有票锁，离线批次同步也调用同一核销方法。实现沿用这套关联，核销按订单、票券顺序加锁，并校验退款暂停、订单结清和权益修复状态。
- 规范首页公开规则为「购票后 7 天内可无理由全额退款；超过 7 天不退但支持免费转让」。该大会的规则继续作为首版默认。
- 已核对当前源代码及官方资料。本次没有验证生产商户退款权限、余额、退款 IP 白名单或真实资金到账。

微信官方说明：普通支付退款按原交易退回，交易的技术退款期限为支付成功后 365 天；受理结果与最终退款结果分开确认，重试使用原商户退款单号。[退款申请](https://pay.wechatpay.cn/doc/v3/merchant/4013070371)

余额不足可能以 `NOT_ENOUGH` 拒绝申请；已经受理的退款可能维持 `PROCESSING`。官方还描述了受理超过 7 天且资金不足后关闭的情况。微信零钱通常较快到账，银行卡一般需要 1 至 3 个工作日。[退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)

退款通知需要验签、解密并快速应答，且必须配合主动查询、重复通知去重。[退款结果通知](https://pay.wechatpay.cn/doc/v3/merchant/4013071196)

商户平台手动退款可能发出 V2 XML 通知；退款必须由原支付商户号处理。[退款 FAQ](https://pay.wechatpay.cn/doc/v3/merchant/4013071200)

`funds_account` 的适用条件随商户资金类型变化，不能统一写死为 `AVAILABLE`。异常退款支持退到用户银行卡或商户银行账户，因此系统需要同时核对退款结果和入账方。[退款申请参数](https://pay.wechatpay.cn/doc/v3/merchant/4013071036)、[异常退款](https://pay.wechatpay.cn/doc/v3/merchant/4013071193)

实现参考：Vendure 将退款初始化为 Pending，由渠道结果驱动状态；本方案采用独立退款状态与结算事件的边界。Medusa 的并发退款问题用于检查额度校验与写入的竞态；本方案将额度检查、占用和审批放入同一订单锁内。[Vendure 实现](https://github.com/vendurehq/vendure/blob/master/packages/core/src/service/services/payment.service.ts)、[Medusa 问题记录](https://github.com/medusajs/medusa/issues/16012)

## 3. 24 小时时限如何定义

自动化目标：审批通过立即调度；API、数据库和调度器正常时，首次提交目标不超过 60 秒。已知资金不足时每 5 分钟原单重试，财务补足实际退款出资账户的资金后，无需再次审批或要求用户重新申请。

「有钱」指原支付商户按其资金规则选定的退款出资账户有足够可用于本次退款的资金。账户总额或其他商户余额不能直接作为依据。旧资金流商户的未结算账户与可用账户选择需按官方参数配置；其他类型遵循各自规则，不能笼统把未结算资金判为不可用。出资策略在商户验收时确认，固化到执行单，重试保持一致。

| 计时项                   | 本系统的建议目标                | 超时动作                                                      |
| ------------------------ | ------------------------------- | ------------------------------------------------------------- |
| 用户提交到人工审核       | 24 小时内处理，属于运营目标     | 提醒审核负责人，不自动批准                                    |
| 审核通过到首次请求       | 正常情况下 60 秒内              | 调度异常告警                                                  |
| 已知资金不足后的再次请求 | 每 5 分钟；支持财务手动触发一次 | 首次提醒财务，持续排队，不要求用户重新申请                    |
| 审核通过后仍未被微信受理 | 24 小时升级处理                 | 后台标红、提醒财务和大会负责人，重试继续                      |
| 微信受理到最终成功       | 跟踪微信返回结果                | 24 小时未结束进入关注列表；银行卡在官方正常时效内展示预计区间 |

用户文案表达「审核通过后发起原路退款，实际到账时间以微信支付及银行处理为准」。24 小时是内部处理和升级时限。当前官方资料不支持所有付款方式均在余额补足后 24 小时内到账的承诺。

首版通过实际退款应答判定资金不足，无需额外的余额查询权限，也无法精确知道商户每次入账时刻。资金满足后在下一次到期调度中重试，目标约 5 分钟内发起；大额队列、渠道限流、商户权限异常或系统故障会影响该目标。后台展示实际延迟和故障原因。人工点击补款按钮也需要微信应答确认，不能凭点击认定资金已足。

## 4. 用户入口与交互

主入口：`个人中心 → 我购买的订单 → 申请退款`。本人购买的报名详情同时提供入口，两处进入同一个 `/account/refunds/[orderId]` 页面。代购参会人的报名详情只显示参会权益变化，财务详情继续只向购买人开放。

申请页内容：大会、票种、关联参会人、已付金额、已退金额、本次申请金额、原支付方式、退款规则、票券影响和到账说明。用户不填写银行卡、微信号或 OpenID。原路退款跟随原交易实际支付账户，即使购买人与实际微信付款人不同也不更换收款方。

退款原因可选，补充说明可选；无理由退款不要求证明材料。未填写原因时，给微信的通用原因使用「用户申请退款」。对外退款原因单独限制微信允许的 UTF-8 字节长度，内部备注不发送给微信。

| 场景                                     | 用户看到的操作                       |
| ---------------------------------------- | ------------------------------------ |
| 符合规则且无进行中的申请                 | 申请退款                             |
| 已提交，待审核                           | 查看退款进度、撤回申请               |
| 审核通过，等待资金或提交                 | 查看退款进度、联系主办方             |
| 微信处理中                               | 查看退款进度                         |
| 已完成                                   | 查看退款详情                         |
| 被拒绝或已撤回                           | 查看处理原因；仍符合规则时允许新申请 |
| 超过大会自助期限、已使用票券或身份待核验 | 查看规则、联系主办方                 |

页面状态采用「待审核 → 已通过 → 退款处理中 → 退款成功」，将驳回、撤回和异常作为明确分支。已通过但尚未提交时，文案为「退款已通过，主办方正在安排退款」；微信受理后才显示「微信支付处理中」。每一步显示发生时间，异常显示下一步和最近更新时间。用户成功页说明退回原交易实际付款账户；非原路的人工异常处理只有核验到账去向后才展示实际处理结果。

提交前明确提示：「审核期间票券仍可使用；使用后将影响全额退款审核。全额退款审核通过后，票券暂停使用。」已通过的申请发生资金或技术异常时显示「退款处理中，请联系主办方了解进度」，不引导用户再申请。技术故障期间仍可查看进度；提交是否成功未知时按幂等键查询原申请，不能让用户通过连续点击创建新单。

用户关闭页面后任务继续运行。状态由服务端返回，刷新和重新登录能恢复；前端倒计时不驱动退款，也不推断成功。

## 5. 资格、金额与审核规则

1. 用户必须登录，服务端核对订单购买人身份及组织、大会范围，复用现有 Cookie、CSRF 和购买人权限边界。公开票码或支付链接不足以授权退款。
2. 必须存在与订单匹配的成功支付流水，且有可退金额；未支付订单使用取消订单流程，免费票使用报名取消流程。
3. 当前大会按可信支付成功时间起算 7 × 24 小时，以服务端接收并成功持久化的申请时间锁定资格，边界采用不晚于截止时间。统一用 UTC 存储时间，界面按大会时区展示。审核、余额等待导致跨过 7 天，不取消既有申请资格；撤回后新申请按新时间校验。微信 365 天技术期限在提交渠道前独立检查，临近期限提前升级处理，不以长期排队代替处理。
4. 无可信支付时间或存在多条异常成功支付时进入人工核验，不能用订单创建时间代替支付时间，也不能任取一条流水。
5. 已签到或电子票已使用时沿用现有全额退款限制。用户提交后、管理员批准前仍保留票券原资格；批准时再次锁定检查核销状态，发生变化则阻止批准并提示人工处理。
6. 一笔订单最多存在一个未结束的退款申请。提交时在订单锁内预留申请金额，避免用户申请和管理员直接退款同时使用同一额度。
7. 用户只能撤回待审核申请。批准和撤回采用相同锁与版本条件，并发时只允许一方成功。批准后自动执行的资金动作不开放用户撤回。
8. 审核结果为通过或驳回；驳回必须写明具体原因。符合已公示无理由退款条件的申请，应按公示规则履行；资金不足进入待处理队列。
9. 正常用户申请不支持审批时改金额。确需协商部分退款，只能在原申请仍待审核时记录协商依据并关闭该待审核申请，再建立管理员申请。原申请已批准后，首版不提供取消已批准退款义务或缩减批准金额的按钮。
10. 新订单保存购票时的退款政策版本；当前历史订单使用有依据的历史公示规则。无法确定时交由人工核验，不能把新增限制追溯套用到历史订单。

全额退款按「已核验退款总额 + 本次申请额达到原交易可退款总额」判断。已经部分退款的订单，申请剩余全部金额同样走全额退款的核销校验和暂停逻辑，不能仅比较本次金额是否等于原订单金额。

金额全部以整数分计算，首版普通微信退款仅支持 `CNY`。一个申请绑定一条已核实的原支付，不能按订单状态随意换支付流水。原支付历史包含已经变为 `refunded` 的成功付款记录；微信交易状态为 `REFUND` 时也不能据此推断已经全额退完。

正常路径中：可新申请金额 = 原交易可退款总额 − 已成功原路退款总额 − 未结束申请剩余预留金额。同一申请的执行尝试不重复占用额度，查询申请详情返回其自身预留金额。微信侧的退款限额与商户对用户尚欠的退款金额分别核算；发生外部退款、返回商户账户或金额差异时停止新资金指令，进入第 11 节核验流程，不能继续套用正常路径公式。

申请金额、批准金额保留原始值；已完成金额、经核验的外部履行金额和剩余预留是独立字段。任何外部退款分配给申请之前，都要明确关联原支付及该申请，按唯一退款记录入账。渠道已发生的真实退款即使与本地预留冲突，也要记录并报警，不能因本地额度校验失败而丢弃。

原交易金额、用户实际现金支付、渠道退款金额、用户实际现金退款及优惠退款分别保存和展示。无优惠的 ¥399 订单全额退款为 ¥399；含微信优惠时按渠道分摊展示实际现金退款，金额预览标明渠道确认前后的区别。每次申请使用原交易总额和本次退款金额，不使用扣除历史退款后的金额作为渠道 `amount.total`。同时校验官方退款次数和期限限制，渠道返回上限错误时转人工处理。[退款申请规则](https://pay.wechatpay.cn/doc/v3/merchant/4013070371)

## 6. 管理员工作台

在「报名管理」增加退款筛选及待审核数量；复用报名详情的「订单、支付与退款」区域进行审核，无需增加全新一级导航。

审核卡片包含购买人、参会人、票种、付款时间、申请时间、政策符合情况、原付款渠道、申请金额、已有退款、核销状态、发票影响。按钮为「同意并原路退款」「驳回申请」。确认界面同时展示大会、订单、金额和权益变化。

批准后显示渠道状态、累计等待时长、下次重试时间、最近错误和经脱敏的流水编号。提供「查询最新结果」；资金不足时提供「已补足资金，立即重试」，按钮只触发原单处理。查询与重试都限频，不能制造第二笔退款。微信明确关闭后另设「确认继续退款」，展示原批准额、已退额和本次余额；换单不能藏在普通重试按钮后面。

外部处理使用「暂停自动提交」「核验外部退款」「恢复自动处理」三个明确动作。暂停期间持续查询既有执行单。已发出但结果未知、微信处理中或异常待解决的执行单，会阻止外部新退款和自动换单，具体条件见第 11 节。

审核读取需要 `event.order.read`；通过、驳回、财务重试及现有管理员直接退款需要 `event.order.refund`，服务端同时限定大会范围。AI 管理动作继续遵守现有 critical 操作审批，新的资金相关路由在完成登记前对代理默认关闭。

## 7. 申请与渠道执行分开建模

新增 `refund_requests` 保存用户意愿与审核事实；扩展现有 `refunds` 保存每次渠道执行。一次申请正常对应一次执行；渠道明确关闭后才可能产生关联的后续执行。

申请记录包含组织、大会、订单与原支付引用、申请人及来源、申请和批准金额、币种、政策快照、审核状态、审核人及原因、申请/审核/终结时间、版本号、当前剩余预留金额。审核状态为 `pending_review / approved / rejected / withdrawn`；批准后履行状态为 `open / completed / manual_required`，批准前为空。批准是审核事实，只有核验已向付款人完成退款后才能把履行状态设为完成。驳回、撤回或履行完成时设置终结时间；驳回和撤回释放预留，异常和技术失败保持未终结。

订单增加退款执行方式 `automatic / external_hold` 及变更原因、操作人和时间。该限制统一作用于用户申请、管理员直接退款和后台执行；即使订单当前没有退款申请，外部处理中也不能新建并提交退款。

冻结原支付信息、原票券及报名 ID、原库存归属和全额退款是否取消资格等业务快照。批准后保护相关转让、票种变更和恢复资格操作；不得按回调时可变的报名资料猜测库存归属。当前一报名一订单的唯一约束保留，不增加多订单合并退款能力。

渠道执行记录新增申请引用、来源、原支付商户号、商户退款单号、微信退款单号、原交易号、不可变请求快照及摘要、出资策略、渠道原始状态、归一化状态、实际现金退款额、入账方类别、受理和成功时间、结构化错误码、下次调度时间、重试计数、租约及版本字段。入账方类别为 `payer / merchant / unknown`，后台只显示必要的脱敏描述。`SUCCESS` 作为渠道事实保存，只有入账方符合付款人退款结果时归一化为业务成功；返回商户账户或去向不明归入人工处理。

历史退款保留原始来源和状态，不将已有成功记录冒充微信核验结果。新记录必须显式指定状态，移除数据库默认 `succeeded`；现有人工记账路径同步显式写入状态及依据，未知渠道不能直接标成功。迁移期间不开启新退款，确保旧写入方升级完成后再开放。

新增 `refund_notification_inbox` 保存已经通过验签和归属验证的通知编号、必要业务字段及处理状态。日志不记录密钥、签名原文、完整通知载荷或用户收款账号。

数据库约束及事务条件：

- 每个订单最多一个未终结申请；每个申请最多一个当前执行尝试。索引约束与订单锁同时使用。旧执行记录不可覆盖或删除。
- 商户退款单号在原商户内唯一，并继续满足本系统全局单号约束；外部退款以原商户和微信退款单号去重。通知按组织、商户和通知编号去重，不能只用未验证的通知编号短路处理。
- 幂等键按调用者、操作和资源隔离，并保存请求摘要。同键不同金额、原因或版本返回冲突；重放时仍检查当前身份和权限。
- 申请的购买人引用 `customer_users`，审核人引用管理员 `users`，不把用户 ID 写进当前退款表的管理员 `createdBy`。系统执行记录标明系统来源，审计可追溯至审核人。
- 申请、订单、支付、票券和大会的关联在数据库和服务端同时校验。金额为非负整数，单次金额大于零；创建资金指令时总额不得超过可退额度。
- 状态变化采用版本条件更新，租约附带递增领取版本；过期任务不能覆盖新状态。有效的迟到渠道结果仍交统一核验处理，不能因租约过期丢弃。
- 未结清申请保护订单、报名及组织的删除路径；用户注销只处理身份关联和个人资料，不能级联删除退款与资金审计事实。

| 系统执行状态               | 含义                                   | 后续动作                                         |
| -------------------------- | -------------------------------------- | ------------------------------------------------ |
| queued                     | 已批准、等待提交                       | 调度提交                                         |
| waiting_funds              | 微信明确返回资金不足，尚未受理         | 原退款单号、原参数重试                           |
| submitting / query_pending | 提交中或结果不确定                     | 查原单；保持额度预留                             |
| processing                 | 微信已受理                             | 查询和接收通知                                   |
| succeeded                  | 微信确认退款已到付款方，金额匹配       | 幂等入账，结清已履行金额                         |
| closed                     | 微信明确关闭本次执行                   | 人工复核后可按原批准额度创建后续执行             |
| abnormal                   | 微信退款异常、退回商户或去向待核验     | 提醒财务、保留未履行义务、继续核验               |
| failed                     | 已确认未受理的权限、参数等错误         | 人工修复；原申请继续显示待处理                   |
| superseded                 | 外部退款改变剩余额度，原执行已停止提交 | 保留旧参数；核验旧单未受理后由管理员确认剩余金额 |

`closed / abnormal / failed` 不会自动撤销已经批准的退款承诺。申请仍保留剩余额度，避免客服另开退款。`ABNORMAL` 可继续转成功，禁止将其简单当作终态失败释放额度。对渠道扣款已结束但用户尚未收款的情形，分别记录资金去向与待履行金额，不再自动发出资金指令。

## 8. 调度、重试与通知

```text
用户订单页 -> API：提交申请 -> 数据库：申请与预留
管理员详情 -> API：审核通过 -> 数据库：执行单与下次执行时间
API 后台调度 <-> 微信退款申请 / 查询
微信结果通知 -> API：验签、归属验证、持久化 -> 统一结果处理
统一结果处理 -> 订单 / 票券 / 发票 / Outbox -> 现有 Worker 通知
用户订单页 / 管理员详情 <- API 返回统一状态
```

推荐由 API 内新增退款调度模块执行资金任务，复用当前微信支付维护任务模式；现有 Worker 处理退款通知消息。两个新增内部模块分别负责业务审核及幂等收敛、渠道调度；没有新的部署服务和新运行语言。

调度器每 10 秒扫描到期执行记录，通过数据库租约和条件更新领取任务，单次有界分页。定时器只负责唤醒，所有状态及下次执行时间持久化，服务重启后继续领取。一个商户的到期提交按批准时间顺序调度，默认每秒最多 1 个请求，并执行跨副本限流；同一执行单正常重提至少间隔 1 分钟，资金不足间隔 5 分钟。提交、查询和通知恢复分别限额，单笔大额失败不阻塞其他可处理订单。

请求前先持久化 `submitting` 和固定请求内容。租约超时或进程重启后，遗留提交任务先进入 `query_pending`。微信请求在数据库事务外执行；同一退款号的所有发送使用相同参数。底层返回保留 HTTP 状态、微信错误码、脱敏错误信息和是否可能已受理，不靠中文错误文案判断分支，也不把所有异常包装成同一种可重试错误。

- 已知 `NOT_ENOUGH`：5 分钟后原单重试；第一次及等待 24 小时发送去重的运营提醒。正常流程持续跟进，不能耗尽通用任务的 5 次重试后永久遗忘。
- 请求超时、网络断开、响应验签失败：结果视为不确定，先查原退款单；需要重发时保持原退款单号与原参数。不得换号试探。
- `SYSTEM_ERROR / FREQUENCY_LIMITED`：按官方原单重试规则退避，先核验是否已受理；查单不存在时也只允许原单重发。错误信息本身不能证明一笔资金动作完全未发生。[官方业务示例](https://pay.wechatpay.cn/doc/v3/merchant/4015217336)
- `PROCESSING`：前 5 分钟按约 1 分钟查单；之后按 5、10、20、30 分钟衰减，最长间隔 30 分钟，通知随时触发收敛。以上为结合官方指引的本系统调度选择。
- `CLOSED`：查询确认原单关闭，再由有权限的管理员确认沿用既有批准金额继续处理，生成新执行单号并关联旧单。用户无需重新申请。
- `ABNORMAL`：财务在微信商户平台处理，持续核验结果；不能自动改用商家转账或换收款账户。
- 权限、签名、商户归属错误：显示具体错误，等待配置修复后原单核验；避免高频请求。
- 确定参数错误：锁定原申请并记录修复依据。受理状态不明时保持原单原参数；只有确认未受理或已关闭后才允许修复执行计划。金额、原交易、商户或收款去向变化不能通过普通重试修改。
- 24 小时告警只升级处理，不自动标记失败、释放预留、取消票券或另外发起一笔退款。退款接近渠道期限时提前提醒财务。

通知处理顺序为：校验原始字节签名、时间戳和算法，解密，核对事件类型、商户、交易与退款标识、金额和币种，持久化收件箱，然后在官方要求的 5 秒内应答。持久化失败返回可重试错误，不能先返回成功再仅存于内存。持久化成功后由后台恢复业务处理。[通知规范](https://pay.wechatpay.cn/doc/v3/merchant/4013071196)

仅解析 `REFUND.SUCCESS / REFUND.CLOSED / REFUND.ABNORMAL` 等受支持的退款事件，不能复用 `TRANSACTION.SUCCESS` 的字段假设。通知缺少判断资金去向所需字段时，查单补齐后再结清。签名正确但本地找不到退款或金额不匹配的事件持久化到隔离待办并触发查单，不直接修改订单；跨组织或商户身份不符的请求拒绝。回调和查单使用同一个结果处理函数，成功状态不能被迟到的处理中或失败通知覆盖。

关键指标：最老未审核申请、最老待提交退款、资金待处理总额、调度延迟、待查询数量、异常数量、回调验签失败及已入账但权益待修复数量。用户接收审核结果和退款完成通知；自动重试不逐次发送。财务负责人使用现有大会权限和通知接收人配置，告警去重并可追踪处理人。站内进度和后台待办始终保存；短信或邮件发送失败独立重试，不能回滚退款，也不能作为退款是否成功的依据。

## 9. 票务、发票与数据一致性

- 待审核：预留退款额度，订单保持原支付状态，票券按原资格使用；驳回或撤回释放预留。
- 审核通过的全额退款：原子设置该申请拥有的票券核销暂停标记；库存暂不释放，订单继续保留付款事实并叠加退款进度。所有已批准且未结清退款，包括部分退款，都暂停新增发票出具，避免按退款前净额开票。
- 全额退款成功：取消关联报名和票券，按实际原库存归属释放一次名额；用户公开名片及参会服务按资格联动退出。保留报名、订单、支付和历史核销事实。
- 部分退款成功：保留票券资格，订单标记部分退款，按净额调整开票金额。
- 已开发票：标记退款待调整并形成财务待办；不开启自动删除发票或自动伪造红冲结果。
- 失败和待人工处理：审批后的核销暂停继续有效，财务持续跟进。首版没有单方面结束已批准退款义务、释放预留或重新放行票券的操作；不能通过标记失败恢复其他原因已取消的票券。

保持 `order → ticket → registration` 的资金操作锁顺序；核销侧持有票锁后检查暂停标记，避免反向获取订单锁。审核通过与核销并发时只有一个先成功：已核销阻止整单退款批准，已暂停阻止核销。发票写入统一遵循 `order → invoice`，只涉及发票时也先取订单锁，不能先锁发票再回取订单。开票申请、后台出具、文件上传确认和退款净额更新均使用该约束。

资料转让、改票种、补发或恢复票券、报名合并及管理员核销入口均检查该申请的暂停标记。离线批次同步继续调用统一核销校验，不能仅凭离线时间戳补记为有效签到。当前代码可确认服务端同步入口，尚未确认实际终端具备离线放行界面；凡活动启用本退款流程，核销终端必须联网取得当次许可，断网显示待核验并转人工处理，不能按缓存显示验票成功。无法满足这一点的核销终端不得用于该活动的自动放行。

回调、查单和历史退款同步以渠道退款唯一键去重。正常情况下，资金入账、申请结清、业务更新、状态日志、审计和 Outbox 在一个数据库事务内提交，库存按原始归属最多释放一次，不能减为负数。部分退款累计到原交易全部可退金额时，按全额结清处理。

退款成功是需要保存的资金事实。若外部退款发生在已核销、报名已合并、票种已改变等冲突之后，仍记录渠道事实和实际履行金额，同时设置 `fulfillment_attention` 及修复待办。只自动处理能核实属于本订单的权益；不因重新执行购票资格校验失败而丢弃退款，不误取消其他有效报名。财务修复采用按订单重放权益收敛的内部任务，过程幂等、保留审计，不能再次发送退款请求。

名片可见性、参会服务、候补递补和成功通知由带唯一业务键的 Outbox 事件驱动。服务端授权立即检查票券状态，异步展示更新失败可补偿。重复消息不重复释放库存或发送成功通知；历史外部退款导入默认只刷新可见历史，不补发过期的客户短信。

退款新入口开关作为大会退款政策字段，升级默认关闭，验收后在规范大会启用。开关同时保护用户申请和新的管理员微信退款审批；关闭后继续执行已批准退款、查询、接收通知及收敛结果。需要暂停资金提交时使用订单执行暂停，查单和通知仍保持运行。微信收款开关也不能意外停止已有退款结果同步。

## 11. 凭据、商户与外部退款

复用原微信商户号、商户 API 私钥及证书序列号、APIv3 密钥、微信支付公钥及 ID。商户号确定交易归属；私钥签名请求；公钥校验渠道响应；APIv3 密钥解密通知。微信退款 API 不需要用户另行授权 OpenID 或提交收款信息。

原交易号、商户号和支付引用固定在退款执行中。支付记录新增原商户号快照；历史记录通过原支付证据及渠道查询核实后补齐，无法确认的记录进入人工核验。当前集成商户号与原支付不一致时停止提交并提醒修复，不能拿新的商户号尝试旧订单。

凭据版本引用用于追溯，签名与查单使用该原商户当前有效的凭据；公钥轮换按响应或通知序列号选择受信密钥，不能接受未知密钥，也不能在配置更新时丢失未结退款所需的解密能力。集成禁用与商户撤权分开处理：前者不阻断历史退款，后者停止新资金提交并持续显示故障。密钥从既有加密配置读取，不进入快照、日志、代码或说明文档。

上线前核对原商户的退款权限、资金类型、出资参数和可退款资金、实际启用的出口 IP 限制、HTTPS 通知可达性及有效凭据。通知地址固定为服务端配置的公网 HTTPS 地址，不能由客户或普通管理员输入任意外部地址。官方文档已核对；这些商户级能力仍需要真实配置验收，不能根据收款成功直接认定退款全部就绪。

商户平台已退的历史订单使用后台「核验外部退款」。输入商户退款单号，向原商户查询，核对原支付、退款标识、金额、币种、状态和入账方，再通过同一结果处理函数同步。查不到或无法识别资金去向时保留人工核对待办，不允许仅凭截图或管理员点击写成成功。首次联调需验证本商户平台退款单与 V3 查询的兼容性；不兼容的历史单保留差异待办和财务证据，禁止自动重复退。

外部处理按以下顺序协调：

1. 有权限的财务先将订单设为 `external_hold`，填写原因。新申请、审批和后续渠道提交被阻止；已有执行记录继续查询和接收通知。
2. 系统等待正在执行的请求结束并核验结果。只有不存在进行中的发送、受理状态不明、`PROCESSING` 或尚未解决的 `ABNORMAL` 时，才显示可进行外部新退款。超时不能自动解除这一限制；一次查单不存在也不足以证明仍在运行的旧请求不会受理。
3. 财务在商户平台完成操作后，将退款单号交给核验入口。部分外部退款按独立记录入账，并经明确匹配抵扣当前申请的未履行金额；批准金额和旧执行请求保持不变。
4. 外部金额与本地计划冲突时继续暂停。恢复前核验全部相关执行和外部退款，并在订单锁内重算剩余义务及渠道额度。旧执行已明确关闭时，可由管理员确认继续；旧执行因金额变化停止提交时，必须取得验签通过的查单不存在结果，且无在途租约及其他未决执行，再由管理员确认剩余金额并创建新执行。旧单参数始终保留，系统不会自行修改原参数或换号。

本系统无法锁定微信商户平台中的独立人工操作。上线后的日常退款统一从本系统发起；确需外部处理时遵循暂停与核验流程。绕过流程发生的外部退款由通知或每日对账发现后导入，并冻结冲突订单；不能声称系统能够预先感知所有外部退款。

异常处理若退回商户账户，渠道原始结果照常保存，用户申请仍显示待人工处理，不发送退款完成通知，不释放剩余义务或再次自动退款。财务需核实商户平台中是否仍可处理该异常单；资金已退回商户且无法继续向用户退款时，转既有财务流程履行剩余义务，系统持续保留人工处理待办。首版不承诺自动核验独立线下转账，不提供无证据的结清按钮，也不调用向其他账户付款的接口。[异常退款方式及入账方](https://pay.wechatpay.cn/doc/v3/merchant/4012810603)

首版不依赖商户平台 V2 XML 自动通知完成同步，使用明确的查询核验入口；V3 API 申请显式携带专用 V3 通知地址。上线前核对既有商户平台回调配置，避免把 V2 XML 指向现有支付成功或 V3 退款处理器。每日人工财务对账检查漏单、金额差异和退回商户的异常，后台待办记录核对人及处理证据。系统对已知退款持续自动查单；全量微信账单自动导入不纳入首版。

## 12. 验收、发布与回退

验收按以下场景和可观察结果执行：

| 场景                                                   | 必须满足的结果                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------ |
| 7 天边界、无原因申请、审核跨期、撤回后重申、缺可信时间 | 资格按原政策和服务端申请时间判定；历史订单不被新限制追溯覆盖       |
| 购买人、代购受益人、其他用户、跨组织及不同管理员权限   | 只有正确购买人能申请；未授权者无法查看财务详情或审核               |
| 重复提交、审批双击、撤回与审批并发、管理员直接退款冲突 | 最多一个活跃申请，额度只预留一次，相同幂等键不同内容返回冲突       |
| 资金不足后补款、持续等待 24 小时、限流及大批量积压     | 原单按计划重试；目标时限可观测，超时升级且任务不被有限重试次数丢弃 |
| 请求超时但已受理、通知先到、查单不存在、响应签名错误   | 保持原单和预留，先核验；不猜测成功，不换号试探                     |
| 多副本、租约过期、进程在提交及入账前后崩溃             | 新进程恢复持久任务，迟到结果不覆盖终态，资金动作幂等               |
| `PROCESSING / CLOSED / ABNORMAL / SUCCESS`，关闭后续单 | 所有分支可追踪；明确关闭后才允许确认新单，不超过剩余批准金额       |
| 退款成功但退回商户，或入账方无法识别                   | 保存渠道事实，保留用户待处理义务，不误发到账通知                   |
| 通知重复、乱序、跨商户、未知退款、金额或币种不一致     | 归属验证先于去重，异常隔离；仅可信且匹配的结果可结清               |
| 审批与核销、旧二维码、离线批次和管理员补核销           | 同一票锁裁决；批准后无法被服务端核销，终端断网不自动放行           |
| 审批或成功与开票、出具文件、转让、票种变化并发         | 锁顺序一致；全额和部分退款均保护开票净额，冲突保留修复待办         |
| 全额、部分、累计全额、优惠订单和重复成功事件           | 原实付历史正确；现金和优惠分别显示，权益及库存最多处理一次         |
| 外部暂停遇到正在发送、处理中或结果未知的退款           | 不允许外部另开退款；旧单查询和通知继续运行                         |
| 外部部分退款、已有预留、历史导入和恢复执行             | 真实资金事实不丢失，金额差异冻结，旧参数不变，不重复发送历史短信   |
| 更换凭据、原商户不匹配、停收款、关闭新入口             | 原商户路由稳定；历史退款可恢复，错误不会变成成功                   |
| 发票或权益修复失败、通知渠道失败                       | 钱款结果保留，修复独立重试；不会重发资金请求                       |
| 兼容迁移、历史人工退款、用户注销或报名删除             | 不伪造历史核验结果；未结退款和审计事实不被级联删除                 |
| 手机申请、撤回、后台审核、重新登录及敏感页面访问       | 进度可恢复，申请表有提交中和错误反馈，敏感页面不加载第三方统计     |

实施后运行受影响 API、Worker、Admin 测试与数据库集成测试，再运行 `pnpm check`、`pnpm canonical:check` 及退款专项验收。并发、崩溃恢复和真实数据库约束必须通过集成测试，不能全部用内存模拟代替。浏览器验收采用自然窗口或隔离测试环境，遵守项目共享视口规则。

真实小额支付和退款只在明确授权的测试交易上验证，不拿客户订单试验；同时核对渠道结果与订单、票券、发票和库存。资金不足、极端时序等难以稳定制造的状态使用可信渠道样例和故障注入测试，再以真实成功退款验证签名、回调与查单链路。

开放入口前的门槛：原商户身份及出资配置核实；专用通知和主动查单均通过；全链路授权测试退款成功；无未处理的迁移错误；历史不明退款订单已隔离；核销终端符合联网校验要求；退款负责人、补款负责人及实际可达的告警渠道已落实。任一资金相关门槛未满足时保持入口关闭，后台明确展示欠缺项。短信模板尚未就绪可使用现有可用通知渠道，站内状态与财务告警不能缺失。

工程拆为数据与状态、微信执行、界面、业务联动、验收五组工作，在同一个受控功能版本内交付；各组不单独对用户开放。按生产 Runbook 经 PR、CI、已合并 main 的证明镜像发布；上线前数据库备份，使用兼容增量迁移。当前默认大会政策或公开说明更新后运行 `pnpm canonical:export` 并提交完整与公开快照，所有推送前通过规范检查。

故障时先关闭新申请和新批准，保留现有退款查询、通知和完成处理。存在未结束外部退款时不能直接回退到完全不认识新退款状态的旧镜像。修复当前版本或保留兼容的退款处理版本，待未结束退款完成或明确交接后再回退前端和其他代码；禁止通过回滚数据库抹去已发生的资金事实。

本轮涉及超过 8 个文件及两个内部服务模块，属于跨前后台的资金流程迭代。最关键的外部依赖是原商户可退款能力；该能力未通过验收时，可以完成开发和自动化测试，生产自助入口继续关闭。真实退款权限与账户配置的缺失必须按具体项报告，不用更换商户或人工写成功来绕过。

以下表格记录方案审查阶段的修订。用户确认后的代码实现和验证结果另见交付记录；生产商户验收仍按第 11、12 节执行。

| 级别 | 上一版遗漏或不清楚的地方                         | 本版修订                                                                         |

| 高   | 外部退款和本地自动重试可能同时执行               | 增加订单级暂停、在途请求核验、外部退款导入和恢复条件，披露无法锁定商户平台的边界 |
| 高   | 只看退款成功状态，可能误把退回商户当成用户到账   | 分开保存渠道结果、入账方和用户退款义务，异常不自动结清                           |
| 高   | 权益状态冲突可能阻止保存真实退款结果             | 资金事实入账，权益冲突生成可重放修复待办                                         |
| 高   | 租约超时、错误分类、换单条件和额度占用不够明确   | 持久请求快照、先查单、结构化错误、明确关闭后确认续单、数据库唯一约束             |
| 高   | 核销与开票联动只描述正常入口                     | 补齐旧票码、批次核销、联网要求、管理员入口及部分退款开票锁                       |

| 中   | 旧接口、历史数据、用户审计身份和密钥轮换未具体化 | 异步结果适配、移除默认成功、保留历史来源、分别关联客户及管理员身份               |
| 中   | 已批准退款失败后可由管理员「结束义务」但没有依据 | 删除该操作；保持已批准义务和核销暂停，人工异常持续可追踪                         |
| 中   | 通知失败、商户平台查询不兼容及回退条件不完整     | 状态与通知分离，差异待办保留，旧版本不接管未结退款                               |

本方案保留的业务决定：用户退全部剩余可退金额；管理员审核；默认微信原路退；待审核可撤回；批准后暂停全额退款票券；资金不足自动重试；银行卡到账按渠道实际时效展示。首版的人工边界包括商户异常、身份不清、多条异常成功支付和无法查询核验的外部退款，均保留负责人及处理记录。

本节对应方案审查阶段，当时仅修改设计文档。后续实施没有修改生产商户设置或真实订单；文档不包含客户身份、真实交易标识或凭据。

## 14. 实施后复核补强（2026-09-04）

- 商户配置更新、退款创建与审批、外部退款关联、回调入箱统一持有组织级配置事务锁；需要多个锁时依次取得配置、订单、票券和报名锁。历史主动查单继续可用。
- 渠道错误保留 `verifiedResponse`。无签名或验签失败的查询响应保持结果未知，不能用于退役旧执行、放行新单或认定未受理。
- 外部退款先结清、旧提交后返回明确拒绝时，旧执行转为 `superseded`。已完成申请保持完成，剩余义务需经核验和明确确认后继续。
- 多笔成功支付或原支付金额异常时，已核验现金事实仍保存在对应支付下；订单转人工核验，票券、库存和发票保留，防止重复支付中的一笔退款误取消整体权益。
- 资金成功后权益补偿失败时，订单保持暂停并阻止核销、权益修改与开票。修复成功后，票务与库存只处理一次。
- 保存渠道确认的实际支付、现金退款和优惠退款。历史字段未知时返回空值，不推断为零；只有每笔成功退款的明细均已确认时才展示对应汇总。短信 `amount` 沿用订单退款总额参数，页面和邮件正文展示现金及优惠；启用前核对短信模板中的金额口径。
- 已完成或撤回申请的延迟审核通知停止发送，仍未处理的财务及权益异常持续通知。后台筛选、订单切换和用户页面刷新均丢弃过期请求结果。
