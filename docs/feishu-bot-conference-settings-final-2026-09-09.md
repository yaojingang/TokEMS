版本：1.0  
日期：2026-09-09  
状态：方案审阅与修订完成，等待用户确认后实施  
源码基线：本地 main，`f44a5e1` 及当前工作区；本次未修改功能代码

## 1. 本次确认的产品

在「大会配置 → 飞书机器人」中提供三步接入：**连接应用 → 选择接收群 → 试发并开启**。组织共用一套企业自建应用凭据，每场大会独立选择一个企业内部群，每天默认在大会时区 09:00 推送昨日运营数据。

日报包含访问、报名、支付、退款申请、退款成功、发票需求与资料提交，并附当前累计、待审核和异常关注项。群消息只含聚合数据，操作按钮进入 TokEMS 后台；审核、退款与开票继续使用原有权限和业务流程。

复用当前飞书客户端、数据库、Outbox、BullMQ 与 Worker，补齐界面、指标和可靠性。CLI 用于接入协助与诊断，生产自动推送直接调用飞书 OpenAPI。首版固定指标、每日一次、一个群，无新增服务容器或语言运行时。

当前提案的确认范围包括以下五项：

1. 主入口位于大会配置，组织设置提供共用连接的管理入口。
2. 使用企业自建应用，由企业管理员在飞书完成应用权限和发布审批。
3. 采用三步向导，试发成功后由管理员明确开启自动日报。
4. 首版接入企业内部正常群；外部群、群内审批、即时提醒和多群推送为后续独立需求。
5. 按本文件实施和验收，开发量初估 5 至 8 个工作日，企业审批等待时间另计。

## 2. 方案审阅结论与修订

本轮审阅覆盖原方案、相关调用链、现有权限和 UI 组件，并重新读取飞书官方文档。下表表示设计问题已经在本版中明确处理，功能代码的修复与验证属于确认后的实施。

| 审阅发现                       | 触发与影响                                                                              | 最终处理                                                               |
| ------------------------------ | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 保存后校验可能中断组织连接     | 原方案第 4.3 节先保存；`feishu-digest.service.ts` 更新凭据时立即暂停订阅                | 新凭据验证通过后才原子替换；失败保留旧连接                             |
| 连接状态不能代表发消息权限     | 获取机器人信息和群列表成功，仍可能被群禁言或缺少发送权限                                | 分别显示凭据、群读取、试发三个验证结果                                 |
| API 试发绕过定时发送服务       | 当前 `sendTest()` 直接发送，Worker 停止时仍可试发成功                                   | 试发、补发和自动日报共用 Worker 发送路径；补调度心跳                   |
| 配置版本缺少明确边界           | 现有 `revision` 也随调度、验证和发送结果变化；旧试发可能晚于凭据替换返回                | 区分配置版本与运行状态；试发验证绑定连接版本、群和大会                 |
| 群状态与分页完整性不足         | 当前客户端过滤 `disbanded`，官方返回 `dissolved/dissolved_save`；不完整列表不能证明退群 | 按官方枚举处理；完整分页成功后才协调失效绑定                           |
| 退款缺少成功时间会污染未来日报 | 原方案可能因历史缺失让每日退款和净额持续为空；人工退款路径也未填 `succeededAt`          | 区分可信发生时间与已成功的时间上界，补人工确认路径和缺失数据提示       |
| 财务名称容易被理解为实到账     | 支付流水金额含业务订单口径，未表示银行结算或扣手续费后的金额                            | 统一使用支付金额、退款金额、支付净额，并写明金额口径                   |
| 预览、试发、历史的时点关系不清 | 预览与试发之间会新增订单；重试重新统计会改变同一条消息                                  | 预览注明生成时间；试发重新取数；同一投递重试固定快照和卡片             |
| 失败状态缺少完整恢复路径       | 生成失败没有快照，发送中断结果未知，队列重放也可能遇到仍在发送的任务                    | 明确生成重试、租约、结果待确认和人工处理；不用同一个“重试”按钮混合处理 |
| 变更范围和权限同步遗漏         | 更换组织机器人影响多场大会；新接口与现有 Agent 操作目录需保持一致                       | 显示受影响大会、统一权限约束，补操作目录与契约验收                     |

关键源码证据：

- `apps/api/src/common/feishu-digest.service.ts`：`updateConfiguration()`、`verify()`、`sendTest()`、`resendDelivery()`。
- `apps/worker/src/feishu-digest.worker.ts`：订阅调度、`sending/generating` 状态和配置核验。
- `packages/integrations/src/feishu.ts`：群分页、群状态、发送结果分类。
- `packages/database/src/feishu-digest.ts`：现行统计窗口、退款、发票和金额聚合。
- `apps/api/src/common/commerce-operations.service.ts`：人工退款成功写入与 `processedAt`。
- `apps/api/src/common/refund-workflow.service.ts`：渠道结果核验、成功时间、当前执行单和关注规则。
- `apps/api/src/common/agent-operation-catalog.ts`：飞书配置、群列表、日报预览和历史的现有只读操作。

## 3. 接入引导与授权体验

### 3.1 明确授权对象

后台功能名称为「飞书机器人」，主操作使用「连接飞书应用」。帮助文案说明：「连接企业自建应用后，机器人可向已加入的群发送大会日报。应用权限与发布由企业管理员在飞书完成。」

飞书应用安装、机器人入群和 TokEMS 配置保存分别由各自系统负责。首版提供官方入口、分步说明和自动诊断；后台不显示没有实现的个人扫码授权或自动发布承诺。

企业自建应用需要在飞书开放平台配置并通过企业内部发布审批；权限变更也需要发布生效。依据：[企业自建应用开发流程](https://open.feishu.cn/document/home/introduction-to-custom-app-development/self-built-application-development-process)。

### 3.2 第一步：连接应用

首次打开显示三个步骤的进度，展开「连接应用」。已有组织连接时自动显示机器人名称，进入第二步。

提供两种折叠内容：

- **还没有应用**：默认展开开通清单，按钮「前往飞书创建应用」，跳转官方 [开发者后台](https://open.feishu.cn/app)。
- **已有应用**：直接填写 App ID、App Secret，旁边提供「在哪里找到这些信息」。

开通清单为：创建企业自建应用 → 启用机器人 → 开通两项权限 → 创建版本并提交企业审核。两项权限分别显示名称、用途和复制按钮：

| 权限                     | 页面中的用途说明                         |
| ------------------------ | ---------------------------------------- |
| `im:chat:read`           | 读取机器人已加入的群，供你选择日报接收群 |
| `im:message:send_as_bot` | 以机器人身份向所选群发送日报             |

主按钮「验证并连接」。按钮下提示：「验证通过后保存连接；此操作不会向群发送消息。」检验过程中依次显示凭据、机器人能力、群读取检查结果；发送能力显示「待试发验证」。不用单一“已授权”状态掩盖未完成环节。

表单规则：

- App ID 说明为「应用凭证中的 App ID，以 cli_ 开头」。只去除首尾空格，不擅自改写输入。
- App Secret 使用密码输入框，可短暂显隐，不提供已保存密钥的回显或复制。
- 相同 App ID 下，不输入新 Secret 表示保留现有值；更换 App ID 必须提供对应的新 Secret，禁止把旧 Secret 拼给新应用。
- Secret 不进入浏览器持久化存储、URL、埋点或诊断信息。提交成功或离开页面后清除输入值；提交失败在当前页面保留，便于修正。
- 关闭或刷新后恢复已经保存的进度。尚未提交的 Secret 需要重新填写，界面明确说明。

**已有连接的替换保护**：先在服务端验证候选凭据和群读取能力，成功后以配置版本条件原子保存；验证失败、超时或版本冲突均保留旧连接。更换前列出本组织受影响的大会和数量，主操作改为「替换连接并暂停相关日报」。替换成功后各大会重新试发、手动开启；旧凭据失效后无法继续发送的情况按故障提示处理。

权限已在飞书开通但尚未发布时，提示发布生效流程。服务端不能准确判断企业审批环节时显示「等待飞书配置生效」，提供「重新检查」，不编造具体审核状态。

提供「复制给企业管理员的配置说明」，内容包括用途、两项权限、发布要求和机器人入群步骤，排除任何密钥。复制只写入本机剪贴板，由用户自行发送。

### 3.3 第二步：选择接收群

显示当前机器人名称、应用 ID，以及「仅显示此机器人已加入的群」。选择器支持群名搜索，重名群使用短 ID 辅助区分；不需要用户填写完整群 ID。

群为空时显示：

> 暂时没有可选择的群。请在飞书目标群的「设置 → 群机器人」中添加当前应用机器人，然后返回这里刷新。

主按钮「刷新群列表」。同时提供「已添加仍找不到」帮助，按顺序检查机器人是否同名、应用是否发布、群与应用是否属于同一企业、当前群是否已解散。复制机器人名称便于群管理员准确搜索。

首版允许机器人所在的企业内部正常群。官方列表中的 `external=true`、`dissolved`、`dissolved_save` 分别标明外部或不可用；不将未知字段强行解释为内部正常群。不支持的群显示原因且不可选择。群接口的成员范围和状态依据：[群列表](https://open.feishu.cn/document/server-docs/group/chat/list)。

群列表按完整分页结果处理。任一页失败、游标缺失、达到数量上限或结构不符合预期时显示「群列表未读取完整，请重试」，保留既有绑定；只有完整成功且版本一致的查询，才能证明某目标群已不可用。

选择群后默认每天 09:00，大会时区只读。主按钮「保存并继续」，保存当前大会的关闭状态配置并进入第三步。新群与旧群不同时，按钮和旁文明确说明将暂停当前大会日报；其他大会不受本次选群影响。

### 3.4 第三步：试发并开启

展示接收群、大会名称、时间、当前日报预览，以及独立的日期与生成时间。预览说明：「以下数据生成于页面标注时间，试发时会更新统计。」预览失败显示重试入口，不展示伪造的零数据。

发送测试前显示一次未勾选的确认：

> 我确认该群成员可以查看本大会的汇总经营数据。

主按钮「发送测试日报」。点击后创建持久化任务，立即返回任务 ID；页面依次展示「等待发送」「正在发送」「已发送」或具体失败状态。关闭页面不终止任务，再次打开可恢复结果；同一操作的双击、刷新重试复用幂等键。

试发走与自动日报相同的 Worker 路径，卡片带「测试」标记。未得到确定发送结果前，不开放开启按钮。等待较长时显示「任务仍在处理，可稍后在发送记录查看」，避免将前端等待超时误判为发送失败。

成功后显示：「测试日报已发送到『群名』。请在群内核对内容，确认后开启每日推送。」主按钮变为「开启每日推送」，旁边说明未来第一份报告的数据日期与发送时间。此时无需再次弹出相同的数据可见确认。

开启前服务端重新核对连接版本、目标群、试发结果、配置版本、大会状态、后台链接和发送服务状态。试发期间改过应用或接收群，则提示重新试发。单纯修改发送时间保留有效的群测试结果。

### 3.5 飞书 CLI 的配合方式

本机核验版本为 `lark-cli 1.0.67`。接入诊断可使用 `im +chat-list --as bot` 检查群列表，以及 `im +messages-send --as bot` 的 `--msg-type interactive`、`--content`、`--idempotency-key`、`--dry-run` 检查卡片请求。命令能力以该版本帮助为依据，身份和配置方式参考 [官方 CLI 文档](https://github.com/larksuite/cli/blob/main/README.zh.md)。

联调使用与 TokEMS 相同企业应用的独立 profile，明确应用身份和目标群；真实发送由授权测试操作触发。常规后台用户通过三步向导完成接入，无需安装 CLI。生产 Worker 使用既有 OpenAPI 客户端，运行依赖由服务器管理；CLI 的直接发送结果只用于排查，不写入后台的群试发验证标记。

## 4. 页面布局、文案与日常管理

### 4.1 布局与组件

路由为 `/events/:eventId/settings/feishu`；组织连接入口为 `/manage/settings/feishu`。两处共用连接表单与诊断组件，组织页列出连接影响的大会，日报详情仍进入各自大会配置。

沿用当前 Vue 3、普通 CSS 和已有设置页组件。新页面使用既有全局变量与局部 CSS，不引入第二套组件库、字体或样式框架。源码已有主色 `#1b416f`、正文色 `#172233`、辅助色 `#67707b`、边框色 `#dce1e3`、4/6/8px 圆角；正文使用当前系统中文字体。

首次接入以纵向步骤为主，每一步只有一个主要按钮；已连接状态隐藏完整教程，保留「接入帮助」。主内容区至少 960px 时，设置与预览采用约 3:2 的两栏；更窄时依次排列。发送记录位于下方，窄屏改为逐条记录，长群名自然换行。

### 4.3 配置变更规则

- 修改时间：保存后重算下一次计划，当天已经生成过自动日报时不再新建一条。
- 修改群：保存时暂停本大会，清除群试发标记，新群试发成功后再开启。
- 更换组织应用或密钥：验证通过后替换，暂停受影响大会，清除与旧连接版本关联的试发结果。
- 暂停：保留群与时间，取消尚未进入发送阶段的旧任务。恢复时仅在连接版本、群和试发仍有效的条件下直接开启。
- 群重命名：更新显示名，不改变接收群身份，也不单独清除测试结果。
- 大会草稿或配置中：允许预览及手动试发，自动推送关闭；归档后禁止新发送，保留历史。
- 大会结束：按原配置继续发送财务与待办日报，管理员可暂停；不自动新增提醒频次。

## 5. 日报内容与准确性

### 5.1 时间定义

日报日期为大会时区前一完整自然日，窗口左闭右开。当前累计和待办按首次生成时的只读一致性快照统计。消息显式显示报告日期、时区和生成时间，后台当前列表的数量可能随业务变化。

首次开启后的计划只取未来时间；当天设定时间已过，则从次日开始。夏令时导致本地时间不存在时顺延到首个有效时刻；重复时刻选择首次出现的一次，配合日期唯一键避免重复。无法解析时区时阻止启用并说明原因。

### 5.2 指标表

| 分类 | 名称                           | 定义                                                                                                       |
| ---- | ------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 昨日 | 访问次数                       | 大会第一方日访问表，沿用现有去重与机器人排除口径；不展示 UV 或转化率                                       |
| 昨日 | 新增报名记录                   | 在窗口创建，且未在窗口结束前被替代的报名记录；窗口后的替代不改写该日新增。当前待办继续排除全部已被替代记录 |
| 昨日 | 支付订单 / 支付金额            | 按可信 `payments.succeededAt`，订单去重、支付流水金额求和；成功后退款的支付仍计入发生日                    |
| 昨日 | 新增退款申请                   | `refund_requests.createdAt` 内的申请数，用户与管理员来源分别可追溯；申请 ID 去重，执行重试不增加申请数     |
| 昨日 | 退款成功 / 退款金额            | 按核实成功时间和成功退款流水计数、求和；部分退款计实际成功金额                                             |
| 昨日 | 支付净额                       | 昨日支付金额减昨日退款金额，可为负；采用订单交易口径，未扣除手续费，不表示银行结算或利润                   |
| 昨日 | 新增开票需求                   | 在窗口创建的 `invoice_requests`，包括支付后自动建立的待补资料需求                                          |
| 昨日 | 提交开票资料                   | 窗口内首次或再次从其他状态进入 `pending_review` 的状态日志，按发票申请 ID 去重；同状态编辑不重复计数       |
| 昨日 | 成功签到次数                   | 成功核销记录数；在进行中和结束阶段展示，与独立签到人数区分                                                 |
| 当前 | 累计与库存                     | 累计访问、有效报名、已确认参会、当前有效已支付订单、订单净额、剩余库存；使用后台同名口径                   |
| 当前 | 报名待审核                     | 当前 `pending_review` 且未被替代的记录                                                                     |
| 当前 | 退款待审核 / 等待资金 / 处理中 | 按申请 ID，结合审核状态和当前有效执行单统计                                                                |
| 当前 | 退款需关注                     | 与现有退款列表 `attention` 的人工处理、关注原因及超时规则共享判定                                          |
| 当前 | 发票待处理                     | `pending_review`、`issue_failed`、`adjustment_required` 的并集                                             |
| 当前 | 发票待补资料 / 开票中          | 分别统计 `awaiting_details` 和 `issuing`                                                                   |
| 当前 | 其他关注项                     | 复用当前支付异常、合作咨询、低库存指标；低库存阈值沿用代码                                                 |

退款状态统计按申请去重，关注项可能与待审核或等待资金重叠。卡片不展示把这些分类机械相加得到的“待办总数”。

### 5.3 退款时间与历史缺口

新渠道退款使用已经校验的渠道成功时间；新人工确认退款使用后台记录成功的时刻，同时补写 `succeededAt`，页面说明人工数据按系统确认时间统计。

旧人工退款仅在 `source=manual` 且 `providerPayload.processedAt` 能确认来自现有服务器写入路径时，使用该确认时间。其他缺失记录不以创建时间代替成功时间。

成功状态与 `updatedAt` 同事务落库构成时间上界：当前已成功且 `updatedAt` 早于报告开始，能够说明该流水此前已成功，故排除该日；它不会永久阻断未来日报。对状态更新时间不可靠的历史导入，上线预检只读列出异常；确需观察标记时，在备份和写冻结后的兼容迁移阶段，将当时已核实为成功的流水记入既有退款 JSON 元数据 `digestSuccessObservedAt`。该字段只表示“至此已成功”，不补造成功日期，也不改变金额或退款状态。

若可信上界和其他证据仍不能排除流水属于报告窗口，相关日退款笔数、金额和支付净额标记不可用，其他指标继续发送。质量标记只对受影响窗口生效，历史缺口不全局扩散。该判断、人工路径及任何上线观察标记均有定向测试和审计，不能凭管理员随手填写的时间解除缺口。

### 5.4 其他质量规则

- 访问采集未满完整日或发生不兼容的时区变更时显示「暂无完整数据」；完整日无访问才显示 0。
- 按币种聚合校验。单大会多币种时，金额部分提示到后台按币种查看，不直接相加；数量部分继续展示。
- 成功支付重复、退款超过有效支付等异常，不通过随意去重或截断数值掩盖；按后台规则提示数据待核对。
- 发票需求、资料提交与当前待办是不同阶段，不合并为单一“新增申请总数”。
- 同一投递重试固定快照；新增一次试发则更新统计。已发报告不因迟到回调自动改写，后台重查可看到更新，时间说明交代差异。
- 历史 V1 保留原指标名称和定义；缺少新版指标显示「该版本未统计」。V2 只用于新生成的日报。
- 聚合异常不能回落到全零卡片。质量问题用结构化标记定位到具体指标，数据库不可读取时生成失败。

## 6. 消息卡片与后台落点

静态 Card JSON 2.0 的顺序为大会与日期、昨日新增、当前待办、当前累计、按钮、生成时间。需人工处理时标题橙色，其余蓝色；长内容优先折叠解释文字，保留指标名称和值。以下全部为虚构示意数据：

> **中国 GEO & AI 营销大会｜运营日报**  
> 数据日期：2026-09-08 · Asia/Shanghai  
> **昨日新增**  
> 访问 1,286 次 · 新增报名记录 36 条 · 支付订单 28 笔  
> 支付金额 ¥11,172.00 · 新增退款申请 3 笔  
> 退款成功 1 笔 / ¥399.00 · 支付净额 ¥10,773.00  
> 新增开票需求 8 笔 · 提交开票资料 5 笔  
> **当前待办**  
> 报名待审核 6 · 退款待审核 2 · 退款等待资金 1  
> 发票待处理 7 · 发票待补资料 3  
> **当前累计**  
> 已确认参会 268 人 · 剩余库存 232 席  
> [查看大会] [审核报名] [处理退款] [处理发票]  
> 生成于 2026-09-09 09:00，当前待办以此时刻为准

| 按钮     | 目标                                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 查看大会 | `/events/:eventId/overview`                                                                                                                  |
| 审核报名 | `/events/:eventId/registrations?status=pending_review`                                                                                       |
| 处理退款 | `/events/:eventId/registrations?panel=refunds&refundStatus=pending_review`；有需关注项时优先 `attention`，其次待审核，再其次 `waiting_funds` |
| 处理发票 | `/events/:eventId/invoices?worklist=actionable`                                                                                              |

补齐报名状态筛选初始化、退款面板自动展开和发票多状态工作列表。发票查询新增固定 `worklist=actionable`，与单状态 `status` 同传时拒绝请求；分页、导出和计数使用相同条件。过滤参数做枚举校验，刷新、登录回跳和浏览器后退均恢复正确状态。

按钮最多四个。登录只恢复安全的站内目标路径，服务端继续验证操作权限。生产链接必须来自有效 HTTPS 后台域名，缺少配置时禁止正式启用；本地测试可使用现有本地域名。历史卡片不执行 HTML，标题与 Markdown 特殊字符转义，链接只接受固定后台域名和允许路径。

卡片请求体按 UTF-8 编码后的完整请求体计大小，内部预算不超过 24 KiB。飞书官方卡片请求上限为 30 KB；超出内部预算则缩减说明或生成明确错误，不拆成多条未经定义的日报。JSON 2.0 需飞书 7.20 及以上客户端。依据：[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)、[卡片 JSON 2.0](https://open.feishu.cn/document/feishu-cards/card-json-v2-structure)。

## 7. 运行链路与可靠性

```text
后台保存配置 → PostgreSQL 组织连接 / 大会订阅
                          ↓
      Worker 每分钟扫描 → 唯一投递 + 事务 Outbox
                          ↓
     试发 / 补发请求 → 事务 Outbox → BullMQ
                          ↓
        同一发送 Worker → 固定快照 / 卡片 → 飞书群
                          ↓
             投递账本 / 诊断 → 后台状态与历史
```

### 7.1 配置与验证版本

连接增加独立 `connectionVersion`，只在影响发送授权的配置替换、停用或重新启用时变化。大会订阅增加 `configVersion`，只在群、时间、时区和启停等设置变化时增加。现有 `revision` 保留为运行层乐观锁，诊断检查、`nextRunAt` 或最近发送时间更新不冒充配置变更。

试发验证记录绑定组织、大会、当前连接版本和目标群；所有开启条件都需要有效的验证时间。保存、发送、补发携带客户端读取的配置版本，过期请求返回冲突，不能覆盖其他管理员的新配置。

`manual_test` 允许尚未完成群验证的当前已保存目标，校验连接、配置版本、可见范围确认及群可用性；`scheduled` 和 `manual_resend` 还必须具备该连接版本下有效的目标群试发结果。首次试发不依赖自身将要建立的验证标记。

每次投递保存连接版本、大会配置版本和接收群快照。发起网络请求前，短事务锁定相关配置并核对版本、状态和发送租约，再原子进入 `sending`。在此之后发生暂停或改群，消息仍可能到达；后台文案明确这一边界。晚返回的旧试发可以记录“已发送”，但不能验证新连接或新群。

### 7.2 调度、租约与发送结果

- 每分钟扫描到期订阅，使用现有 `FOR UPDATE SKIP LOCKED` 和日期唯一键。事务同时写投递和 Outbox，队列重放不创建额外自动日报。
- `generating` 和 `sending` 使用数据库租约令牌、到期时间和条件更新。未过期的发送租约遇到重复任务时保持处理状态；租约到期后才按发送结果恢复，避免将正在成功发送的任务误标为未知。
- 首次网络提交前固定 `aggregateSnapshot`、完整 `cardPayload`、群和内容摘要。发送重试不重新统计，也不更换群。
- 每条投递使用 `uuid=delivery.id`。飞书同 UUID 一小时内至多成功发送一次；跨小时由本地账本和恢复策略控制，不宣称跨系统绝对只发送一次。[官方去重规则](https://open.feishu.cn/document/server-docs/im-v1/message/create)
- 明确的限流拒绝可重试，发送尝试最多 5 次，默认间隔 30、60、120、240 秒；有 `Retry-After` 时取更长等待。同一投递首次提交一小时后停止自动发送，进入人工处理。
- 网络超时、发送 5xx、响应结构损坏、成功响应缺少消息 ID 等结果不确定情况统一进入 `unknown`，不当作明确失败自动补发。
- 如果已保存飞书消息 ID 但本地收尾失败，恢复任务只补账，不再次发送。消息 ID 未能持久化时按未知处理。
- 增加每分钟的账本恢复扫描，处理长时间未入队、过期生成租约和过期发送租约。业务账本是依据，不能仅依赖 Redis 队列尚在。

生成租约和发送租约均为 120 秒，生成超过 30 秒时续租，发送前重新获取完整租约。生成超时作为生成错误；飞书请求最长 15 秒，进入网络请求后不再由其他 Worker 接管发送。实例暂停后恢复执行仍需核对租约令牌；租约已经失效的实例不得继续发起请求。

### 7.3 迟到、改时间与人工处理

| 情形                         | 行为                                                                                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 服务重启，迟到不超过 12 小时 | 处理原定报告日期，在卡片标明延迟                                                                                                               |
| 超过 12 小时                 | 留下 `skipped` 记录及原因，继续未来计划；不集中补发多天日报                                                                                    |
| 修改时间后当日唯一记录已存在 | 保留原记录，未来新时间从下一报告日开始；不重新创建当日日报                                                                                     |
| 生成失败且没有快照           | 允许「重新生成」，沿用原报告日期和当前生成时间，明确当前累计与待办会更新；仅在 `firstSendStartedAt` 为空、原配置仍有效且未过 12 小时窗口内开放 |
| 明确发送失败且有快照         | 可「补发」，创建关联原记录的新投递和新 UUID，使用原数据并标记补发                                                                              |
| 结果待确认                   | 先看群消息，可标记「人工确认已收到」或明确补发，记录管理员和时间                                                                               |
| 已改群或换应用后处理旧记录   | 不自动发送旧数据；原记录保留查看，重新试发当前配置；旧授权版本的补发入口关闭                                                                   |
| 原记录已成功、已取消、已跳过 | 不提供再次发送；试发仍是独立且显式的操作                                                                                                       |

“人工确认已收到”保留原 `unknown` 技术结果，另记处理结论，不伪造飞书消息 ID。人工补发同样使用幂等键；原投递只允许一个未终结的补发子任务，避免多人并发点击造成多条消息。

### 7.4 可观测性与服务故障

Worker 每次完成调度扫描后在现有 Redis 写入部署范围内的心跳，TTL 为 180 秒，内容仅包括成功时间与构建版本。大会配置 API 返回最近成功扫描时间、队列可达状态、下一次计划和最近投递；超过 TTL 或不可读取时显示“发送服务待恢复”，阻止新开启，已有订阅保持配置。

心跳证明调度循环近期运行，试发经过 Worker 进一步检验真实发送路径。正常单大会场景目标为计划时间后两分钟内完成；集中到期和外部服务故障以实际排队状态为准。

应用与群维度节流共享现有 Redis：本系统按同一应用每秒最多 10 次消息请求、同一群每秒最多 1 次请求。外部其他机器人仍可能占用飞书群的共享频率，继续按限流处理。数据库聚合设置 30 秒超时，工作量限制为现有调度批次每轮最多 100 个订阅；积压数量和最久等待时间进入日志及诊断。

无效应用凭据暂停组织连接；群解散、退群或群禁言暂停受影响订阅。暂时网络故障不触发全组织停用。按官方错误语义区分，例如 `230002` 为机器人不在群、`230018/230035` 涉及发言限制、`230020` 为限流，不把 `230013` 统一解释为退群。

## 8. 数据模型、接口与权限

### 8.1 数据增量

复用现有四类表，不新增业务主表。所有增量均为兼容性扩展：

| 位置               | 新增或调整                                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 组织集成 JSON 配置 | `connectionVersion`；保留现有加密凭据、状态和校验时间                                                                                                                                 |
| 大会订阅           | `config_version`、`test_verified_connection_version`、`pause_reason`；现有群、时间和验证时间继续使用                                                                                  |
| 投递账本           | `card_payload`、`connection_version`、`subscription_config_version`、`lease_token`、`lease_until`、`first_send_started_at`；`resolution` JSON 记录人工结论、操作者、时间和关联补发 ID |
| 指标快照           | V1/V2 可判别契约；V2 增加退款申请与待办、发票需求与提交、指标级质量标记；质量受影响的数值可为 null                                                                                    |
| 现有人工退款写入   | 按系统确认时刻填充已有 `succeededAt`，不改变退款业务资格或执行规则                                                                                                                    |

V2 日指标固定新增 `refundRequests`、`invoiceDemands`、`invoiceSubmissions`；当前待办新增 `refundPendingReview`、`refundWaitingFunds`、`refundAttention`，监控新增 `refundProcessing`。保留原有其余指标字段；原 V1 的 `invoiceRequests` 仅用于 V1 展示。`qualityIssues` 每项包含错误类别、受影响指标路径和说明，不向前端返回退款流水明细。质量检查不得将 null 自动转换为 0。

历史行的新增字段默认为 null 或初始版本。上线时保留旧投递和旧订阅，迁移后要求首次真实试发写入当前版本的验证，再开启新链路。不会因为新增字段默认值而把旧订阅视为已经验证。

### 8.2 接口

前缀统一为 `/api/v1/admin`。契约在 `packages/contracts` 中定义并供前后端共用。

| 接口                                                                    | 最终行为                                                                                                  |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `GET /integrations/feishu-bot`                                          | 脱敏配置、连接版本、分项诊断；管理者可读取受影响大会摘要                                                  |
| `PATCH /integrations/feishu-bot`                                        | 升级为候选凭据先验证、再按 `expectedConnectionVersion` 保存；停用无需访问飞书；首次连接后发送验证仍待完成 |
| `POST /integrations/feishu-bot/verify`                                  | 检查已保存配置，返回分项结果；明确凭据失效才变更连接状态，暂时失败保留当前配置                            |
| `GET /integrations/feishu-bot/chats`                                    | 完整查询成功返回群列表，失败不返回可用于退群判断的部分成功结果                                            |
| `POST /integrations/feishu-bot/chats/refresh`                           | 完整成功后协调失效绑定，检查连接版本；普通读取不暂停订阅                                                  |
| `GET/PATCH /events/:eventId/feishu-digest`                              | 读取运行状态或按 `expectedConfigVersion` 保存设置；启用要求有效试发、连接版本和服务就绪                   |
| `GET /events/:eventId/feishu-digest/preview`                            | 当前只读快照与预览，不发送消息                                                                            |
| `POST /events/:eventId/feishu-digest/send-test`                         | 持久化投递与 Outbox，返回 202、投递 ID 和 `queued` 状态；只接受已保存且版本匹配的目标群                   |
| `GET /events/:eventId/feishu-digest/deliveries`                         | 最近 100 条，返回原状态、人工处理状态及可执行操作                                                         |
| `GET /events/:eventId/feishu-digest/deliveries/:deliveryId`             | 历史详情与任务状态，供试发轮询和刷新恢复                                                                  |
| `POST /events/:eventId/feishu-digest/deliveries/:deliveryId/resend`     | 原快照补发，经权限、版本、目标群和并发限制检查后返回 202                                                  |
| `POST /events/:eventId/feishu-digest/deliveries/:deliveryId/regenerate` | 仅对无快照的生成失败记录，在规定窗口内重新入队                                                            |
| `POST /events/:eventId/feishu-digest/deliveries/:deliveryId/resolve`    | 仅记录人工确认收到的结论，不发送消息                                                                      |

所有手动发送和恢复请求保留 Idempotency-Key；同键异参返回冲突。同键重试返回原投递。`expectedConnectionVersion/expectedConfigVersion` 防止旧页面更新覆盖新设置，值为首次创建版本时也通过唯一约束处理并发创建。

试发状态轮询每 2 秒一次，30 秒后降为每 5 秒；两分钟后停止自动轮询并提供刷新，后台任务继续。只有请求被明确接受时显示排队，浏览器请求超时通过同幂等键确认原任务，禁止立即生成新键重发。

### 8.3 权限与 Agent 目录

- 组织连接读取使用 `org.settings.read`，凭据操作、校验及群列表使用 `org.settings.manage`。
- 大会页的预览、历史和运行信息要求 `org.settings.read` 与 `event.dashboard.read`；相关写操作要求 `org.settings.manage` 与 `event.dashboard.read`。
- 使用现有组织成员权限模型，所有查询约束当前组织与大会 ID。本次不引入新的逐大会成员授权模型或新权限码。
- 导航入口、路由守卫、API 和派生的可执行操作同时遵守权限，不依赖只隐藏按钮。
- 现有 Agent 只读操作目录同步声明新的组合权限和返回结构，更新契约快照；首版不将凭据替换、群发及人工补发自动开放给 Agent。

### 8.4 凭据、数据与模板隔离

凭据继续使用 `INTEGRATION_ENCRYPTION_KEY` 和现有密钥版本机制加密。API 与 Worker 必须使用一致配置，Secret、access token、Authorization 和供应商原始响应体不进入日志；错误对外使用分类信息，诊断仅保留脱敏错误码和追踪 ID。

服务端获取并缓存 `tenant_access_token`，以供应商返回的有效期为准。缓存按组织、应用和连接版本隔离；候选凭据验证使用独立缓存，保存失败不替换现有缓存，替换成功后新任务只取新版本令牌。旧请求返回的令牌或诊断不能覆盖当前连接。依据：[应用凭证](https://open.feishu.cn/document/server-docs/authentication-management/access-token/tenant_access_token_internal)。

出站域名固定中国版飞书 `open.feishu.cn`，拒绝任意 API 主机和携带令牌的回调 URL。后台按现有管理员认证与请求保护执行，不接收前端自行拼装的待发卡片或统计数值。

群消息不包含个人信息、退款原因、税号、票码或访问令牌。群成员或管理员变更后，TokEMS 无法保证历史聚合消息不被转发，首次试发的可见范围确认用于明确接收范围。

组织集成、群绑定、投递、观察标记等运行数据排除在规范快照与大会复制模板外。新大会默认无群且关闭自动发送。第一方访问采集与前台第三方统计隔离规则保持不变。

首版保留聚合快照和账本，不新增自动清理流程。历史 UI 只显示最近 100 条，超过范围由现有运维查询处理，未来单独定义保留策略。

## 9. 实施交接与验收

### 9.1 实施范围

预计涉及超过 8 个文件，约 25 至 35 个源码、测试和迁移文件。完整首版作为一个可发布单元，包含以下交付：

### 9.3 发布与回退

## 10. 外部依赖与确认边界

需要企业管理员准备 App ID、App Secret、应用机器人能力、两项权限和发布审核，并将机器人添加到授权测试群与正式运营群。所需官方 API、文档和本机 CLI 命令已核对可用入口；实际企业凭据、企业政策、群权限和生产环境配置仍以实施联调为准。

企业禁止安装自建应用时，本版接入前提不成立，届时单独确认 Webhook 适配范围；统计、配置与投递主体可以复用。国际版 Lark、外部群、群内直接审批、即时提醒、原生任务同步和多群日报均不在本次实施范围。

用户确认本文件后，开始本地实现与验证。提交、推送、合并、生产发布和正式群启用继续按各自授权及仓库流程执行。
