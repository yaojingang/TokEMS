# 多名额购票实施与验收记录

用户已确认按最终方案 v2.0 实施。本地开发和本轮验收已完成。基线为本地 main 的 `34ddc59055beaa7b04d83e1e35fbb62dedb71a98`，代码保留在工作区，未提交、推送或部署。现有并行任务的修改均保留。

## 已交付功能

- 后台原增购开关同时控制一次多名额、代购及后续增购；累计有效名额默认 5，支持配置 1 至 20。
- 前台支持数量输入、加减和快捷选择，按人数生成稳定的参会资料卡，实时计算总价；可包含本人，也可全部代购。
- 每份资料按当前发布表单校验；保存草稿，减员时确认并支持撤销；条款和代购授权明确勾选，切换账户及迟到请求隔离。
- 一次创建一张固定订单、N 个名额明细与预留、一次整单支付、N 张独立票。报价变化重新确认；过期或关闭订单重新创建购买意图。
- 整单审核、批量付款确认、免费名额分别取消、未认领资料编辑及手机号认领；认领邀请按名额隔离、轮换失效，短期重放密文到期清理。
- 购票人通过新订单详情查看全部名额与财务；参会人只取得自己的票和参会服务。支付访问凭证不返回名单或票码。
- 用户选择名额申请退款；管理员逐名额指定金额及保留或取消参会权益。退款资金、名额分配和权益关闭分别核对，其他有效名额继续使用。
- 后台订单明细、审核、补偿退款与资料修改已适配；报名列表和 CSV 按名额分配金额，订单统计与发票按原支付聚合，保留历史财务记录。
- Worker 支持整单到期释放、审核结果和到期通知、认领及票券通知。支付待确认、成功资金待补票和核验冻结均保留库存。
- 0065 迁移完成明细结构、历史补写和约束；部署预检兼容旧结构、新结构，并拒绝半套迁移、缺票、状态不一致或退款履约异常。
- 新版条款范本 `2026-09-10-batch-v2` 已加入代码及后台“载入多人购票条款范本”入口。旧报名继续保留原版本与同意记录。

## 审查闭环

数据结构、核心支付与权限、退款、Worker/部署、前台规格及前台质量均完成独立审查。审查发现的并发权限、支付库存保护、退款资金归属、多个订单锁序、发布快照一致性、字段错误定位、跨账号迟到响应与 CSRF 恢复问题已修复，并通过对应反向回归。

后台报名列表单人金额、退款只影响目标名额及真实 CSV 五人合计金额通过额外数据库回归。后台浏览器另外验证了整单五人审核和两个名额不同权益处理方式的退款。

## 发布与恢复安排

本轮完成代码及隔离验收。共享 `127.0.0.1:8088` 和生产服务保持当前运行版本。仓库的 Docker 发布构建要求干净工作区；当前还包含本任务及其他任务的未提交内容，本轮未运行共享预览替换。

正式开放依次执行：

1. 形成审核后的提交与阶段 A 发布基线，按项目规则完成 PR、CI 和镜像证明。阶段 A 设置可选的 `BATCH_PURCHASE_CREATION_ENABLED=false`，仅允许新建单名额，继续处理所有已存在的多人订单；这一能力已在真实数据库中验证。
2. 在目标大会载入并发布 `2026-09-10-batch-v2` 条款，产生新表单和发布版本。其他大会如有自定义条款，应使用其已确认的内容。此步骤不改写历史报名的条款快照。
3. 本地规范大会的条款和关联设置实际发布后，运行 `pnpm canonical:export` 并保存两份规范快照；推送前运行 `pnpm canonical:check`。当前快照文件校验通过，目标大会的新条款尚未发布，因此本轮没有宣称快照已切换到新条款。
4. 获得相应发布授权后，按生产 Runbook 完成备份、支付结清、预构建镜像部署和验收；再开放阶段 B 的多人新建。默认代码支持多人，仍受原大会增购开关约束。
5. 在授权范围完成真实微信支付、重复通知、所选名额退款和发票调整验收。回退使用具备全部多人履约能力的阶段 A；已产生新版订单后，不回退到 0065 之前的应用。
