# 登录与合作伙伴中心体验升级方案 v1.0

日期：2026-09-17。状态：用户已确认，功能已实施，正在完成本地验收。代码核对基线：54e6201209955e1ff9918443cde649e6f2e4486f。

## 1. 目标与范围

本轮统一完成登录授权体验、合作伙伴首页结构、海报文案管理三项升级。继续使用现有 Nuxt 前台、NestJS API、PostgreSQL、共享 contracts 和会员海报渲染器；不新增部署服务、第三方账号、密钥或运行环境。

保留佣金规则、推广归因、金额计算、提现审批和支付渠道的现有行为。现有会员报名海报外观保持一致。本轮不新增统计图表、日期筛选、营销短信或文案生成服务。

最小方案是只调整菜单和区块位置；它能满足信息布局，但无法完成历史授权识别与文案跨设备保存。因此推荐按下述三个可独立验收的步骤交付。

## 2. Review 发现与处理决定

| 现状或风险 | 本轮决定 |
|---|---|
| 登录弹窗每次要求勾选，contracts 将 consentAccepted 固定为 true，前端请求也固定传 true | 前后端共同调整，服务器验证真实授权记录，不能只修改前端勾选状态 |
| 本地 geo-conference 的用户协议、隐私政策版本为空；后端仅在版本非空时记录同意 | 空版本不计为有效同意；正式启用免重复确认前补齐组织协议链接及版本，历史用户下次登录主动补确认 |
| 验证码当前一次性消费 | 身份验证和协议确认分为明确状态，采用短期、一次性的待确认凭证，避免同意后要求重新收短信 |
| 页面默认打开资料页，四项余额位于所有子页面的公共区域 | 默认展示推广收益，余额只在推广收益中渲染 |
| 推广效果与佣金明细分散 | 合并到推广收益，保持原统计口径与数据来源 |
| 海报与会员共用 Canvas 渲染器 | 扩展伙伴专用可选文案，会员分支继续使用原默认内容 |
| 头像与文字受 visibleFields、posterFields 双重控制 | 自定义文案不能绕过原资料授权；头像继续由资料设置管理 |
| 保存资料会生成新版本，新增文案可能被后续编辑覆盖 | 将文案纳入资料版本快照，所有用户端、管理端更新路径保留未修改字段，并采用版本冲突检查 |
| 编辑文案后跳转修改头像可能丢失输入 | 同一会话暂存草稿，保存头像后返回推广素材；离开模块时明确提示未保存状态 |

## 3. 登录注册体验

### 3.1 用户流程

输入手机号 → 获取验证码 → 验证身份 → 服务端检查当前组织的有效协议版本及同意记录。

- 已有完整、有效同意记录：直接建立登录会话，回到原业务页面。
- 新用户、历史记录缺失、需要接受新版本的用户：在当前居中弹窗内进入“确认协议”步骤，默认不勾选，展示协议入口，点击“同意并继续”完成注册或登录。
- 勾选属于本次身份与协议版本。验证码输错、重发时保留本次有效选择；更换手机号、组织或协议版本时清空。
- 手机号验证码验证成功之前，不返回账号是否存在、注册时间或授权状态。
- 获取验证码处保留手机号用途和隐私说明入口；完整账户授权在验证身份后完成。
- 新用户在完成授权前不建立可用账户会话；管理员已创建的伙伴账号保持原身份，完成登录后关联原伙伴关系，不重复创建。
- 登录授权与报名条款、代报名授权、合作伙伴规则确认分别管理，不能互相替代。

### 3.2 后端与接口

复用 `/api/v1/customer-auth/otp`、`/verify` 和 `customer_consents`。`/verify` 增加显式状态结果：已登录或待确认协议；已登录结果保留现有会话字段。增加 `/api/v1/customer-auth/consent` 完成待确认流程。旧请求只有明确传入同意且版本匹配时，才允许原子完成授权和登录。

待确认凭证使用随机不可预测值，数据库只存哈希；绑定组织、手机号、原验证码挑战和协议版本，5 分钟有效。采用独立 HttpOnly、SameSite Cookie 传递，生产 Secure；提交执行同源/CSRF 校验。它只能完成授权，不能访问账户、订单、伙伴或提现 API，不进入 URL、统计或日志。验证码成功消费与凭证生成原子完成；最终同意、账号创建或关联、凭证消费、会话创建同样原子完成。

过期提示重新验证；拒绝或关闭不记录同意。并发提交只允许一次消费；提交期间协议版本变化，展示新版本并要求再次确认。账号禁用、组织隔离、短信限流与错误次数限制继续生效。前端取消固定写入 `consentAccepted: true` 的逻辑。

沿用现有组织协议版本字段：需要用户重新接受的内容更新必须发布新版本，普通排版调整保持版本。校验版本对应的公开协议内容及链接，不能用客户端任意版本替代服务器当前版本。

**配置门槛：**版本和协议链接不完整时，本地演示保持现有逐次确认流程，并明确提示配置缺失；该状态不产生有效版本授权，也不启用免重复确认。正式环境验收要求真实协议链接和版本齐全。协议正文及是否需要重新征得同意由运营审核发布，不能自动编造正文或补写历史同意。

### 3.3 弹窗体验

手机号、验证码、协议确认三步使用同一居中弹窗。错误在当前步骤内突出显示，保留有效输入；键盘焦点定位到错误或待操作项。阅读协议使用新标签页，返回后保留步骤。移动端允许弹窗内部滚动，操作按钮始终可达。

## 4. 合作伙伴中心结构

菜单固定顺序：

1. 推广收益（默认首页，沿用内部 earnings 标识）
2. 推广素材
3. 资料设置（原资料与公开设置）
4. 提现与结算
5. 佣金申诉

直接进入 `/account/partnerships/:eventId` 展示推广收益。使用 `tab` 查询参数保留指定页签，刷新、返回与前进维持当前页签；无效参数回到推广收益。修改头像使用 `tab=profile&focus=avatar` 并记录返回推广素材的上下文。

推广收益排列：

- 顶部四项收益：可提现收益、待结算、提现处理中、已结算，保留现有金额及解释。
- 中部推广效果：推广访问次数、每日去重访问人次、有效推广订单、有效推广成交额，保留累计范围和统计口径说明。
- 下部佣金明细：沿用现有订单和佣金数据、状态、冲正信息及明细呈现。

仅推广收益显示四项汇总，其他子页去除重复条带。提现与结算保留申请表所需的可用金额提示、金额校验和结算记录，不再复制四卡概览。待确认规则、暂停、关闭、追偿等与操作有关的提示继续在适用页面显示。

统计范围仍为当前用户、当前组织、当前大会。每日去重人次的跨日累计含义保留，成交额与佣金收入清晰分开，不更改退款、自购、部分冲正计算。接口失败展示错误和重试入口，不伪装为零收益；无数据展示真实零值和说明。

## 5. 推广素材与海报文案

### 5.1 页面布局与可编辑内容

桌面左侧依次为专属推广链接、海报文案设置、保存与下载操作；右侧为海报预览。移动端纵向排列，继续使用个人中心既有 UI 规范和会员海报的 1080×1440 版式。

首期提供两个伙伴专用纯文本字段：

| 字段 | 建议上限 | 行为 |
|---|---:|---|
| 邀请语 | 32 个 Unicode 字符 | 独立显示于身份信息下方；未自定义时沿用默认邀请语 |
| 合作介绍 | 80 个 Unicode 字符 | 自定义时替换海报介绍区；未自定义时使用已获海报授权的资料介绍，再回退到通用默认文案 |

公司、职务仍占独立身份信息区域，避免邀请语被公司职务覆盖。姓名、公司、职务和头像统一在资料设置维护，文案区提供明确入口。大会名称、时间地点、伙伴身份标记、二维码、推广目标、二维码说明及模板版式由系统生成。

纯文本校验在前后端一致执行，展示字符计数；拒绝 HTML 和控制字符。长英文、中文、数字、换行、emoji 需要实测排版，宽度超限提示调整；不静默截掉用户保存的关键文案，不遮挡二维码。

### 5.2 草稿、保存、授权与下载

编辑实时预览，并标记“未保存”。保存成功后刷新预览与服务端版本；下载前要求保存当前修改，避免预览与下载不一致。生成期间禁用下载，生成失败可重试。

“恢复默认文案”恢复当前编辑草稿，点击保存后持久化。刷新页面、重新登录、跨设备登录均读取已保存文案。新文案仅作用于当前大会海报，不回写个人简介或会员海报。

自定义文案属于用户主动准备分享的内容，保存处明确告知将出现在下载海报。资料自动带入继续遵守原字段公开与海报授权；自定义合作介绍也受介绍的海报授权控制，关闭授权时隐藏并提示用户前往资料设置。不能借用文案配置自动公开联系方式或头像。

海报点击“修改头像”跳转资料设置并聚焦头像区域。同一组件会话中保留未保存文案；头像保存成功后返回推广素材，重新生成海报。资料中关闭头像海报授权时使用现有占位形象，不自行开启授权。取消头像修改可返回原草稿。离开整个模块或刷新前提示未保存修改，不将草稿自动提交。

### 5.3 数据设计

在现有伙伴资料版本快照增加可选 `posterCopy` 对象，含邀请语与合作介绍，旧记录默认空值。复用现有资料保存权限与版本管理；增加独立文案 PATCH 接口，按当前伙伴身份、组织、大会校验并以版本号防止覆盖。资料、隐私及后台编辑新版本必须继承未修改的文案字段。

账户接口返回完整本人配置；公开接口只返回已发布、已授权的必要海报字段，草稿不可泄露。保持个人资料审计、发布状态与当前草稿管理规则；保存文案不自动公开个人详情。普通会员渲染分支不接收伙伴文案覆盖。伙伴详情页若展示相同个人海报，应使用同一已发布版本与渲染逻辑。

## 6. 改动范围与顺序

预计涉及超过 8 个源文件及配套测试，属于跨前后端迭代。主要文件包括 CustomerAuthDialog、useCustomerSession、customer.module、customer-auth.service、账户伙伴页面、partner-poster、personal-event-poster、partner-distribution.service、contracts、数据库 schema 和新增迁移。

数据流：

用户弹窗 → 认证 API → 验证挑战 / 同意记录 → 登录会话
合作伙伴中心 → 伙伴 API → 资料版本 / 既有财务查询 → 推广收益与海报渲染

实施顺序：

1. 合作伙伴首页结构调整。独立交付默认首页、菜单、余额与推广效果整合，验证深链接和移动端。
2. 推广文案与头像跳转。追加向后兼容字段，完成文案持久化、隐私控制、预览下载一致性和会员海报回归。
3. 登录协议确认。追加待确认凭证存储、更新共享接口与全部登录调用方，完成历史授权判断和配置门槛。前后端作为一个完整交付单元切换。

新增数据库迁移采用追加表/字段方式，不删除现有授权、账户、伙伴和财务记录。待确认凭证定期清理沿用现有认证清理机制。迁移编号在实施时按照主分支顺序分配，避免与其他迭代冲突。

## 7. 验收与回归

- 登录：新注册、老用户、管理员预建用户、历史记录缺失、版本变化、版本为空、验证码错误与过期、重发、换号、取消、待确认凭证重放与过期、并发提交、账号禁用、跨组织访问。
- 入口：个人中心、报名、合作伙伴中心全部共用认证流程；成功后回到原业务位置，报名条款及伙伴规则不被跳过。
- 页面：无参数默认推广收益，指定页签、浏览器刷新返回正确；四项汇总只出现于推广收益；错误与空数据可区分；财务值与旧接口一致。
- 海报：默认及自定义文案、字数边界、长英文、emoji、空头像、图片加载失败、授权关闭、恢复默认、并发版本冲突、切换头像后的草稿恢复；扫描二维码目标仍为本人推广链接。
- 预览与导出内容一致；伙伴详情海报遵守发布版本；会员报名海报无回归。
- 桌面与移动端在隔离浏览器验证，不改变用户现有浏览器窗口尺寸。
- 运行 pnpm check、pnpm test:partner-account、pnpm test:partner-dialogs、pnpm test:registration-experience，以及新增认证/海报/权限集成测试；按登录链路影响补跑 pnpm test:batch-registration 与 pnpm test:payment-resume。
- 账户、登录、提现、申诉仍禁止第三方统计，公开区到敏感区保持新文档导航。

## 8. 本地交付、发布与回退

用户确认后依次实施、验证，再更新主目录 tokems 的共享 8088 预览。保留现有数据、素材、工作树和未跟踪文件。GitHub 提交推送与生产发布按相应授权执行。

若更改组织公开协议配置，推送前按仓库规则导出并核对规范快照。用户协议同意记录、伙伴文案及其他个人数据不进入规范模板；pnpm canonical:check 必须通过。

新增字段允许旧版读取。认证上线先部署兼容 API，再切换前台；回退先切回原登录 UI，再回退 API，尚未完成的短期确认凭证自然失效并要求重新验证。海报配置数据保留，回退前端后展示原默认海报；回退期避免旧版资料写入覆盖新文案。无需回退或清空数据库。

最终交付：三个模块的功能变更、测试结果、桌面/移动端截图、本地体验地址及本方案验收清单。协议实际正文与版本属于正式启用前的运营配置门槛。
