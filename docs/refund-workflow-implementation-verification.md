## 已实现的使用流程

1. 购买人在个人中心的订单和报名详情中进入退款页，查看原支付方式、关联参会人、金额、规则和到账说明。符合七天规则时提交全额剩余金额的退款申请，原因选填。
2. 待审核申请可以撤回。管理员在报名管理和报名详情的退款面板中批准或驳回；驳回需要原因。重复点击、并发审核和撤回使用版本及幂等约束。
3. 批准后自动提交微信原路退款。资金不足按五分钟间隔调度；请求结果未知时先查单，保留相同退款单号和请求内容。微信受理后持续查单，并接收验签解密后的退款通知。
4. 仅在渠道确认用户收款后结清退款。全额退款批准时暂停票券，成功后注销票券、取消报名、释放名额；部分退款保留参会资格并调整开票净额。
5. 用户可查看进度。后台提供等待资金、处理中、异常、已完成等筛选，以及外部退款核验、自动执行暂停和恢复。通知失败与资金状态分开记录。

24 小时仍是审核和异常升级的运营目标。资金不足时持续重试；到账时间按微信及银行结果展示，银行卡通常为 1 至 3 个工作日。系统不会因超时自行写入退款成功。

## 数据和运行方式

- 新增迁移 `0060_customer_refund_workflow`、`0061_refund_scope_constraints`、`0062_refund_cash_breakdown`，建立申请、执行、通知收件箱、商户调度记录、跨表归属约束及可空现金／优惠明细。历史未知金额不填零。
- 历史退款保留来源；新增退款状态必须显式指定。原商户号、原支付引用、金额、出资策略和退款单号在执行单中固定。
- 复用 API 的后台调度和现有通知 Worker，无新增部署服务。
- 大会退款默认关闭。开启需具备相应权限，并通过服务端退款配置就绪检查。停用新收款不阻断既有退款查单和完成处理。
- 未结申请、无申请的外部退款执行、待处理或隔离通知存在时，阻止更换原商户或 APIv3 解密密钥；微信验签公钥轮换保留受信历史公钥。
- 新入口位于账户、订单及后台敏感区域，沿用网站统计隔离边界。

## 审查后补强

- 外部退款发现时，冻结订单与插入待核验执行占位在同一事务完成，防止核验间隙恢复自动退款。
- 资金成功与票务、发票补偿分开保存。补偿失败不丢失资金事实，期间继续阻止权益变更及开票，定时重放修复。
- 发票文件替换按实时退款净额检查，不能借恢复旧文件绕过退款后的发票调整。
- 完成后的申请不会被旧退款关闭通知倒退。关闭后续单保持显式确认和幂等记录。
- 暂停的订单先从提交候选中排除，防止占满队列；已发出超时告警的申请不会阻塞后续告警。
- 购买人授权先于退款状态判断，避免向非购买人暴露财务状态。短信配置兼容旧客户端，并保留未提交的新场景配置。
- 缺失通知签名在查询商户配置前返回未授权；退款配置问题以明确业务错误返回。
