## 1. 建议确认的方向

将「允许购票人继续增加名额」升级为「允许一次购买多个名额及后续增购」。开启后，首次购买和后续增购共用一个流程：**选择票种 → 选择本次数量 → 逐位填写参会人 → 确认总额 → 一次付款 → 每人独立出票**。

推荐采用 **一个购票订单 + 多个参会名额 + 一次总额支付**。购票人统一管理订单、支付和发票；每位参会人拥有独立报名记录、认领入口、电子票和核销状态。

以本地当前大会通票 ¥399 为例：首次选 5 个名额，填写 5 位参会人的资料，支付 ¥1,995。购票人可以包含自己，也可以全部为他人购买。已买 1 个名额且累计上限为 5 时，本次最多增加 4 个，新增订单金额为 ¥1,596。

### 推荐产品决定

| 项目     | 本次推荐口径                                                               |
| -------- | -------------------------------------------------------------------------- |
| 开关     | 沿用现有开关，同时控制首次多人购买、为他人购票和后续增购                   |
| 数量     | 默认 1；提供减号、数字输入、加号，以及可用范围内的快捷数量                 |
| 票种     | 首版一单一种票，同一订单内每个名额单价相同                                 |
| 名额上限 | 沿用每位购票人在本大会的累计有效名额上限；默认 5，后台现有配置范围 1 至 20 |
| 参会资料 | 付款前填写完整；本人可带入资料，其他参会人逐位填写                         |
| 付款     | 一个订单号，一次按总额付款；重试复用原订单和支付协调机制                   |
| 后续增购 | 已付款订单保留原明细，新增名额创建新的批量订单                             |
| 退款     | 购票人选择需要退的参会名额，可选一位、多位或全部；审核后原路退款           |
| 发票     | 按订单申请，展示人数、票种和净可开票金额                                   |
| 人工审核 | 多人订单整体审核；整单通过后统一支付，整单驳回后允许带回资料重新提交       |

本次覆盖付费与免费票、本人和纯代购、自动确认与人工审核。混合票种、团购折扣、Excel 导入、先买空白名额再补资料、跨大会合并付款和不同发票抬头拆票申请，留在本次范围之外。候补邀请继续限定本人一个名额。

## 3. 后台报名设置

开关文案建议改为：

> **允许一次购买多个名额及后续增购**  
> 开启后，购票人可在首次报名或后续增购时选择多个名额，填写各位参会人信息后统一付款。

上限字段改为「每位购票人累计最多有效名额」。说明：

> 包含该账号购买的本人和代购名额。待审核、有效待支付、支付确认中和已生效名额均占用额度；完成取消或退票并关闭权益的名额释放额度。

后台同时显示「按当前设置，首次最多可购买 5 个名额」的解释，以及设置保存后的生效说明。

- 开关关闭：新申请保留本人单名额报名；已创建订单的支付、认领、退款和票证继续按订单状态处理。
- 已报名用户没有剩余额度：前台展示已占用数量与上限，隐藏可执行的增购动作。
- 降低上限：保留已创建的合法名额，后续新购按新上限计算；已有数量超过上限时显示超出原因。
- 关闭报名或改变开关：阻止不符合新规则的新建订单；旧订单按原有效期履约，不静默取消。
- 上限为 1 且开关开启：允许替一位他人购票，页面明确显示当前可购买 1 个名额。
- 上限按当前登录购票账号在本大会购买的名额计算。其他购票人为本人购买的票仍受本人唯一参会身份约束，但不占本账号的购票额度；页面分别展示本人参会资格与本账号已购名额。
- 本次升级沿用后台现有开关值，不在迁移或种子同步中自动切换大会设置。

## 4. 报名页交互

### 4.1 选择数量与展示金额

数量选择紧接票种卡片。默认选中 1，支持直接输入正整数，快捷项建议为 1、2、3、5，并按当前可购买数量过滤。按钮必须有可读标签，可用键盘操作。

始终明确显示：

- 本次购买数量。
- 本大会已占用名额和剩余额度。
- 票种单价、数量、小计和应付总额。

可新增数量取「购票人剩余额度、票种实际可售库存」的较小值。存在待处理订单时，先展示该订单及恢复操作。库存、名额上限与金额最终由服务端复核。

页面建议结构：

```text
大会通票                         ¥399 / 人
本次购买        [−]   5   [+]     快选 1  2  3  5
已占用 0 / 5 个名额，本次可购买 5 个

购票人：已登录手机号                订单和发票归此账号
☑ 本次包含本人参会

参会人 1 · 本人                    资料已带入，可核对
参会人 2                           姓名 / 手机号 / 公司…
参会人 3                           姓名 / 手机号 / 公司…
参会人 4                           姓名 / 手机号 / 公司…
参会人 5                           姓名 / 手机号 / 公司…

已完成 3 / 5 位
大会通票  ¥399 × 5                合计 ¥1,995
□ 同意报名条款并确认获得代报名授权
[确认 5 位参会人信息并支付 ¥1,995]
```

这是信息结构示意；实施时沿用项目已有字体、配色、票种卡片和表单样式。

### 4.2 本人和其他参会人

- 登录购票人信息只显示一次，不要求重复登录或让全部参会人现场获取验证码。
- 首次普通报名默认「包含本人」；从增购入口进入时默认全部为其他参会人。没有本人名额的购票人可手动选择包含本人。
- 已有有效本人报名时，不再添加第二张本人票；在页内提供现有门票入口。
- 包含本人时，第一张卡片带入本人资料，手机号使用已验证号码；纯代购时全部显示独立参会人卡片。
- N 个名额对应 N 份资料，包含本人时是本人 1 份加其他人 N-1 份。
- 每张卡片使用大会已发布的报名字段及必填规则，不重新硬编码一份表单。
- 提供「沿用上一位的公司/机构」操作；不复制姓名和手机号，操作不覆盖已填写的其他字段。
- 完成的卡片可折叠，标题展示姓名、手机号尾号、填写状态；错误卡片自动展开并定位首个错误。
- 增加数量保留原资料；减少数量时优先移除末尾空白卡，涉及已填资料时让用户选择删除对象，保留本次操作的撤销入口。直接删除卡片同步减少数量和金额。

### 4.3 草稿、校验与条款

- 草稿保存数量、票种、本人标记、稳定卡片 ID 和每位参会人的回答；刷新、登录中断后能够恢复。沿用现有最长 30 天保留期，提交成功或用户主动清除后删除该份草稿；存储不可用时仍可在当前页面完成报名，并提示刷新无法恢复。
- 稳定卡片 ID 不使用数组下标。删除、折叠、调整顺序不会让姓名、错误提示、本人标记或条款快照串到另一位。
- 未登录时可选票种和数量，精确购票额度在登录后获取；登录恢复后重新校验人数，不能把登录前显示的库存当成已经锁定。
- 切换票种保留可兼容字段，变化的必填项重新标记；切换到售罄票种不自动把整份多人资料改成候补申请。
- 复用现有草稿隔离与过期机制，按组织、大会、购票账号和购买意图区分；旧单人草稿升级为一个参会人条目。
- 退出或切换账号时清空当前界面；不得把前一购票人的多人资料展示给下一账号。
- 本次填写的手机号先规范化，再检查重复；与现有有效报名冲突时提示冲突卡片，不暴露其他购票人的身份或订单。
- 曾取消的报名按第 7.2 节的身份归并规则处理；新购使用新的报名记录并保留旧历史，不复用旧订单金额与支付流水。
- 任一必填项无效时整批不提交，保留所有已填资料；服务端错误返回卡片 ID 与字段路径。
- 条款和代报名授权一次确认，写入各参会名额的提交快照；营销订阅和公开名片授权继续各自独立，代购不替他人开启公开展示。
- 手机端采用单列卡片和底部金额/提交区，提交区避开软键盘与安全区，不遮挡最后一项内容。
- 将当前条款中关于单名额、代报名、整体审核、选择名额退款和免费票取消的表述一并更新；发布新的条款版本，不改写历史订单的同意记录。条款始终主动勾选，恢复草稿或条款更新后重新确认。

## 5. 订单、支付、出票与增购

### 5.1 一个订单的金额和身份固定

一批人数形成一个订单号、一份价格快照和一个总额。新模型的订单数量、票种、单位价格、参会名额 ID 与购买意图在提交后固定，参会人可修改字段按第 5.4 节管理。正常流程为：

```text
报名页 → 报价与人数校验 → 事务创建：订单 + N 个明细 + N 份报名 + N 个预留
                                ↓
                人工审核（若开启）→ 原订单统一支付
                                ↓
              微信可信通知或查单 → 入账与 N 个名额出票
                                ↓
                购票人汇总通知 + 逐位参会人邀请
```

报价仅供确认，报价接口不创建报名、不占库存。响应携带根据实际发布价格、币种、表单/条款版本、退款规则和审核方式生成的报价指纹；指纹不包含实时库存，其他嘉宾文案更新不使票价确认失效。提交时在事务中重读价格、规则、库存和购买额度，重新计算指纹；上述确认内容变化返回 `409` 和更新内容，保留输入并要求重新确认。数量必须与参会人数组长度相同，服务端从发布票价按整数分计算总额，检查整数溢出及现有渠道允许范围。

继续支付复用原订单。按顺序区分下列场景：

| 场景                         | 处理                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| 请求超时或重复提交           | 使用原购买意图和请求摘要查询/返回原订单；不同内容使用同一意图返回冲突                        |
| 有效待支付单，人员和数量不变 | 原单续付，沿用已有通道协调与支付有效期                                                       |
| 想更换数量、票种或删人       | 购票人明确确认取消原单；完成渠道查单和关单后整单关闭，表单带回原资料，使用新购买意图重新提交 |
| 取消时另一端已支付           | 返回已经支付的原订单和全部名额，停止关闭与重建                                               |
| 取消结果不明、交易处于处理中 | 显示原单确认中，继续查单；不生成另一笔可支付订单                                             |
| 原单已关闭或已经退款         | 原单保留历史；再次购买创建新订单及必要的新报名记录                                           |
| 订单已支付，继续增加人数     | 在剩余购票额度内另建一份新购订单                                                             |

已有合法订单不因关掉增购、关报名、降低名额上限或票种下架而静默失效，付款继续按订单快照和有效期处理。大会整体取消和风控冻结仍遵循现有管理员流程，不能与普通开关等同。新购则使用当前生效配置。

新系统上线后，旧单人接口也不再把已经关闭的订单原行改价重开；它返回明确的关闭状态及重新购买入口。历史未关闭且有效的支付尝试继续处理，不转换订单身份。

### 5.2 统一支付、库存与异常恢复

继续使用现有普通商户的 Native、JSAPI 和 H5 接口，提交整单总额。多名额为同一商户同一大会的商品数量，不需要申请合单支付或引入第二套商户账号。下单商品明细如发送，只包含票种、数量和金额，不包含姓名、手机号或其他参会资料。[微信官方下单文档](https://pay.wechatpay.cn/doc/v3/merchant/4012791897)

库存按名额建立预留，新订单每个明细对应一份数量为 1 的预留，N 份预留在同一事务中创建、结转或关闭。沿用当前预留表并增加明细引用，可以精确判断某个名额是否已经释放。计算可售库存时同时扣除有效预留和已经发出的候补邀请保留量。

每个名额的释放在同一事务生成按明细和预留去重的库存事件，Worker 按原票种和释放数量唤醒候补。旧退款消费者目前按整单全额退款决定是否通知候补，新模型必须支持部分名额退票、免费取消与整批过期；不能等整单全部退款才释放候补机会。

- 普通支付窗口沿用 15 分钟，从订单提交成功起算。倒计时到期先查单/关单；任何活动或未知支付尝试仍保护原库存与购票额度。
- 支付准备、关单和重试始终绑定原订单，校验商户、订单、币种、整单金额与有效支付流水。成功回调和主动查单进入同一个幂等入口。
- 持久化支付通知后，在一个本地事务中记录可信成功支付、确认所有明细、结转所有预留并插入每位一张票以及 Outbox。任一名额写入失败，整笔事务重试；页面显示“支付确认中”，不重复收款。
- 恢复时按明细逐个核对预期票，不能因订单已付或已有一张票就提前返回成功；补齐时遵守每份报名一张票的唯一约束。
- 额外或异常的成功付款保留资金事实并进入核验，不增加第二批名额、不重复计算售票收入，也不任取一笔流水为退款依据。
- 若外部渠道出现“已确认关单后仍收到成功”的异常结果，记录真实资金，锁定相关订单进入人工结清；旧身份已归并或原库存不再可用时不强行出票，不超卖。
- 免费票总额为 0，整批确认和出票，保留现有免费成交标识；不向微信发起零元交易。

### 5.3 成功页、订单页与数据权限

成功页展示“已成功购买 5 个名额”，按各位参会人显示出票和认领状态。个人中心以一个订单卡片呈现票种、原人数、有效人数、实付、退款和净金额。新增 `/account/orders/[orderId]` 作为登录购票人完整订单详情，支付完成后在确认登录身份的情况下进入该页；原 `/order/[id]` 继续承担支付入口。

| 身份/凭证          | 可看到的内容和操作                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| 登录购票人         | 自己购买的完整名单、填写资料、名额状态、订单金额、退款与发票；按规则管理未认领名额               |
| 登录参会人         | 自己的报名、票券、名片、需求与参会服务；不获得他人的资料或整单财务                               |
| 支付访问凭证持有人 | 订单号、大会、票种、数量、金额、支付状态；不返回完整名单、他人票码、认领令牌或退款/发票管理权    |
| 独立认领凭证持有人 | 登录对应已验证手机号后认领本人名额；不得使用凭证访问订单管理接口                                 |
| 管理员/代理工具    | 沿用组织、大会与动作权限；金额动作明确整单范围，名额动作精确定位；新代理动作先登记权限和审批等级 |

购票人本人参会时，自己的票可直接进入现有票页。纯代购成功后进入购买记录，不自动跳到他人的名片或需求页。跳转支付站点、公开站点、账户与返回来源均沿用整页导航边界，不在 URL 查询参数、分析埋点或浏览器持久化中保存访问与认领密钥。

账号删除后保留订单、明细和资金事实；付款或退款未结清时拒绝删除并说明待处理事项。解除账号关联不会把其他参会人变成订单所有人；相同手机号重新注册也不自动接管旧财务。新订单必须保留购买意图与模型版本，禁止因购票人字段变空启用旧订单的身份回退。

### 5.4 修改资料和重新生成认领邀请

普通自动确认订单允许购票人在未认领、未核销且未被相关退款冻结的名额上修改资料。本人已绑定账号且仍处于待支付状态时，也保留本轮工作区正在完善的报名资料编辑入口，手机号继续锁定为登录身份；这项例外不授予更换本人或他人身份的权限。服务端验证当前字段规则、名额版本和手机号唯一性；联系方式沿用现有每名额 10 分钟一次的修改限制。认领成功后购票人不再换人，参会人可维护允许的本人资料；涉及更换身份由已有管理员权限处理并留审计。

人工审核订单中，待审核资料变更与审核通过必须使用同一订单版本竞争；审核人看到过期版本时刷新重审。审核通过后的名额替换或姓名、手机号、公司等已审字段变更，必须取消未支付原单并重新提交整单审核。已经支付的人工审核订单由管理员处理身份更正和重新审核依据，前台不开放绕过审核的换人操作。

新模型只在名额确认并出票后生成认领邀请，有效期从生成时起算 30 天。旧模型已发出的合法邀请按原范围继续有效。新订单的认领必须同时满足名额有效、手机号相符、未归并且没有其他有效本人名额。

提供“重新生成邀请”和“补发邀请”：

- 面向登录购票人且只作用于指定未认领名额；每次轮换撤销该名额旧令牌，其他人的邀请不受影响。
- 令牌表只保留哈希。首次成功响应返回明文链接，为应对响应丢失，使用现有通知加密能力在幂等记录中短期保存密文结果，最长 10 分钟；只有同一登录购票人、同一幂等请求且令牌仍有效时可重放解密响应。通知 Outbox 沿用现有密文保存方式，不把明文链接写入数据库或日志。
- 10 分钟后幂等重试只返回已执行状态和有效期，不再次轮换；界面可使用新请求重新生成。令牌已认领、撤销或被替换时，即使幂等记录尚未到期，也不能返回过期链接。
- 轮换和补发使用幂等键，冷却时间为每名额 10 分钟；补发使用现有短信/邮件限流。过期后名额仍有效时允许重新生成。
- 修改联系方式时轮换令牌；取消名额、审核驳回、退款关闭权益或身份归并时撤销未消费令牌。
- 修改、补发、认领与退款共用版本和锁定规则；旧通知消费前再次检查令牌、收件人和名额状态。

### 5.5 人工审核、免费取消与候补

多人订单采用整单审核，后台显示全员资料、人数、金额及当前版本。整单通过后统一支付；整单驳回后关闭预留并返回资料重新填写。审批不静默删人、不改变已经确认的总价。批量审核只在人员、版本与库存全部通过时成功。

新模型审核期限为提交后 30 天，预留和订单期限一致。到期时整单关闭、释放尚未转换的预留、撤销邀请并发出一条购票人汇总通知。当前实现只会清理待支付订单，因此“待审核到期关闭”是本次明确新增的生命周期处理。旧模型待审核单保留原行为，后台提供识别与人工清理入口，迁移不自动取消它们。

审批、用户取消和过期清理由同一锁与状态条件协调；超过期限不能继续原单审批。通过时按当前容量扣除其他有效预留和候补保留量后复核全批库存；不足时原单在期限内保持待审核。通过后获得 15 分钟支付窗口，免费单则立即出票。

免费票独立提供“取消名额”，允许购票人选择一个或多个未核销且未处于异常冻结的名额。一次明确确认后取消对应票、释放对应库存与额度并撤销邀请；无退款申请和微信资金指令。已核销免费票由管理员处理。页面在免费票条款中提前说明这一规则。

免费订单部分取消时保留原成交记录，展示原人数、已取消人数与有效人数；全部名额取消后订单进入已关闭状态，原免费成交记录保留，不生成虚构退款流水。

候补邀请继续限定本人一个名额，服务端拒绝多人提交。多人报名遇到库存不足时保留名单，用户可以主动减少人数或返回；系统不把其中几位自动转换为候补。

## 6. 退款、发票、通知与统计

### 6.1 按参会名额退款和记账

购票人先选择参会人，服务端返回每位剩余可退金额、不可退原因和累计总额。已核销、已取消、已全额退票、已被进行中申请占用或不符合订单退款规则的名额不能选。一次可选择一位、多位或全部，沿用每个订单最多一份未结束申请的约束；一个名额的申请不阻止其他名额正常核销。

示例：¥399 × 5 已付，选择 2 位申请退款 ¥798。批准后只暂停这 2 张票，退款成功并完成票务处理后只取消这 2 个名额；另外 3 张票有效，订单显示部分退款，净金额 ¥1,197。

退款依旧按原订单快照中的开放状态、时限与票务条件判断，使用可信支付时间；审批延迟不会改变已经受理的申请资格。申请保存选中明细、报价版本、各名额金额、权益处理和政策；管理员不能静默缩减用户申请金额。单个订单只保留一份活动申请，所以整单锁内同时预留订单总额度与各名额额度。

三层记录各有职责：

1. 退款申请明细记录承诺退哪些名额及金额，稳定保留审批依据。
2. 实际退款分配记录每一笔可信渠道退款的哪部分归属哪个名额，关联原支付、执行单和申请明细；唯一键避免重放重复分配。
3. 名额上的库存释放和权益关闭标记记录本地履约，资金已到而本地处理失败时单独重试，不再次发出资金请求。

用户退票按所选名额全部剩余可退金额申请。管理员补偿性退款可以保留该名额权益；按名额取消时要明确取消对象与已批准金额。各明细的剩余可退额按原成交分配金额扣除已成功分配退款计算，再扣除活动申请预留；同一申请重试不重复预留。

正常情况下，一次选 2 人产生一次 ¥798 的渠道退款。分次外部履行时，财务在核验时明确分配到具体名额；系统不按名单顺序猜测资金归属。一个名额的批准金额全部履行后才关闭该名额；未履行完成的已批准名额继续暂停，另外未参与退款的名额仍可使用。

渠道原单金额始终为原支付总额；本次退款金额为批准的名额金额之和。多次部分退款沿用官方次数和间隔约束，同一次失败或结果不明时复用原退款单号；“受理成功”不等于到账成功。[微信官方退款规则](https://pay.wechatpay.cn/doc/v3/merchant/4012791903)

金额按人民币分保存。票价成交额、微信现金支付额、优惠额和实际现金退款分别展示；¥399 的名额发生渠道优惠时，页面的预计现金退回额以渠道确认结果为准。本次不引入站内团购折扣，订单内各名额的基础成交金额相同，已发生的渠道优惠仍正确核验。

分配与权益边界：

- 单笔退款分配之和不得超过该笔已核验退款；分配与原支付、订单、币种、组织和大会一致。已归属业务的单笔正常退款要求分配总额相等。
- 外部退款存在尚未分配金额时保留实际资金事实与待核验金额，暂缓新的冲突退款和开票，不丢弃通知，不以超额申请检查否认已经发生的退款。
- 资金结果已经成功但某名额的票务同步失败，标记该名额待处理；订单金额事实照常记录，目标名额保持暂停，其余明确不受影响的名额继续有效。
- 已明确定位的退款使用名额范围保护；付款来源不明、超额或无法定位外部退款等异常使用整单财务核验保护。核销限制范围由明确的风险类型返回，不能把任意一个名额的售后都映射成整单不可核销。
- 只在对应名额实际取消时释放一次库存和购票额度。补偿性退款且权益保留时继续占用额度；该名额净金额为 0 时也不能仅凭金额自动取消。
- 当前订单状态 `refunded` 表示钱的状态。新名额的入场、名片与需求资格由已确认付款事实、名额状态和目标票状态共同判断，避免“全额补偿且保留权益”被整单财务状态误禁用。

### 6.2 发票与通知

发票按订单申请，使用一份抬头和净可开票金额，数量来源于订单及名额历史。申请、审批、出具、导出和下载均按订单核对，不依赖某位参会人尚未归并或仍在参会。退款后的净金额和已开文件分别处理；已出具发票进入现有调整流程，原文件金额保持可追溯。存在活动退款预留时暂停新的开票提交与出具，界面说明原因；仍允许查询历史发票。已取消某人的名额不导致整张订单发票消失。

购票人收到订单提交、支付和退款汇总通知；每位参会人接收自己的邀请和参会通知。本人购票避免向同一手机号重复发送意义相同的消息。业务事件按订单或名额确定唯一 ID，投递按事件、收件人和渠道去重。第三方发送结果不明时保留未知状态并查验，不通过换一个投递 ID 立即补发。旧队列事件和新事件均由兼容 Worker 处理，通知迟到时重新检查资料版本与权益，避免向旧手机号发送过期邀请。

| --------------- | ---------------------------------------------------------------------------- |

## 7. 推荐实现与兼容设计

### 7.1 方案取舍

最小可上线选项：仅在自动确认大会开放同票种多人订单，并只允许整单退款；仍需完成真实一次支付、全部出票、权限、库存和发票适配。

推荐本稿的完整闭环，同时支持整单审核和按名额退票。5 人订单发生其中 1 人无法到场时可以直接处理售后，避免运营人工拆解整单资金。

另一条可行路线是保留每人一个订单，增加合并付款批次。该路线复用单人订单较多，但增加付款金额分配、跨子单退款、发票归属和重复通知的长期协调成本。本项目推荐将订单直接扩展为多个名额。

### 7.2 数据结构与历史身份

沿用现有订单、支付、报名、票券、库存预留、申请与执行表。新增三张职责明确的表：

| 结构                      | 关键内容及约束                                                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `order_items`             | 订单、报名、组织/大会、稳定位置、票种/单价快照、成交分配金额、名额状态、版本、取消与库存释放时间；报名 ID 唯一，订单内位置唯一     |
| `refund_request_items`    | 申请、原支付、订单明细、申请/批准金额、权益处理和版本；同申请内名额唯一，范围复合外键一致                                          |
| `refund_item_allocations` | 实际退款执行、原支付、订单明细、对应申请明细（若有）、已核验分配金额、分配依据和时间；同一执行与名额唯一，关联跨订单或跨支付时拒绝 |

新增可空兼容字段与索引，不删除旧字段：

- `orders` 增加模型版本、原始购买数量和可信成交支付引用。历史订单为版本 1，升级后新建订单统一为版本 2，包括人数为 1 的新订单。
- `orders.registrationId` 改为可空。历史模型限定数量 1 且引用非空；新模型限定数量为 1 至 20，数量为 1 时引用非空，数量大于 1 时引用为空。真实关系统一来自 `order_items`，不设置虚构主参会人。
- 每份明细通过复合外键分别关联同组织、同大会的订单和报名。若单人兼容引用非空，必须对应其唯一明细的报名。订单数量等于明细数量、金额等于明细金额之和，在完整创建事务和迁移验证中检查。
- `inventory_reservations` 增加明细引用；新模型按名额预留数量 1，旧行按其原有语义保留。部分退款释放依据名额与原票种，不按当前票价或当前大会模板推断。
- `invoice_requests.registrationId` 改为可空，财务范围外键使用订单 ID、组织和大会，保留订单唯一；非空历史报名引用另以明细关系校验。不能因复合外键含 null 就失去订单范围保护。[PostgreSQL 约束说明](https://www.postgresql.org/docs/current/ddl-constraints.html)
- 新增订单的购买意图始终存在，账号解绑也不清空。可信成交支付引用通过支付 ID 与订单 ID 的组合约束核对。免费订单引用现有免费成交记录；异常多支付保留明细并暂停自动选取依据。
- `refunds` 增加保护范围 `order` 或 `items` 的兼容标记，默认 `order` 以保护历史语义；新申请只在能明确定位目标名额时使用 `items`，由申请明细和退款分配表定位受影响对象。
- 新模型的 `external_hold` 继续保护整单资金、改人和开票；是否暂停全部参会权益由订单新增的 `entitlementsOnHold` 明确表示。支付来源不明或外部退款无法定位时设置整单权益冻结；已定位的名额退款使用对应票的 `refundPausedBy` 和明细保护原因。仅发票同步失败时不冻结其他人的入场权益。旧模型保留原保护语义。
- 新增表和关联的删除规则保护成交与售后事实；账号删除只解绑身份，不能级联删除这些账务数据。

历史补写遵循当前可信状态：每张旧订单建立一个名额明细，保留订单号、当前金额、票码、原时间与归属。原订单曾被复用的更早尝试不伪造不可获得的价格明细，保留原支付尝试、预留历史、状态日志和已有快照，并标记历史模型。异常多成功支付或不明退款分配保留待核验状态，不任意选第一笔。

当前手机号和参会账号唯一索引以 `supersededAt is null` 为条件，取消状态不会自行释放唯一键。重新报名时必须：锁定该手机号和旧名额；确认目标旧名额已关闭权益、无影响该名额的未结清退款和支付；预生成新报名 ID，在事务内先设置旧记录的 `supersededAt` 释放唯一身份，再创建新报名，最后填写旧记录的 `supersededByRegistrationId`。任一步失败全部回滚，避免立即唯一约束或外键阻止归并。另一位参会人的订单仍有效时，也不阻止已经退票的这位重新报名。整单资金异常且无法判定名额安全时继续阻止。

旧记录可见性拆成业务资格与财务历史：被归并的旧报名不再占当前参会身份；旧订单、旧发票与旧退款继续按订单查询，不因 `supersededAt` 被过滤掉。新报名必须重新取得本人或代报名授权；新邀请认领时可归并本账号已安全结束的旧报名，不自动继承他人的认领权限。

### 7.3 API、版本与操作入口

路径相对于现有 `/api/v1`，新增写接口均要求登录身份、组织/大会范围、CSRF、明确参数和幂等键。

| 接口或页面                                                      | 明确行为                                                                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `POST /registrations`                                           | 保留单人请求/响应兼容，使用新版统一创建逻辑；已关闭订单不原行复用                                            |
| `POST /registration-batches/quote`                              | 登录后获取报价、可选数量、阻断原因和报价指纹；只读，无库存保留                                               |
| `POST /registration-batches`                                    | 大会、票种、数量、稳定卡片 ID、参会人数组、本人标记、表单/条款版本、授权、报价指纹与购买意图；整体成功或失败 |
| `GET /customer/events/:eventId/purchase-context`                | 返回订单数、已确认名额、审核/支付预留、剩余额度和唯一待处理订单；旧字段兼容，页面新文案使用名额数            |
| `GET /customer/orders/:orderId`                                 | 登录购票人完整订单、明细与逐人能力；响应不向参会人降级泄露                                                   |
| `POST /customer/orders/:orderId/cancel`                         | 待审核或未支付订单整单取消；版本检查，支付准备/查单/关单协调；未知结果返回原单处理中                         |
| `POST /customer/orders/:orderId/items/cancel-free`              | 仅零元且已确认订单，明确选择未核销名额及版本，完成无资金取消                                                 |
| `PATCH /customer/orders/:orderId/items/:itemId/attendee`        | 修改允许的未认领名额，校验版本、审核要求、身份冲突和退款范围                                                 |
| `POST /customer/orders/:orderId/items/:itemId/claim-invitation` | 显式轮换一个可认领名额的邀请，选择是否通过既有渠道补发，服务端限流                                           |
| `GET /customer/orders/:orderId/refund-context`                  | 返回每位资格、剩余金额、不可退原因和退款上下文版本                                                           |
| `POST /customer/orders/:orderId/refund-requests`                | 明确选中的名额 ID 和上下文版本；多名额必须提供选择，金额由服务端核算                                         |
| `POST /admin/events/:eventId/orders/:orderId/review`            | 多人整单审核，决策和预期订单版本；权限和审计沿用报名审核要求                                                 |
| `/account/orders/[orderId]`                                     | 完整购买详情和逐人售后入口；作为多人购买与管理的统一落点                                                     |
| 原 `/order/[id]` 及支付接口                                     | 返回支付摘要和付款状态，不向仅持支付凭证者返回名单、全部票或认领令牌                                         |

创建响应包含 `order`、`items`、`myRegistrationId`（存在本人时）和整体下一步动作；名额字段包含稳定明细 ID、报名 ID、可展示状态、是否本人以及服务端计算的可用操作。每位的票码只通过具备相应票证权限的接口返回。由服务端决定下一步是审核、支付、确认中或已完成。

引入订单模型版本和响应能力标识，旧单人格式只对单名额返回。所有新版网页、支付站、后台、Worker、通知模板、代理工具及模拟后端一起升级；缓存旧页面遇到多人资源时返回可识别的升级提示，保留输入并刷新，禁止截取第一位。旧金额型退款及旧报名级审核遇到多人单也要显式拒绝或引导正确入口。

变更人数导致内容变化时使用新购买意图。网络超时恢复使用原意图，不因刷新而生成第二单。服务端按组织、大会、购票人、操作和意图隔离幂等范围，请求摘要覆盖稳定明细 ID、规范化身份、票种、数量、表单、报价和授权；相同意图不同摘要返回冲突。重复尝试不得规避现有持久化限流。

### 7.4 锁定、额度和外部故障

下单、重建、改人、认领和账号删除先获取涉及的身份协调锁，按组织、大会、规范手机号/账号键稳定排序，再获取购票人/大会的额度协调锁。有微信交易状态变化时，随后获取现有支付准备/关闭协调锁，再进入业务行锁。统一业务行锁顺序为订单 ID、名额 ID、报名 ID、票券 ID、票种库存 ID、售后记录、相关账号；不需要的类别跳过，同类按稳定 ID 排序。

改人同时锁定旧、新身份；认领同时核对账号当前身份；账号删除在身份协调后按照相同顺序处理相关订单，最后解绑账号。现有先锁账号再锁订单、先锁票再锁报名的路径也要接入这一约定。外部 HTTP 请求在数据库短事务之外，使用现有支付或退款执行记录协调结果，不持有数据库锁等待微信。

活动名额按明细状态计算：有效待审核、有效预留、支付结果未知、已确认及已核销名额占额度；已批准退款但尚未关闭权益的名额继续占额度。零元名额取消或退票完整履约后释放。订单财务状态本身不能代替名额状态。

单批数量限制为当前配置且最多 20。一次建单整体成功或失败，批量查询与写入，禁止循环调用单人下单接口模拟批量。库存不足不能自动减少付费人数。新旧入口在同一购票人和身份协调中运行，避免单人接口与批量接口分别放行导致超额。

数据库失败、微信不可达、Redis 不可用、通知延迟和重复事件都沿用现有可核验状态处理：未知交易保留原单与库存，短信故障不阻止出票，退款资金事实与票务补偿分离。每个新重试或保护条件都对应上述明确状态，不增加独立服务、账户或通用重试框架。

## 8. 实施顺序与工作量

跨前台、支付站、后台、API、Worker、数据库、代理契约和部署检查，预计约 45 至 70 个文件，按实际依赖统计收口；上一版 30 至 45 个文件和 8 至 12 个工作日的估算偏乐观。按一位熟悉项目的工程师估算约 12 至 18 个工作日，包含迁移与回退演练，商户真机验收安排另计。新增部署服务、第三方账号、密钥和必填环境变量均为 0。

## 9. 验收标准

核心成功标准：**一次购买 5 人，生成 1 个订单、5 条报名、5 个名额明细，一次实际支付 ¥1,995，生成 5 张独立电子票；收入只计 ¥1,995。**

| 场景                                      | 必须通过的结果                                         |
| ----------------------------------------- | ------------------------------------------------------ |
| 首次购 1 / 2 / 5 个名额                   | 数量、卡片数、应付金额、报名数、库存变动、出票数一致   |
| 纯代购 / 包含本人                         | 购票人与参会人权限正确，本人手机号只绑定一次           |
| 已买 1 个再增购 4 个                      | 新增一单支付 ¥1,596；再购 1 个被累计上限阻止           |
| 5 改 3，再改 5                            | 金额正确，原资料按约定保留/删除并可撤销，无卡片串人    |
| 某位信息缺失或手机号重复                  | 整批不建单，定位对应卡片，其他输入保留                 |
| 有待支付订单 / 连点提交 / 两个浏览器并发  | 引导恢复原订单；不会创建超额名额或重复可支付订单       |
| 报价后改价、改表单、改上限或关闭开关      | 重新校验并明确提示；已有效创建订单按原规则履约         |
| 库存仅剩 3 个却提交 5 个                  | 全部失败，提示库存，不生成半批报名                     |
| 10 倍并发抢最后一批库存                   | 售出与有效预留不超过库存，账号累计不超限               |
| 付款取消、超时、未知、迟到通知和通道切换  | 真实资金先结清；预留准确释放；已付款批次仅出票一次     |
| 支付入账事务失败 / Worker 停止 / 通知重放 | 恢复后补齐全批票，无重复扣款、无重复出票，通知可补发   |
| 免费 5 人订单                             | 一次提交完成 5 位，不调用付费下单                      |
| 多人整单审核通过、驳回、超时、库存不足    | 全部状态一致，审核通过后一次支付，驳回可恢复资料       |
| 候补邀请提交数量 2                        | 前端解释限制，服务端明确拒绝                           |
| 5 人中选择 2 人退票                       | 申请 ¥798，成功后只取消 2 张票，剩余 3 张可核销        |
| 选中一张已核销票 / 退款审批与核销并发     | 不批准违反当前退款规则的操作；其余票权益不被误改       |
| 退款重放、余额不足、未知结果、外部退款    | 保留正确退款预留与责任，不重复执行、不自动猜测取消对象 |
| 部分退款后开票 / 已开票后退款             | 可开票金额正确，已开票进入既有调整状态                 |
| 购票人、参会人、其他用户、跨大会管理员    | 返回数据与动作权限各自正确，无整单财务或他人资料泄漏   |
| 历史已付/待付/退款/认领中的单人订单       | 迁移前后仍可操作，原单号、票码、支付与发票可追溯       |
| 手机、桌面微信、桌面浏览器                | 合适的支付入口，表单不遮挡、可键盘访问、恢复后人数准确 |
| 公开首页进入报名/支付/账户与返回          | 全页边界正确；敏感流程真实 Head 无统计脚本             |

本轮补充以下反向验收，作为进入多人开放阶段的必要条件：

| 场景                                       | 必须通过的结果                                                   |
| ------------------------------------------ | ---------------------------------------------------------------- |
| 新单人、旧单人、多人接口交叉提交           | 共用额度和身份保护，不能绕过数量上限                             |

| 修改已审资料与审批同时发生                 | 版本冲突；审核人不能批准未看过的新名单                           |
| 认领与改手机号/补发/退款并发               | 一个有效结果，旧邀请失效，无转错名额                             |
| 邀请到期或浏览器刷新后再次获取             | 可受控重新生成，不依赖无法取回的令牌哈希                         |
| 生成邀请后响应丢失、同键重试、令牌已被认领 | 短期密文结果按权限重放，过期或撤销后不回传旧链接，不创建重复邀请 |
| 两人退款中分次外部履行                     | 每笔退款映射可追溯，未完整履行名额保持正确状态，无重复分配       |
| 普通一人退款与另外四人核销                 | 未参与退款的票可核销；无法定位的整单异常按明确风险范围保护       |
| 全额补偿并保留某位权益                     | 财务金额与名额状态分开，票/名片/需求入口遵循保留权益决定         |
| 免费订单取消 2 人                          | 无资金退款请求，准确释放 2 个名额与预留/销量，重复请求无二次释放 |
| 2 个名额退票后候补队列等待                 | 按实际释放数量推进候补，事件重放不重复发出保留邀请               |
| 30 天新模型审核到期与审批竞争              | 仅一个状态生效；旧模型审核单不因迁移被自动关闭                   |
| 新表不存在时执行目标部署预检               | 使用旧结构检查；字段不足或查询失败不能判为无交易                 |
| 原单有 5 个明细但只有 1 张票               | 部署与恢复检查明确失败；补齐后才通过                             |
| A 回退版本读取 B 创建的多人单              | 完整支付、票证、认领、售后页面实际可用；仅多人新建被阻止         |
| 历史发票对应的报名已归并                   | 账户、后台、同步导出和 Worker 异步导出仍可查且金额不翻倍         |
| 账号删除与支付、退款、认领并发             | 未结清时拒绝删除，历史金额保留，财务不转移给其他参会人           |
| 10 批各 20 人并发购买最后 25 个名额        | 每批整体提交或失败，无超卖、超额度、半批记录或死锁残留           |
| 内存模拟模式、数据库模式、旧页面缓存       | 行为分支一致；模拟成功不作为数据库并发和真实支付证据             |

自动检查以现有 `pnpm check` 为全量门禁，增加真实 PostgreSQL 上的订单明细、批量下单并发、身份归并、按名额退款、迁移与回退集成测试；执行 `pnpm test:registration-experience` 与 `pnpm test:payment-resume` 回归。浏览器模拟付款只能证明页面与状态衔接；真实微信收款和原路退款需要在验收授权范围内单独核验，并明确记录证据。

## 10. 迁移、发布与回退

确认后先核对当前工作区及正在进行的支付恢复、后台操作和 Worker 改动，保留他人工作。隔离开发或演练使用独立项目、镜像、端口与数据卷；不接管主目录 `8088` 共享预览。桌面视觉检查使用自然视口，固定尺寸测试使用隔离浏览器，遵守共享视口清理规则。

迁移分为结构扩展、补写、验证三步，均纳入阶段 A 的发布：

1. 发布预检先探测数据库是否存在名额表及所需字段，选择完整旧模型或新模型检查。探测出半套结构、读取失败或计数不可信时阻止发布；不能把空结果当作没有交易。
2. 按既有 Runbook 创建数据库备份、记录运行版本与容器和镜像回退标签，并在预检、停服前、停服后完成支付结清。停止旧写入后执行增量结构和历史补写，避免旧代码在补写后继续创建缺明细订单。
3. 历史补写可重入，按稳定 ID 分批；校验每张旧单恰好一个明细、金额相符、范围外键有效、原支付与退款总额相同、旧订单数与票码不变。旧预留曾被释放后重新使用时保留其每次原始票种，不能都改映射为最后一次购买票种。
4. 在包含有效待付、已付、部分/全部退款、归并、旧式订单、过期预留和历史重开记录的脱敏副本演练迁移、重跑、失败中断与应用回退；不伪造财务关系来使验证通过。
5. A 首次迁移失败时保持写冻结与恢复标记；只有确认没有版本 2 订单、结构兼容验证通过且满足 Runbook 恢复条件时，才能恢复原镜像。A 的全部服务与数据模型验证通过后恢复流量；先保持单名额新购，证明已有多人样本可被完整履约。B 在 A 的基础上发布多人新建入口，不再把关键售后能力延后。

部署支付结清检查同时覆盖活动支付尝试、未处理支付通知、已付款缺明细/缺票、退款资金与权益同步异常。新模型按每个已购买名额核对对应票的存在及合法状态，免费已取消名额和明确保留权益的补偿退款按各自规则校验。部分退款订单也检查剩余票，不仅检查 `paid`。处理过且后续已退款的支付事件仍可凭原交易事实结清，不因合法退票变成永久未完成。

回退使用通过证明、能够处理新数据的 A 版本。部署脚本也必须具备上述结构探测和多人结清能力，不能调用旧版本“每单一张票”的检查。A 的回退演练验证构建身份、迁移哈希兼容及实际页面，不只验证容器启动。新增结构保留，禁止覆盖恢复数据库或删除多人订单；资金未知时继续原单核验。

正式发布遵循 `docs/production-deployment-runbook.md`，生产目标为已合并 PR 的 `merge_commit_sha`，且有该 SHA 的成功主分支 CI 与完整预构建镜像证明。部署保留 `BUILD_*` 身份、写冻结监督、生产数据保护与本机/公网/版本验收。阶段 A/B 的推送、PR 与发布按用户授权和仓库规则单独执行，本轮不产生这些动作。

当前本地 `geo-conference` / `tokems26` 仍是规范模板来源。代码文案、条款或关联设置完成后按规则导出完整与前台快照；获授权推送前运行 `pnpm canonical:check`。名额、草稿、订单、认领邀请、退款分配及其他个人/交易数据不得加入规范快照。规范同步保留生产销量与支付数据。

## 11. 对标与资料

参考只提取与本次目标直接相关的机制：

- [Ticket Tailor：结算表单](https://help.tickettailor.com/en/articles/950989-how-to-edit-your-checkout-form)：购票人问题按订单填写一次，参会人问题按每张票填写。本方案采用这种信息分层。
- [pretix 订单模型源码](https://github.com/pretix/pretix/blob/master/src/pretix/base/models/orders.py)及[官方订单明细接口](https://docs.pretix.eu/dev/api/resources/orders.html)：一个订单关联多个 position，每个明细有独立参会人和金额；付款后可按参会人分发通知。本方案采用订单与名额分离，并保留 TokEMS 现有账号认领和微信支付机制。
- [微信普通商户下单](https://pay.wechatpay.cn/doc/v3/merchant/4012791897)：订单总额与商品数量的接口基础。本方案中的“单订单总额付款”为据此作出的设计选择。
- [微信普通商户退款](https://pay.wechatpay.cn/doc/v3/merchant/4013070371)：部分退款及原交易金额基础。具体退款结果继续由可信通知和查单确认。

本轮重新读取了微信官方下单与退款资料、数据库约束资料及本地公开接口，未调用带商户凭据的交易接口。方案复用现有账号、微信商户、短信和任务基础设施，无需在实施中另行索取一套凭据。
