**建议确认的业务结果**

财务或管理员将实际开具的电子发票上传并成功登记后，系统自动向该订单的购票人发送短信，同时向发票申请中填写的接收邮箱发送邮件。短信携带当前文件的免登录访问地址；系统侧支持点击后直接返回 PDF，用户可预览或保存。链接建议有效 30 天，文件替换、作废或进入退款待调整状态后失效。

直达 PDF 的系统能力与短信渠道的投递资格需要分别验收。阿里云当前公开规范对文档链接、动态链接参数和跳转有限制，当前不能承诺这类短信一定获批或送达。带链接的短信上线必须以该业务场景、实际路径和完整样例通过渠道核验为条件。

**2. 用户与财务的完整流程**

```text
用户支付并提交开票资料
          |
财务审核 -> 在开票系统开具发票 -> 上传 PDF/OFD
          |
API 校验文件、发票状态、订单净额及退款状态
          |
同一数据库事务：登记文件 + 已开具 + 通知事件
          |
现有 Worker 校验当前版本，建立文件领取链接和渠道任务
          |
          +--> 阿里云短信 --> 购票人手机 --> 免登录文件入口
          |                                     |
          +--> 邮件渠道 --> 发票接收邮箱           +--> 校验令牌和版本
                                                       |
后台分别展示队列、受理、送达或失败 <--- 回执查询           +--> 私有存储 --> PDF
```

1. 用户继续填写现有的公司全称、统一社会信用代码、接收邮箱。无需新增手机号表单。
2. 财务或管理员按现有流程审核，上传已开具的文件。上传前显示“登记成功后自动发送短信和邮件”，并展示脱敏后的实际收件人及渠道可用状态。
3. 只有文件存在、大小、媒体类型、文件签名、SHA-256 校验通过，且发票登记事务提交成功，才创建通知。仅选择文件、上传失败或事务失败均不触发。
4. API 返回“发票已开具，通知排队中”。客户此时即可在原个人中心查看文件，后台无需等待短信网络请求。
5. Worker 从持久化事件取得当前文件，校验版本和有效性，分别执行短信及邮件。一个渠道失败不阻止另一个渠道。
6. 用户打开短信中的链接，系统校验通过后返回 PDF；支持 PDF 的浏览器可直接预览，其他终端按自身能力下载或调用阅读器。
7. 后台接收短信回执并展示结果。财务可只补发失败的短信或邮件。

**3. 收件人、自动发送与补发规则**

短信发给订单购票人。现代订单优先使用该购票人账号当前已验证手机号，账号无法读取时使用订单购票人手机号快照；仅在 `purchaserCustomerUserId` 与 `purchaseIntentId` 同时为空的历史订单中，允许沿用原报名手机号。身份存在歧义时记录“缺少有效购票人手机号”，交由后台处理。代他人购票时不自动发送给参会人。

邮件优先发给发票申请中的接收邮箱；历史申请缺少该邮箱时才回退购票人邮箱。这个邮箱可以是申请人指定的财务邮箱，因此邮件中的凭证只授予当前文件读取权。手机号缺失不阻止邮件；邮箱缺失不阻止短信。国内短信只接受现有适配器支持的中国大陆手机号，其他号码展示原因。

| 操作或事件 | 发送规则 |
| --- | --- |
| 首次上传并登记成功 | 当前文件自动发送一轮短信和邮件 |
| 批量导入 | 每条成功记录自动发送；批次失败不撤销成功条目的通知 |
| 替换、恢复文件 | 在原子切换文件后，旧链接失效；当前版本自动发送一轮 |
| 作废、取消、退款待调整 | 取消尚未下发的成功通知，撤销该版本领取链接 |
| 明确失败后重试 | 只重试相应渠道；文件状态保持已开具 |
| 人工再次发送 | 默认选择失败渠道；可明确选择短信、邮件或两者 |
| 用户在个人中心重新发送 | 复用现有入口，明确显示渠道，按当前文件重新排队 |
| 发布新版本 | 历史已开发票不自动补发；有需要时人工逐条发送 |

首次自动发送以“发票申请 + 文件版本 + 渠道”为唯一业务键。同一请求重试、重复事件、重复点击不创建第二次有效发送。人工补发产生单独的请求键，并记录操作者；同一渠道处于排队、发送中或等待结果时，返回现有任务。

管理员和用户补发统一执行每申请每渠道 10 分钟的持久化冷却，起点为补发任务入队时间。该间隔沿用现有用户侧 10 分钟设计。更换文件产生新版本，不受旧版本补发冷却阻止。首次自动发送和人工请求之间也检查是否已经存在当前版本任务。

**4. 免登录文件入口**

拟增加站点路径 `/invoice/file/:token`，沿用当前站点域名。生产展示域名以部署环境 `PUBLIC_ORIGIN` 为准；当前项目生产站点为 `hui.ailingdaoli.com`。内部通过网关映射至 API 专用文件读取接口。

- 令牌使用密码学安全随机数，长度 24 个英文字母和数字，首位为字母，保留约 142 位随机强度。手机号、税号、订单号、文件 ID 不构成令牌。
- 每个令牌绑定组织、大会、订单、发票文件及精确版本。版本沿用现有文件 ID、存储路径、内容摘要和出具时间的身份定义，兼容“替换时保留文件 ID”的现有行为。
- 领取地址有效期固定为创建后 30 天，有效期内允许重复查看。短信预览、HEAD 和 PDF 分段请求不消耗链接，避免手机预抓取导致无法打开。
- 同版本补发时重用尚未过期且未撤销的链接；过期后生成新的 30 天链接。更换接收手机号或邮箱时，发出新凭证并撤销原交付凭证。
- 数据库存储令牌哈希用于查找，原文仅按现有通知密钥加密存储，供重试和补发复用。事件、审计、运营列表及普通日志不保存明文链接。
- 文件继续存放于私有对象存储。API 每次校验后从内部存储读取并流式返回，避免把 10 分钟预签名地址作为短信长期链接，也避免站外跳转。
- PDF 返回 `application/pdf` 与 `Content-Disposition: inline`，支持 HEAD、Range、206/416 和安全文件名。OFD 保留原格式下载，界面如实显示 OFD；本次不做格式转换。
- 新链接要求当前发票状态为 `issued`，文件仍为当前有效版本。过期或撤销返回简短失效页，并提供个人中心重新获取入口；存储临时不可用返回可重试错误，不把临时故障显示成作废。
- 返回 `Cache-Control: private, no-store`、`X-Robots-Tag: noindex, nofollow, noarchive`、`Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`。文件及错误页均不加载统计、营销或第三方脚本。
- 新路径所有网关、反向代理和 API 请求日志都必须隐藏令牌；下载审计只记录资源 ID、结果和时间。正常下载使用每 IP 每分钟 60 次的入口限制，验证 Range 重试与共享网络下的使用体验。

持有链接的人可以在有效期内读取该份发票，因此转发短信会同时转交读取能力。后台提供“撤销领取链接并重新发送”，用于误发处理。已经保存到设备的 PDF 无法远程撤回。

**5. 短信文案与阿里云上线条件**

建议提交的通知正文：

> 您的${eventName}电子发票已开具，请于${expiresAt}前查看并保存：https://hui.ailingdaoli.com/invoice/file/${fileToken} 请妥善保管此链接。

签名由现有阿里云短信签名配置添加，不在正文重复拼接。`expiresAt` 使用明确的截止日期时间；变量长度和大会名称按审核通过的属性限制校验。文件替换后仍发送这条当前有效发票通知，后台时间线注明“文件更新后重新通知”。

该正文是产品目标稿，尚不具备可直接上线的渠道资格。当前阿里云规范包含以下约束：

- 完整链接应放在固定模板内容中，不能把完整 URL 作为普通变量传入；普通“链接参数”要求首位字母、英文数字组合，最长 8 位。
- 规范列有文档类链接限制；官网加变量的链接列为不可跳转。
- 官方说明：若参数长度无法满足场景，需要提交完整示例，由审核人员综合评估。带链接短信还存在运营商拦截风险。

以上见[阿里云通知短信模板规范](https://help.aliyun.com/zh/sms/user-guide/notification-template-specifications/)和[模板常见问题](https://help.aliyun.com/zh/sms/user-guide/message-template-faq)。

本方案假设渠道愿意接受“官网上的电子发票领取、24 位随机参数、直出 PDF”的真实场景。如果该假设不成立，系统功能仍可用于邮件和后台领取，但短信直达 PDF 的上线目标尚未完成。不得把凭证缩短到 8 位来换取免登录财务文件访问，也不使用跳转伪装审核内容。

确认方案后的渠道工作由实施方准备完整文案、实际路径、无真实客户信息的样例发票及材料；组织短信管理员核验现有签名、模板和报备状态，并通过阿里云实际审核确定可用性。现有 `invoiceReady` CODE 若绑定旧参数，必须继续使用旧映射，直到新模板 CODE 与参数映射一起切换；配置显式保存发票场景 `templateVersion`，旧记录默认旧版。测试发送需使用已授权的内部测试号码和实际站点路径，替换当前发票场景中的 `example.com` 测试值。

若直达 PDF 被渠道拒绝，可另行确认“短信打开免登录领取页，再点一次查看 PDF”的替代体验，并按该真实页面重新审核。该页面仍须通过带链接短信的渠道要求，不能预先承诺获批。审核未完成期间保留现有发票查询与邮件交付，新的短信场景保持关闭，不自动替用户选择替代体验。

**6. 后台展示与异常处理**

发票管理和报名详情中的发票面板使用相同的交付展示：

| 信息 | 示例含义 |
| --- | --- |
| 发票状态 | 已开具，与通知结果分开 |
| 短信接收人 | 脱敏手机号及来源“购票人” |
| 短信状态 | 待发送、发送中、已受理待回执、已送达、发送失败、结果待确认、未发送及原因 |
| 邮件接收人和状态 | 发票指定邮箱及渠道结果；没有送达回执时显示“已提交邮件渠道” |
| 领取链接 | 有效截止时间、已撤销或已过期；不在列表中公开原始令牌 |
| 操作 | 补发短信、补发邮件、撤销领取链接并重新发送 |

通知状态以 `notification_deliveries` 的分渠道记录为事实来源。现有 `deliveryStatus` 保留兼容用途，前端不再仅凭它宣称短信已送达。渠道受理后先显示“已受理待回执”，收到送达结果才显示“已送达”；下载行为只记为“链接访问”，不认定实际收件人已阅读。

账号关闭、缺少模板、模板未验证、号码不可用均显示明确原因。任一通知失败均不回滚发票登记、不重复上传文件、不改变开票状态。生产新发票短信不得因为配置缺失而退回本地通知收集器并显示成功。

复用现有队列和阿里云回执查询。明确可重试的渠道故障按现有退避重试，配置错误等待修复后人工补发；超时或连接中断造成结果未知时优先查询回执，不立即创建新的发送请求。阿里云 SendSms 本身不提供幂等保证，业务去重仍由系统承担，`OutId` 用于关联和查询，不能当作渠道幂等键。[阿里云 SendSms 文档](https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms)

两渠道任务先持久化，再分别执行和保存结果；一个渠道抛错不能提前结束另一个渠道的处理。任务重跑时跳过已有成功结果，只继续尚未完成的渠道。单个渠道失败不撤销另一个渠道已经交付的文件领取凭证；版本变更、主动撤销和到期统一控制链接有效性。

替换、退款与通知并发时，在原有订单到发票的锁顺序和当前版本校验下处理；发送前再次核对版本。已被渠道受理的旧短信无法撤回，但其领取链接会因旧版本被撤销而停止提供文件。

**7. 实施边界与文件接口**

最小改动方式是在现有发票页面链接之外增加一个短信任务；它仍有页面中再次下载及默认 10 分钟有效期的使用限制。推荐完成本方案的专用文件领取入口、分渠道通知及后台补发能力，一次形成可验收的闭环。

预计涉及约 15—25 个文件及 1 次增量数据库迁移，复用现有 API、Worker、PostgreSQL、Redis、对象存储和阿里云服务，新增部署服务为 0，新增环境变量和第三方账号为 0。首版不扩展税务平台自动开票、不转换 OFD、不批量补发历史申请。

新链接表包含组织/大会/订单/发票/文件关联、文件版本身份、tokenHash、sealedToken、expiresAt、revokedAt、createdAt；tokenHash 唯一。通知业务键唯一且允许历史记录为空。领取凭证与原 `order_access_tokens` 独立，原有订单/补资料入口保持兼容。

复用的配置和账户：组织级阿里云 AccessKey、AccessKeySecret、已报备签名及审核通过的发票模板；现有对象存储读权限；现有通知加密密钥；现有邮件渠道；现有站点域名及 HTTPS。凭据由当前配置读取，不复制进方案、Git 或日志。模板 CODE 是审核产物，由组织短信管理员在启用时填写。

**8. 验收、发布和回退**

确认方案后，先检查工作区变动，保留目前支付、报名、Worker 等未提交工作；按当前本地 main 的协作规则实施。功能作为一个完整交付单元验证，模板获批与真实通知启用独立控制。

核心验收场景：

1. 单张和批量上传成功触发通知；失败、取消上传和重复登记均不产生额外短信。
2. 购票人和参会人不同、指定发票邮箱和账号邮箱不同、历史订单、手机号缺失、账号不可用、非大陆号码均使用确定的收件人规则。
3. 新浏览器、无 Cookie、无登录态访问有效链接直接得到 PDF；手机终端、保存文件、HEAD、Range、重复打开均正常。
4. 随机令牌、跨组织文件、过期链接、作废、替换同文件 ID、退款待调整均不能取得不应提供的文件。
5. 短信与邮件分别成功或失败、模板未配置、服务关闭、接口超时、结果未知、渠道已受理、重复回执和 Worker 重启均有正确状态。
6. 首次事件重复、管理员连续点击、用户与管理员并发补发、旧事件延迟到达、发送与替换/退款竞态均覆盖；已成功渠道不因其他渠道重试而重复发送。
7. 补发重用未过期链接，过期生成新链接；撤销后原短信打不开，后台审计可追踪。
8. PDF 内容及摘要与上传文件一致，OFD 如实下载；存储短暂故障可恢复，不把一次大文件请求完整缓冲到内存。
9. 真实网关、外部代理和 API 日志不含令牌，响应及错误页无统计、无跨站跳转、无缓存；对象存储权限保持私有。
10. 原开票金额、退款互斥、文件校验、个人中心、发票详情和订单访问入口回归通过。

实施阶段运行：`pnpm --filter @conference/api test`、`pnpm --filter @conference/worker test`、`pnpm --filter @conference/contracts test`，以及受影响 Database/Admin/Web 测试、`pnpm lint`、`pnpm typecheck`、`pnpm build` 和网关测试。全链路测试使用隔离数据与本地通知收集器，验证未知结果与重试时使用可控渠道替身。真实发票短信仅在明确授权的内部号码上验收，核对实际送达和无登录 PDF 打开结果。

本次方案确认不包含 Git 提交、远端推送或生产发布。后续授权发布时执行仓库既有 canonical 检查、PR/CI、预构建镜像与生产 Runbook；本次领取令牌及通知交付记录属于业务数据，不进入规范模板快照。规范通知模板如果同时调整，按现有 canonical 导出和检查规则执行。

运行时回退优先关闭 `invoiceReady` 新短信场景，保留文件入口和邮件交付，避免已发送链接突然失效。数据库采用增量迁移，不删除旧字段或覆盖业务数据。完整回退至旧镜像会失去新入口，因此需先确认存量新链接的处理；这一步应列为回退记录中的明确用户影响。

**需要确认的五项业务选择**

1. 上传并登记成功后自动发送短信与邮件；批量导入、替换和恢复文件采用同一规则。
2. 短信发给购票人，邮件发给发票申请中的接收邮箱。
3. 链接免登录、只可读当前文件，默认 30 天有效，替换、作废或退款待调整后撤销。
4. 后台显示短信及邮件独立结果，支持按渠道补发及撤销链接。
5. 按短信直达 PDF 的目标进行本地实现；带链接短信正式启用以实际渠道审核和授权测试通过为条件。若审核不接受，再确认免登录领取页等替代体验。
