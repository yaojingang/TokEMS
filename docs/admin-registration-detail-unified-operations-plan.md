# TokEMS 报名详情统一运营工作台方案

> 状态：初版方案存档｜版本：v1.0｜评审日期：2026-08-04
>
> 目标页面：`/admin/events/:eventId/registrations/:registrationId`
> 本次示例：大会 101 的报名记录 `2a6104bd-f882-4d34-b73c-398f883d72ab`

## 1. 方案结论

推荐把当前报名详情升级为一个“以报名记录为核心的统一运营工作台”。运营人员进入一条报名后，可以在同一页面完成以下工作：

- 快速确认参会人、报名、订单、退款和发票的当前状态。
- 查看并维护本次报名资料，以及已关联的用户资料。
- 查看订单实付、支付方式、已退金额、可退金额和退款记录。
- 发起全额或部分退款，并在确认前看到退款对发票的影响。
- 查看发票申请、购买方资料、开票金额、电子文件、发送状态和处理历史。
- 审核、驳回、重试、登记发票、上传文件、作废文件、下载和重新发送。
- 在发票资料未提交时，重新发送安全的发票填写入口。
- 查看报名、支付、退款、发票和通知的统一处理记录。

全局报名列表、发票列表、订单列表继续承担搜索、筛选、批量处理和导出。单条记录相关的高频查看与操作全部放进报名详情页。

### 推荐布局

采用“顶部状态轨道 + 主内容区 + 右侧运营栏”的记录型工作台：

- 顶部状态轨道负责回答“现在是什么状态”。
- 主内容区负责回答“具体信息和历史是什么”。
- 右侧运营栏负责回答“下一步可以做什么”。
- 页面内锚点和就地展开表单负责快速定位，常规操作不切换业务页面。

### 最小方案及取舍

最小方案是在现有四格概览后增加第五格发票状态，再把发票管理页的详情用链接打开。该方案改动较少，也会继续保留状态割裂、全场退款数据读取、跨页操作和重复界面逻辑。推荐方案直接复用现有发票底层能力，并在报名详情形成一个完整的单记录工作台。

## 3. 当前页面与真实数据核对

### 3.1 当前首屏

当前顶部概览只有四项：

1. 报名状态
2. 订单状态
3. 订单金额
4. 已退款

页面下方已经有参会人信息、报名信息、订单与支付、退款记录、报名表与授权、用户账号六个模块。信息完整度尚可，结构平均分配，缺少运营优先级，页面高度较长。

### 3.2 示例报名的实际情况

真实接口核对结果：

- 报名状态：已签到
- 订单状态：已支付
- 订单金额：399 元
- 已退款：0 元
- 报名时开票意向：需要发票
- 发票申请状态：已开具
- 发票发送状态：已发送
- 有 1 份有效 PDF 电子发票
- 有完整的申请、提交资料、审核、开具状态记录

当前报名详情只显示“是否需要发票：是”。运营人员无法在这张页面看到已经开票、已经发送和已有 PDF 文件，形成了明显的信息断层。

### 3.3 已具备的能力

现有代码已经提供以下能力，实施时应抽取和复用：

- `RegistrationDetailView.vue`：报名审核、退款、退款余额校验、参会人和报名快照展示。
- `InvoicesView.vue`：发票状态、审核、驳回、重试、标记失败、取消申请、PDF/OFD 上传、登记文件、作废、下载、发送、处理记录。
- `InvoiceOperationsService`：组织与大会范围校验、乐观并发、状态流转、审计、对象存储校验、发送队列。
- `CommerceOperationsService`：部分退款和全额退款、幂等、退款后订单和发票联动。
- 数据库约束：一条报名对应一个订单，一个订单最多对应一个发票申请。

### 3.4 主要技术缺口

- 报名详情接口没有返回关联发票。
- 页面为了显示一条订单的退款记录，会读取当前大会的全部退款后在前端筛选。
- 发票操作逻辑集中在一个较大的列表页面组件中，无法直接复用到报名详情。
- 发票状态和发送状态没有合成运营人员能直接理解的状态。
- 退款成功后会改变发票状态，页面缺少操作前影响提示和统一刷新。
- 发票资料填写入口首次发送后，后台缺少面向单条记录的重新发送入口。
- 用户、订单、发票和通知的业务记录分散在不同页面。

## 4. 三个顶级对标案例

### 4.1 Stripe Dashboard

[Stripe 官方发票管理文档](https://docs.stripe.com/invoicing/dashboard/manage-invoices)明确采用状态驱动的详情操作。发票详情中的编辑、备注、重发、下载等动作会随当前状态变化，列表状态徽标与详情状态允许承担不同粒度的信息。

借鉴点：

- 顶部显示容易扫描的主状态，详情区展示完整原始状态和说明。
- 操作按钮由状态机决定，避免展示当前无法执行的动作。
- 文件下载、发送和更正都围绕同一张发票详情展开。
- 已完成对象保留历史和文件，后续更正通过作废与重开形成可审计链路。

在 TokEMS 中的应用：

- 顶部显示“已开票”“待提交资料”等运营主状态。
- 次级文案显示“已发送”“发送失败”“待调整”等交付状态。
- 发票动作区只显示当前状态允许的动作。

### 4.2 Shopify Admin Order Detail

[Shopify 官方订单详情文档](https://help.shopify.com/en/manual/fulfillment/managing-orders/managing-order-details)把订单信息、付款事件、退款排查、客户资料、联系客户、重发邮件、内部备注和 Timeline 放在订单详情中。支付和退款事件可以直接在时间线展开查看。

借鉴点：

- 单条订单是运营处理的上下文容器。
- 资金动作与时间线放在同一页面，便于排查问题。
- 联系客户、重发邮件和内部备注属于详情页的常规支持动作。
- 快照数据保留交易发生时的历史事实。

在 TokEMS 中的应用：

- 报名记录作为大会运营的上下文容器。
- 订单、退款和发票放在同一主内容区。
- 退款前显示发票联动影响。
- 保留报名表、条款和票价快照的历史语义。

### 4.3 HubSpot CRM Record Page

[HubSpot 官方记录页文档](https://knowledge.hubspot.com/records/work-with-records)将记录页分成身份与动作区、主要信息与活动区、关联记录区。活动时间线、核心属性、关联对象和附件都围绕当前记录组织。

借鉴点：

- 页面始终围绕一个明确的记录主体。
- 高频身份信息和快捷动作持续可见。
- 主区域按任务组织详细内容和活动时间线。
- 关联对象以摘要呈现，需要时再展开完整信息。

在 TokEMS 中的应用：

- 右侧运营栏固定展示参会人联系方式、账号关系和下一步动作。
- 主区域承载订单、退款、发票、报名表和处理记录。
- 信息按运营任务排序，减少同权重卡片造成的扫描成本。

### 4.4 对标后的选择

最终采用以下组合：

- Stripe 的状态机和条件动作。
- Shopify 的订单、资金、联系与时间线一体化。
- HubSpot 的记录中心布局和关联信息组织。
- TokEMS 现有的深蓝编辑式视觉、宋体标题、低饱和状态色和紧凑数据密度。

## 5. 页面信息架构

### 5.1 页面骨架

```text
返回报名管理

参会人姓名的报名详情                         [刷新]
报名码 · 提交时间 · 最近更新时间

┌────────┬────────┬────────┬────────┬────────────┐
│ 报名状态 │ 订单状态 │ 订单金额 │ 已退款   │ 发票状态       │
│ 已签到   │ 已支付   │ ¥399.00 │ ¥0.00  │ 已开票         │
│ 两日通票 │ 订单号   │ 微信支付 │ 可退金额 │ 已发送 · 发票号 │
└────────┴────────┴────────┴────────┴────────────┘

┌────────────────────────────────────┬──────────────────┐
│ 主内容区                             │ 运营栏            │
│                                    │                  │
│ 订单与资金                           │ 参会人档案         │
│ 发票与交付                           │ 联系方式           │
│ 报名资料与表单                       │ 账号关系           │
│ 统一处理记录                         │ 当前待办           │
│                                    │ 可执行操作         │
└────────────────────────────────────┴──────────────────┘
```

### 5.2 页面顺序

1. 面包屑和记录标题
2. 五项状态轨道
3. 当前需要处理的异常或待办提示
4. 订单与资金
5. 发票与交付
6. 报名资料与表单
7. 统一处理记录
8. 桌面端右侧固定运营栏

这个顺序优先支持运营人员常见的三个问题：钱是否收到、发票处理到哪一步、下一步需要做什么。

### 5.3 视觉方向

- **视觉主题**：深蓝编辑式运营记录台，紧凑、克制、可信。
- **内容原则**：先定位记录，再看状态，再完成动作，最后追溯历史。
- **交互原则**：状态单元可定位到对应区域，操作表单在当前区域展开，完成后原位反馈并刷新关联数据。
- **CSS 策略**：继续使用 Vue SFC scoped CSS 和现有全局语义令牌，不引入新的样式框架。
- **层级方式**：画布、主内容和运营栏使用背景明度阶梯；业务分组使用细分隔线；浮层只用于文件选择等需要焦点锁定的任务。
- **数字样式**：金额、数量、订单号和时间使用等宽数字。
- **状态颜色**：绿色表示完成，琥珀色表示待处理，蓝色表示处理中，红色表示失败或高风险，灰色表示未申请、取消和受限。
- **文案**：内部模块优先使用中文标题，英文仅用于编号、代码和少量既有系统标识。

### 5.4 响应式规则

- `>= 1180px`：主内容区与 340px 右侧运营栏并排，运营栏在页面内吸顶。
- `760px 至 1179px`：单列布局，运营栏移动到状态轨道下方。
- `< 760px`：状态轨道使用两列，发票状态占满最后一行。
- `< 520px`：表单和字段列表使用单列，主要按钮保持 40px 最小触控高度。
- 375px 和 320px 宽度不得产生页面级横向滚动。

## 7. 发票状态模型

现有原始状态继续作为业务事实。页面增加一个纯展示派生函数 `deriveAdminInvoicePresentation()`，统一生成标签、颜色、说明和推荐动作。

| 条件                         | 顶部主状态   | 次级说明                   | 推荐动作           |
| ---------------------------- | ------------ | -------------------------- | ------------------ |
| 无申请，报名时未选择发票     | 未申请       | 参会人未申请发票           | 无                 |
| 无申请，选择发票，订单未支付 | 待支付后申请 | 支付成功后创建申请         | 查看订单           |
| 无申请，选择发票，订单已支付 | 状态异常     | 申请记录未创建             | 刷新并提示运营排查 |
| `awaiting_details`           | 待提交资料   | 发票填写入口已发送或待重发 | 重新发送填写入口   |
| `pending_review`             | 资料待审核   | 参会人已提交开票资料       | 审核通过、驳回     |
| `issuing`                    | 开票中       | 财务审核已通过             | 登记发票、标记失败 |
| `issue_failed`               | 开票失败     | 显示失败原因               | 重新开具、取消     |
| `issued` + `not_sent`        | 已开票       | 待发送给参会人             | 发送发票           |
| `issued` + `queued`          | 已开票       | 等待发送                   | 暂停重复操作       |
| `issued` + `sent`            | 已开票       | 已发送，显示最近发送时间   | 下载、重新发送     |
| `issued` + `failed`          | 已开票       | 发送失败                   | 重新发送           |
| `rejected`                   | 资料已驳回   | 显示驳回原因               | 重发填写入口、取消 |
| `adjustment_required`        | 退款待调整   | 已开票订单发生退款         | 作废或登记调整文件 |
| `voided`                     | 已作废       | 保留历史文件与原因         | 重新开具           |
| `cancelled`                  | 已取消       | 显示取消原因               | 查看历史           |
| 无发票查看权限               | 无查看权限   | 需要发票查看权限           | 无                 |

### 7.1 三层状态表达

发票区域同时表达三层信息：

1. 申请生命周期：待资料、待审核、开具中、已开具、失败、作废等。
2. 文件状态：无文件、有效 PDF/OFD、已作废、调整文件、重开文件。
3. 交付状态：未发送、排队中、已发送、发送失败。

这样可以准确覆盖“未提交”“提交未开”“提交已开”，也能支持日常异常处理。

## 8. 各区域详细设计

### 8.1 右侧运营栏

固定显示：

- 参会人姓名、公司、职位、城市。
- 手机号和邮箱，提供复制按钮。
- 用户账号关系：已关联、未关联、权限受限。
- 当前待办：报名待审核、支付即将过期、发票待审核、发送失败、退款待调整等。
- 当前状态允许的快捷动作。

动作按风险分组：

- 常规：刷新、复制联系方式、编辑资料、下载发票、重新发送。
- 流程：审核报名、审核发票、登记开票、发送填写入口。
- 高影响：退款、驳回、取消申请、作废发票。

高影响操作需要展示对象、金额、当前状态和预期结果，并要求二次确认。

### 8.2 订单与资金

展示：

- 订单号、状态、票种、订单金额、实付金额、支付方式。
- 创建时间、支付截止时间、支付成功时间。
- 已退款、可退金额和退款记录。
- 订单状态历史。

退款表单在本区域就地展开，包含：

- 退款金额，默认填入可退余额。
- 退款原因。
- 退款后的订单状态预览。
- 发票影响预览。

发票影响示例：

```text
本次退款 ¥199.00 后：
订单将变为“部分退款”
已开具发票将变为“退款待调整”
```

退款成功后重新读取整条报名运营数据，因为订单、报名、票、退款和发票状态可能同时变化。

### 8.3 发票与交付

发票区域分为四个层次。

#### 状态摘要

- 发票申请编号
- 当前状态
- 开票金额
- 订单实付
- 发送状态
- 最近发送时间

#### 购买方资料

- 个人或企业
- 发票抬头
- 统一社会信用代码
- 开票内容
- 接收邮箱
- 联系手机号
- 申请时间和审核时间

#### 电子发票文件

每份文件显示：

- 发票号码和发票代码
- 原始、调整或重开关系
- PDF 或 OFD
- 文件大小
- 开具时间
- 外部流水号
- 有效或作废状态
- 下载和作废动作

#### 发票处理记录

按时间展示：

- 申请创建
- 资料提交
- 财务审核
- 开票、失败、重试
- 文件登记和作废
- 发送排队、发送成功或失败
- 退款触发的调整状态

### 8.4 发票资料填写入口

`awaiting_details` 和 `rejected` 状态提供“重新发送填写入口”。

规则：

- 生成新的订单访问令牌，范围只包含 `invoice:read` 和 `invoice:write`。
- 令牌有效期为 24 小时。
- 服务端只保存令牌摘要。
- 发送新入口时撤销同订单之前未过期的发票填写令牌。
- 通过现有 Outbox 和通知模板排队发送。
- 同一发票 10 分钟内不重复发送。
- 页面显示排队、成功、失败和最近发送时间。
- 原始令牌不展示在后台页面，也不写入日志。

### 8.5 报名资料与用户资料

报名资料区域展示并允许编辑本次报名快照：

- 姓名、手机、邮箱、公司、职位、城市。
- 票种、报名码、状态、提交和更新时间。
- 额外表单字段、营销授权、条款版本和条款快照。

编辑规则：

- 需要 `event.registration.manage`。
- 只修改本次报名记录和对应核心表单答案。
- 使用 `expectedUpdatedAt` 处理多人同时编辑。
- 手机号、邮箱执行与报名流程一致的校验和标准化。
- 保存后记录审计日志。

已关联用户账号且拥有 `customer.manage` 时，页面额外允许编辑：

- 用户常用姓名、邮箱、公司、职位和城市。
- 标签和内部备注。

报名详情响应为已关联账号补充 `profileVersion`。修改常用资料时复用现有 `UpdateCustomerAdminSchema`，提交当前版本并处理并发冲突。账号资料编辑同时要求 `customer.read` 和 `customer.manage`。

用户账号状态、账号删除、历史合并和数据导出继续留在用户管理页，这些操作影响多场大会或具有较高破坏性。

### 8.6 统一处理记录

统一时间线合并以下来源：

- 报名创建、审核和资料修改。
- 订单状态记录和支付事件。
- 退款记录。
- 发票状态记录、文件动作和发送状态。
- 与本报名关联的通知投递记录。

每条记录包含：

- 业务类型
- 标题和简短说明
- 操作者或系统来源
- 发生时间
- 成功、处理中、失败或中性语义

默认加载最近 30 条，继续加载不离开当前页面。时间线元数据只返回安全字段，不返回访问令牌、完整支付载荷和对象存储路径。

## 10. 数据与接口方案

### 10.1 推荐方案

扩展现有报名详情接口，增加按权限裁剪的资金和发票上下文。页面级时间线使用单独的游标接口，在首屏完成后加载。

#### 报名详情响应新增字段

```ts
finance:
  | {
      access: 'included';
      refunds: Refund[];
      refundedAmount: number;
      refundableAmount: number;
    }
  | {
      access: 'restricted';
    };

invoice:
  | {
      access: 'included';
      request: InvoiceRequest | null;
    }
  | {
      access: 'restricted';
    };
```

权限规则：

- 报名基础数据继续需要 `event.registration.read`。
- 退款明细需要 `event.order.read`。
- 发票详情需要 `event.read` 和 `org.invoice.read`。
- 写操作继续使用各自现有权限。
- 活动接口逐类裁剪内容：订单与退款事件需要 `event.order.read`，发票事件需要 `org.invoice.read`，通知事件需要 `event.notification.read`。

#### 新增接口

```text
PATCH /admin/events/:eventId/registrations/:registrationId/attendee
GET   /admin/events/:eventId/registrations/:registrationId/activity?cursor=&limit=30
POST  /admin/events/:eventId/invoices/:invoiceId/request-details
```

`PATCH attendee` 输入：

```ts
{
  expectedUpdatedAt: string;
  attendee: {
    name: string;
    mobile: string;
    email: string;
    company: string;
    title: string;
    city: string;
  }
}
```

活动接口响应：

```ts
{
  items: Array<{
    id: string;
    kind: 'registration' | 'order' | 'refund' | 'invoice' | 'delivery' | 'notification';
    title: string;
    description: string;
    tone: 'neutral' | 'info' | 'warning' | 'success' | 'danger';
    actorName: string | null;
    occurredAt: string;
  }>;
  nextCursor: string | null;
}
```

## 15. 风险与应对

| 风险                       | 影响                   | 应对                                                           |
| -------------------------- | ---------------------- | -------------------------------------------------------------- |
| 页面信息过多               | 首屏和长页扫描变慢     | 状态轨道、任务排序、右侧运营栏、渐进展开和下方时间线分页       |
| 发票状态与发送状态混淆     | 运营判断错误           | 使用主状态加次级交付说明，完整原始状态保留在发票区域           |
| 退款引发发票联动           | 局部刷新显示旧数据     | 操作前预览影响，成功后刷新完整详情                             |
| 发票页面与报名页面逻辑分叉 | 状态和动作不一致       | 抽取共享派生函数、动作组件和组合逻辑                           |
| 对象存储不可用             | 无法上传或下载         | 保留已有状态，禁用文件动作，明确显示服务错误，其他操作继续可用 |

| 敏感信息泄露               | 税号、邮箱和手机号越权 | 服务端按权限裁剪，活动元数据白名单，下载审计                   |

## 16. 依赖、回滚和扩展边界

### 依赖

本方案不增加新的第三方服务、API Key 或运行时。继续使用现有：

- PostgreSQL
- 对象存储和预签名上传
- Outbox 与通知 Worker
- 邮件或短信通知配置

对象存储或通知渠道未配置时，对应操作显示不可用或失败状态，页面其余功能正常工作。

### 回滚

- 阶段 1 只增加读取字段和页面展示，不修改业务数据，可以直接回退前端和新增响应字段。
- 阶段 2 沿用现有发票和退款状态机，回退报名详情入口不会影响已经完成的业务操作。
- 阶段 3 的报名资料编辑使用现有报名表字段，不增加数据库表，回退后历史数据继续有效。
- 新接口为增量接口，旧报名、订单和发票页面继续可用。

### 最脆弱假设

本方案假设一条报名对应一个订单，一个订单最多对应一个发票申请。当前数据库唯一索引已经保证这个关系。如果未来支持团体订单或一单多票、多张发票，顶部状态单元和下方发票区域需要升级为集合摘要，页面路由和整体结构可以继续沿用。
