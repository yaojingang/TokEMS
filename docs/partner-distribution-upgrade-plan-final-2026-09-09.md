# TokEMS 合作伙伴与分销升级最终方案

版本：v2.0，详细审查修订版，待用户确认  
日期：2026-09-09  
代码基线：本地 `main`，`34ddc59055beaa7b04d83e1e35fbb62dedb71a98`  
本文件完整替代 v1.0 的实施口径。本轮只审查和完善方案，未修改业务代码、数据库、运行服务或微信商户配置，未进行真实转账。

## 1. 建议确认的完整方案

在普通用户账号上新增**大会级“合作伙伴”资格**，注册默认关闭，由管理员开通。伙伴可以编辑独立资料，选择公开字段，获取分销链接与海报，查看收益并申请提现。支持未购票用户成为伙伴，合作资格与参会资格独立。

完整交付五个入口：**大会首页合作伙伴模块、个人中心合作伙伴中心、后台用户快速开通、大会后台分销管理、组织后台微信出款设置**。技术上沿用现有 Nuxt、Vue、NestJS、PostgreSQL、Redis 和异步任务体系，新增部署服务数为 0。

采用一级推广、订单结算批次归因、版本化佣金、独立财务账本和人工审核。分两阶段交付：第一阶段形成推广、计佣与人工结算闭环；第二阶段打通微信“商家转账”，由用户逐笔确认收款。

| 待确认参数 | 推荐默认值 |
| --- | --- |
| 开通与公开 | 管理员开通；伙伴确认条款后生效；总公开与联系方式默认关闭 |
| 佣金 | 首发固定 10%；后台同时支持订单数阶梯和个人固定比例 |
| 归因 | 30 天内最后一次有效主动点击；每次有效结算批次锁定；自然访问不覆盖 |
| 计佣范围 | 本大会适用票种的真实已支付订单；本人作为购票人的自购与代购不计佣 |
| 结佣时间 | 支付满 7 天与订单退款窗口结束后满 24 小时取较晚值；退款、争议与异常继续冻结 |
| 提现 | 税前 10 元起，人工审核，税费与实付额由用户确认后出款；平台服务费为 0 |
| 微信资金 | 主办方安排运营账户出款余额；具体准入、场景和额度按真实商户批准结果配置 |
| 生效方式 | 确认方案后实施；生产推广和真实出款分别通过验收后启用 |

这些比例、期限和门槛均为本方案的产品建议。微信平台规则另在第 7 节列明。

业务前提：主办方作为售票主体向自己的推广合作方支付佣金，使用现有普通商户直连模式。多个独立售票商户由平台统一代收代付不在本期范围内，该业务形态需要另行设计支付主体、结算关系与平台资质。

## 2. 本轮详细审查后的关键修订

以下是方案层面的缺口及修订，不代表当前生产系统已经发生相应故障。

| 原方案缺口 | 最终处理 |
| --- | --- |
| 把计佣计算放在支付出票事务里，扩大购票故障影响 | 支付保留现有支付、出票和事件事务；独立消费者持久化计佣，支持补账；出款前复核真实交易事实 |
| 同一订单永久保留第一次来源，与现有超时订单复用冲突 | 增加不可变结算批次；活动批次重试保留来源，安全恢复后的新批次重新归因；支付尝试绑定批次 |
| 规则换版只保留订单快照，伙伴接受新合同的过程不完整 | 增加条款与规则接受历史、生效时间、变更通知及过渡期，历史权益不重算 |
| 微信优惠后的计佣金额存在歧义 | 明确使用核验成功的订单成交总额减成功退款总额；微信付款人现金额与商户到账净额单独展示 |
| 异步、退款和提现并发缺少明确边界 | 独立财务事件收件箱、统一短事务锁顺序、出款提交点和积压冻结规则 |
| 人工结算缺少与微信同等级的防重复设计 | 先锁定执行记录再线下打款；结果不明持续占用；银行流水核验后结清；禁止未知状态换渠道 |
| “查看税费”不足以证明同意实际出款金额 | 保存不可变结算明细，用户明确确认税前、税费、实付与收款人；变更后重新确认 |
| 按每次提现独立算税可能遗漏同项目合并口径 | 财务按付款主体、收款主体、税期和项目汇总，记录已扣、已申报和调整依据 |
| 已提现后退款可能重复追偿税款 | 分开记录佣金冲正、现金追偿和税额调整；税务结果未核定时暂停自动抵扣出款 |
| 多大会共享商户资金和额度，容易重复占用预算 | 商户级出款调度与预算占用，大会级账务；展示余额核验时间及在途款 |
| 公开撤回、海报传播、账号注销与大会取消的边界不够清楚 | 独立公开和海报授权；停止新生成与公开访问；保留必要账务并走最终结清流程 |
| 模板同步可能把规则默认值变成生产合同变更 | 模板只携带展示配置和未启用规则草案；生产财务规则必须显式发布，运行数据禁止同步覆盖 |

## 4. 五个入口与用户权限

### 4.1 大会首页和合作伙伴目录

- 增加“大会合作伙伴”区块和导航锚点，建议放在合作机构区域附近。机构 Logo 墙、报名会员和个人合作伙伴分别维护。
- 首页最多 12 人，目录每页 24 人；按管理员排序值、开通时间和稳定 ID 排序。展示头像、展示名、公司、职位和简介摘要，点击查看详情。
- 公开条件同时满足：大会允许展示、合作资格有效、普通账号正常、用户同意公开、达到资料最低完整度、管理员未隐藏。最低要求为展示名和一句介绍，头像可使用通用图形。
- 联系方式按用户逐字段授权，仅在详情页展示；列表和搜索接口不输出未授权字段。没有可展示伙伴时隐藏首页区块。
- 目录和介绍页的普通浏览不改变推荐来源。主动点击“通过我报名”才进入该伙伴的推广入口。
- 拟采用 `/partners?event={eventSlug}`、`/partners/{publicSlug}?event={eventSlug}`，服务端同时校验组织、大会和伙伴归属。规范网址不包含推广参数。
- 导入型 HTML 首页本期可配置到目录的普通链接，不增加动态组件编译能力。

### 4.2 个人中心的合作伙伴中心

拥有合作关系后，即使未购票也可进入。多场大会可切换，资格、规则和收益分别展示。暂停或关闭资格后仍保留历史收益与结清入口。

| 标签 | 功能 |
| --- | --- |
| 我的资料 | 头像、展示名、公司、职位、行业、业务介绍、网址、电话、邮箱、微信号；编辑、公开预览、逐字段授权 |
| 推广素材 | 复制链接、二维码、海报预览与下载、当前规则及规则变更提醒 |
| 推广收益 | 有效访问次数、归因订单、已支付订单、净成交额、待结算、可提现、处理中、已到账及待抵扣 |
| 提现记录 | 收款信息、申请、税费确认、审核状态、微信确认收款、失败原因、结算凭证 |

资料可以主动从常用资料或参会名片复制，复制后独立保存。管理员可以隐藏或要求修改，不能代替用户扩大公开范围。选择私密资料仍可推广和取得佣金。

提供 1080×1440 推广海报，使用“大会合作伙伴”文案、本站稳定推广码和大会信息。通用海报始终可用；个人海报按单独的海报字段授权生成，默认不含联系方式、订单、票证、余额和收款信息。下载前显示实际预览，避免把“允许官网公开”等同于“允许印在海报上”。

撤回公开授权后，官网列表、详情及新的素材生成同步生效；受控头像链接失效或短期过期。已下载、截图或第三方缓存的内容无法保证撤回，用户在首次公开及下载时看到这一说明。

### 4.3 后台用户列表快速开通

用户管理为组织级页面，“合作伙伴”列必须显示目标大会。行内开通抽屉支持选择大会、继承默认规则或个人固定比例、排序和内部备注；批量操作显示人数、大会及逐项结果。

资格状态为：**待确认、有效、暂停、已关闭**。管理员开通后生成稳定推广码，伙伴首次确认条款与规则后开始接受新归因。待确认阶段可以准备资料，公开展示和计佣尚未生效。

普通停用停止新归因并隐藏公开资料，保留历史合法佣金和结算权利。异常冻结另设“暂停结算”及原因，不通过删除资格清零。重新开通沿用历史关系与计数，已接受旧版条款但新版尚未接受时执行第 5.3 节。

现有“合作申请”保留为意向收集，只有管理员完成用户匹配和开通后才形成合作关系。未注册申请人先完成注册，不通过申请手机号暗中创建可出款账户。

### 4.4 大会后台分销管理

设置五个标签：概览、合作伙伴、推广订单与佣金、提现与对账、分销设置。

- 概览按大会呈现净成交额、佣金义务、可提现、在途、已到账和异常；可筛选时间范围。
- 伙伴管理支持资格、公开预览、隐藏、排序、个人比例、接受规则记录及审计。
- 订单与佣金展示脱敏订单号、批次、归因原因、规则版本、金额基数、比例、释放日和退款调整。
- 提现与对账支持财务审核、用户确认状态、出款执行、查单、人工凭证、税务清单和权限控制的导出。
- 设置包括总开关、票种、固定或阶梯规则、归因期限、等待期、门槛、合作条款、海报和公开区块配置。

已支付订单不提供“直接改推荐人”按钮。纠错采用原佣金冲正和新佣金补记，注明证据与操作者，历史记录可追溯。

### 4.5 组织后台微信出款设置

在“系统设置 → 微信支付”增加商家转账配置：启停、绑定 AppID、批准场景、回调地址、出口 IP、批准额度、核验记录、预算及资金不足提示。凭据由现有受控配置管理；大会页面只显示能力和资金状态。

资金面板分开显示：本系统待审核金额、已批准未提交、渠道在途、本地预算占用、财务核验的运营账户可用余额和时间。人工核验余额明确标注“非实时”，不能据此承诺即时到账。

员工权限拆为资料查看、资料管理、规则管理、财务查看、提现审核与执行、财务导出。大会负责人默认不获得出款权限。涉及本人或已知关联收款人的提现，由另一名有权限人员审核；员工与普通用户使用不同身份表，不能仅比较两个 UUID 就认定已完成自审检查。

## 5. 归因、规则和佣金计算

### 5.1 推广入口与有效来源

推广链接为本站 `/r/{code}`，使用不可猜测的随机码，固定绑定组织、大会、伙伴及本站目的地。服务端验证资格和期限，不接受任意跳转网址，也不信任客户端提交的伙伴 ID、比例或余额。

首版按 30 天内最后一次有效主动访问归因。自然访问、浏览名片、无效推广码不覆盖已有合法来源；新来源跨大会时分别保存。被暂停、过期或未接受规则的来源在下单时再次检查，不因浏览器留有旧 Cookie 获得新归因。

归因上下文采用服务端签名或随机引用的第一方 Cookie，配置 HttpOnly、Secure、SameSite=Lax、主机限定及服务端到期时间。最多保留最近 8 场大会的来源，淘汰最旧项，避免 Cookie 无限增长。跨域时先跳到规范站点再建立上下文，登录和 API 按当前大会读取。

为防止隐藏页面抢来源，嵌入框架、预取和明确机器人访问不建立归因；缺少可判断导航信息的微信环境使用轻量确认页及一次性同源确认操作。报名确认页显示当前推荐来源并允许用户清除，再创建结算批次；资料私密时仅显示“合作伙伴推广链接”，不披露姓名或联系方式。归因入口与确认页不加载第三方统计，不携带个人资料。

同一浏览器登录后保留来源；跨设备、跨浏览器需重新打开链接或扫码。Cookie 不可用时明确显示“未记录推荐来源”，可再次进入推广入口完成确认，首版不使用隐蔽设备指纹兜底。

访问量采用短期去重后的次数，按链接和日期聚合，仅供运营参考，不宣称是精确独立人数。默认最多保留 7 天用于限频和去重的原始技术记录，之后只保留无个人身份的聚合统计；计佣依据始终是订单及支付事实。

### 5.2 结算批次锁定，兼容现有订单恢复

引入订单的不可变 `checkoutRevision`，用户界面仍显示原有订单，内部区分每一次有效结算条件。每个批次保存归因结果，包括明确的“无归因”及原因，保存规则、购票人判断、票种、金额和有效期快照。

| 场景 | 归因处理 |
| --- | --- |
| 首次有效下单 | 按当前合法来源创建批次并锁定 |
| 同一活动批次重试、切换 JSAPI／H5／Native、换设备继续付款 | 沿用同一批次和来源；活动批次中的幂等重试不产生新版本 |
| 旧订单超时或关闭后恢复，且旧支付尝试全部已核验为不可能再成功的终态 | 建立新批次，按本次来源、票种和规则重新锁定；即使仍用原购买意图，也不覆盖旧批次 |
| 旧支付仍在确认、关单未确定、退款或票证状态冲突 | 沿用现有订单安全门禁，禁止以恢复订单绕过确认流程 |
| 旧批次出现迟到的支付通知 | 支付尝试绑定原批次，禁止把资金归给新批次；交易事实冲突进入现有支付核对及财务异常处理 |
| 成功付款、之后参会人认领或修改名片 | 来源与比例不变 |
| 上线前既有订单 | 标记历史范围，不自动追溯分佣；受控补记需单独证据 |

创建或恢复批次与订单变更在同一个数据库事务内完成；支付尝试创建时引用该批次。上次“无归因”可在安全恢复的新批次中变为有归因，已在有效期内的批次不能被后续点击改写。

资格暂停前已形成的有效批次，在该批次原有付款期限内按快照计佣；新批次须重新通过资格检查。单纯资格停用不回收已形成的合法权益，疑似欺诈通过独立结算暂停处理。

### 5.3 固定、阶梯和规则变更

固定比例首发建议 10%。阶梯示例为第 1 至 10 单 10%、第 11 至 30 单 12%、第 31 单起 15%，后台支持配置，示例不自动启用。个人固定比例优先于大会默认比例，票种排除规则仍然有效。

阶梯按本大会该伙伴符合计佣资格、尚未全额退款的已支付订单数计算，包含使用个人比例的适用订单。资格重开和规则换版不清零。每订单最多贡献一次计数，部分退款保留计数，全额退款撤销一次计数，历史已确定比例保持原样。

**分配档位的时点为财务消费者首次成功处理该笔支付的事务**，同一伙伴加锁，分配唯一顺序并持久化。它不使用浏览器时间或假设消息一定按付款时间到达；后台展示支付时间及计佣时间。已保存的顺序在重试、故障恢复中沿用，禁止重新排序改写历史档位。某笔支付处理前已经全额退款时直接记录零佣金原因，不增加有效计数。

规则与个人覆盖采用不可变版本，在结算批次创建时绑定。首次开通和经济条件变更都保存用户接受的条款全文哈希、规则快照、身份和时间。降低比例、调整阶梯、延长等待期等变更新增版本，提前展示；默认过渡期为发布后 7 天。用户主动接受后，新批次使用新版本；过渡期内未接受的用户继续按已接受旧版新建批次；过渡期结束仍未接受时暂停新归因。历史批次和已产生收益继续按原版结算。

若必须即时停止推广，管理员可暂停新归因；该操作不会自动改写旧合同。新票种在适用清单中默认不参与，须发布规则后加入。比例范围为 0 至 100%，阶梯阈值递增、无重叠，首档从第 1 单开始。

### 5.4 金额口径与计算

本期支持人民币。单笔金额使用整数分，比例用万分位整数，汇总使用足够容量的整数类型；大额接口以可安全解析的形式返回，前端不以浮点运算裁定金额。

计佣基数为：**核验成功的订单成交总额 − 累计核验成功的退款总额**。对应现有微信交易核验的 `amount.total` 口径；微信 `payer_total` 表示付款人实际承担金额，商户银行净入账还可能扣除手续费，这两者单独保留，均不替换计佣基数。

例如订单成交 1,000 元，用户使用微信侧优惠后现金支付 900 元，在本方案默认规则下仍按 1,000 元计算，10% 佣金为 100 元。若站内优惠已使订单成交价变为 900 元，则佣金为 90 元。将来增加新的补贴、组合支付或多币种时，必须扩展金额映射和验收后才能参与计佣。

当前应得佣金为 `floor(净成交金额分 × 已锁定比例万分位 / 10000)`，下限为零。每次部分退款根据累计退款重新计算应得佣金，用与上次结果的差额冲正，避免重复舍入。

20 笔每笔 1,000 元、无退款的示例阶梯订单：前 10 笔计 1,000 元佣金，后 10 笔计 1,200 元，共 2,200 元。1,000 元订单按 10% 计佣后累计退款 400 元，应得佣金降至 60 元，合计冲正 40 元。

自购以普通用户购票身份为确定规则；同一伙伴为他人代购也排除。系统可提示已知同手机号、同一已绑定收款身份等关联风险，未建立关联的多账号由财务审核，不承诺识别全部自然人关系。免费票、模拟支付、测试单及历史订单默认不计佣。

### 5.5 等待期、退款和大会生命周期

默认可结佣时间为 `max(支付成功时间 + 7 天, 订单退款截止时间 + 24 小时)`。读取订单退款政策快照，按既有规则确定截止时间；无法可靠解析的历史或异常政策先冻结核对，不静默套用当前大会配置。明确无退款窗口的适用订单按支付满 7 天处理。

退款申请未结案、退款执行中、支付结果不明、外部退款待核对、票证履约异常或争议标记存在时，相关佣金保持冻结。退款请求被驳回或撤回后仍需确认没有在途退款，再重新判断资格。微信退回非原付款方等异常结果不能仅凭状态文字“成功”减少应付或释放冻结，沿用现有退款服务的核验结果。

大会可选“大会结束后 7 天”作为更保守的结佣方案，同样按版本执行。大会取消时停止新推广、暂停尚未提交的出款，按退款事实清算；已提交的出款继续查单并处理追偿。大会归档后保留伙伴财务入口和管理端对账，直到义务结清。

## 6. 提现、人工结算与税费

### 6.1 账本与申请

佣金记录“待结算、可提现、提现占用、已结清、已冲正、待处理追偿”等分类。账本采用追加流水，同一业务事件对应唯一分录组，组内转入与转出守恒；汇总余额可重建，禁止直接改余额。

提现申请以税前金额计，默认 10 元起。每个伙伴每场大会最多一笔活动申请；跨大会不合并提现，组织财务按同一收款人汇总核税。申请按释放时间及稳定 ID 分配佣金，每一分都能追溯到订单；并发申请在同一事务里检查并占用金额，不能超额。

### 6.2 从申请到到账

| 状态 | 操作与资金处理 |
| --- | --- |
| 待审核 | 保存申请、来源分配及收款信息版本，占用税前佣金；用户可取消 |
| 待用户确认 | 财务核定税费、实付和渠道，保存已审核的不可变结算明细；用户确认或取消 |
| 待出款 | 用户已确认，等待财务执行和资金条件；未产生执行记录前可申请取消 |
| 执行中 | 已通过最后复核并持久化执行记录；按渠道展示人工处理中、待微信确认、转账处理中或正在核实；保持占用 |
| 已到账 | 有真实付款成功依据；税前义务按实付与扣缴分项结清，留存凭证 |
| 已拒绝／已取消／确定失败 | 无实际出款或渠道已确认失败、关闭；释放相应占用和未执行税费预留 |

每份结算明细保存税前额、扣缴额、其他费用为 0、实付额、币种、渠道、收款人版本、规则依据及哈希。用户明确确认后才能执行，税前额必须等于扣缴额与实付额之和。实付额须为正且符合渠道最低额度；零实付或特殊税务清算转财务专门结清，不伪造微信转账。

审核或收款信息发生变化时生成新明细，原审批与用户确认失效。默认明细 24 小时未确认可过期取消；执行中记录不适用本地自动过期。确定失败后的重新申请保留旧记录和关联，禁止把失败行直接改成成功。

提交申请、确认结算明细及修改收款人都使用用途独立的短信二次验证，验证码验证凭据有效期最多 10 分钟、单次消费并绑定本次操作内容。活动出款期间不能更换收款人；完成更换后新出款等待 24 小时并重新审核，查询与原单核对继续可用。

### 6.3 人工结算必须形成执行闭环

第一阶段支持财务通过主办方银行账户完成线下付款，再核验登记。个人提供本人收款账户；对公合作方提供合同主体一致的企业账户。账户、开户名及必要凭证加密保存，只给财务和本人授权访问；第一阶段不要求先绑定微信。

流程为：申请 → 财务审核 → 用户确认明细 → 财务点击“开始人工付款” → 系统封存执行记录及金额 → 财务线下支付 → 核对银行流水 → 登记成功或确定未付款。

执行中不得再开微信或第二笔人工付款。财务离开页面、上传截图失败或暂时没有凭证时显示“正在核实”，保持占用。只有核验真实银行流水的金额、收款人、付款账户和银行交易号一致后才结清；截图上传本身不能证明到账。付款账户与银行交易号建立唯一约束，重复登记不重复记账。

微信原单结果不明时也不能转人工支付。切换渠道必须先证明原执行确定未付款，并生成新的审核明细和用户确认。系统不能阻止人员绕过系统另行转账，因此财务操作规范须要求每次线下付款先取得唯一执行记录，每日对账发现系统外出款。

### 6.4 税务口径与已出款后退款

个人推广佣金的所得分类、凭证及申报责任由主办方财务结合合同确定。相同项目的连续性劳务报酬可能涉及按月合并口径，不能让拆分提现自动重复使用减除额度；系统按付款主体、收款主体、税期和财务认定项目汇总，并保存核定依据。企业收款按其合同和发票要求办理。[国家税务总局：扣缴申报管理办法](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5194838/content.html)、[劳务报酬按次确定口径](https://www.chinatax.gov.cn/n810219/n810744/n3752930/n3752974/c3963396/content.html)

首版由财务核定税额，不在主体关系尚未确定时硬编码单一税率。账务区分税费预留、实际扣缴、已申报缴纳及后续调整，保存凭证和时间；用户看到税前、扣缴和净到账。默认在实际出款成功后确认扣缴义务，支付失败时释放尚未执行的税费预留。

已出款后退款先记录应得佣金的负向调整。若没有税务调整，可按条款抵扣后续可提现收益；不足部分保留待追偿，无法从用户微信零钱自动扣回。存在已扣税款时，财务先核定与本次退款对应的可退、可抵或不可调整税额，再确定实际需追偿金额。

示例：税前佣金 100 元，净付 80 元，扣税 20 元，后续佣金需冲正 40 元。系统记录 40 元经济调整；若财务确认其中 8 元税款可依法调整，现金追偿按 32 元执行并记录 8 元税额调整。税务结论未定时将其列为待核定追偿并暂停新出款，禁止同时全额抵扣 40 元再重复处理 8 元。该例只解释账务分离，税额及可调整结果不代表通用税法结论。

合作结束时，低于 10 元的余额允许财务办理最终结清；仍须完成身份、税务和付款核对。不得通过提高提现门槛或关闭账号使已有收益自动失效。

## 7. 微信支付与运营资金

### 7.1 “沉淀资金”如何安排

需要准备商户运营账户的实际出款余额。微信商家转账由运营账户出资，官方提供扫码、网银和转账充值方式；TokEMS 佣金账本与售票收入不会自动成为运营账户余额。[微信官方：充值](https://pay.wechatpay.cn/doc/v3/merchant/4013747269)

本次查阅的公开接入及充值资料没有给出对所有商户统一适用的固定保证金或固定沉淀比例。主办方应按计划净出款、已占用在途款及业务缓冲安排资金，具体审核和限制以实际商户协议与平台结果为准。比如计划净付 10,000 元、内部按 20% 缓冲预算 12,000 元，这只是主办方资金安排示例。退款资金按现有退款渠道另行安排。

```text
购票支付 → 主办方收款账户 → 按商户约定结算
                                ↓
                      财务安排运营账户充值
                                ↓
佣金账本 → 审核及用户确认 → 微信商家转账 → 合作伙伴微信零钱
   ↑                            ↓
支付与退款事实          结果通知、主动查单、资金账单
   └──────────── 核对账务 ────────────┘
```

同一商户服务多场大会时，共享实际资金和渠道额度。调度按商户号协调，占用包含已提交且未明确结束的金额；本地额度预算按中国标准时间自然日统计已成功及保守占用，不因换大会重复获得额度。真实商户还可能有系统外付款，资金面板必须呈现核验时间，并以渠道结果及对账纠正预算。

### 7.2 开通条件和接入模式

商家转账是独立产品权限。官方当前要求良好信用记录和真实场景资料，暂不支持小微商户；已有收款能力不能证明转账已经获批。[微信官方：开发接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4013740645)

拟按“佣金报酬”场景 `1005` 申请，真实填报岗位类型和报酬说明，例如大会推广合作及对应大会佣金。场景、具体上限、用户每日限额、IP 和域名配置均依据该商户批准结果，不把文档示例值当作所有商户通用额度。[微信官方：佣金报酬](https://pay.wechatpay.cn/doc/v3/merchant/4013774590)

使用新版 `/v3/fund-app/mch-transfer/transfer-bills` 及逐笔用户确认模式。授权免确认作为后续扩展。该模式适合本项目累计佣金、等待期、用户申请和独立审核的结算节奏。[微信官方：开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012715211)

微信分账适用于将交易资金按分账关系分配，本期保留现有售票链路，通过内部计佣和商家转账出款。将来若引入多个交易收款主体，再评估分账及平台支付模式。[微信官方：分账产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4012067962)

### 7.3 微信收款身份和确认页面

使用商户绑定 AppID 的独立 OAuth，取得伙伴在该 AppID 下的 OpenID。绑定记录包含组织、客户、商户、AppID、加密 OpenID、收款实名、版本和授权时间。不能从手填微信号、手机号或购票人的 OpenID 推导收款身份；OpenID 也不能跨 AppID 当成相同标识。

通过近期手机号验证和微信授权完成账号关联，使用服务端一次性 state、固定回调及防重放机制。桌面显示“使用微信扫码继续”，短期接续码仅传递受控流程，微信端必须重新验证对应用户，不能仅凭二维码修改收款人和金额。收款绑定不跨组织自动共享，同一组织与 AppID 下的重复收款身份需核对，禁止多个普通账号直接重复绑定同一身份。

独立 `/payout/` 页面承担微信绑定与确认，纳入敏感路由和现有跨域接续体系。实际 AppID 的 OAuth 权限、授权域名、JS 安全域名及商户绑定需核验。收款实名与公开展示名分开；调用时按微信要求加密姓名。官方要求转账金额达到 2,000 元时必须提供姓名，本方案微信提现统一填写姓名并通过渠道校验，不把 OAuth 成功视为实名已经核验。[微信官方：发起转账](https://pay.wechatpay.cn/doc/v3/merchant/4012716434)

微信内通过 `requestMerchantTransfer` 和对应 `package_info` 调起确认；前端调用成功只更新交互状态，到账仍由服务端核验。[微信官方：JSAPI 调起确认](https://pay.wechatpay.cn/doc/v3/merchant/4012716430)

### 7.4 状态、查单与失败恢复

- 发起前持久化唯一执行记录及商户单号。网络调用在数据库事务外完成，使用有版本的租约；旧任务回写不得覆盖新状态。
- HTTP 成功、接口受理或用户界面提示都不能直接记为到账。`WAIT_USER_CONFIRM`、处理中、请求超时及未知错误持续占用金额。
- 请求超时或系统错误先查原单，依照官方错误分类和重试期使用原单处理。超过原单重试期也须查明实际结果，再决定是否创建新执行，禁止换单号盲目重发。
- 用户确认窗口为 24 小时；实际关单可能晚于 24 小时。本地计时器只触发查单，不据此释放金额。撤销请求受理也须等到明确终态。
- 仅核验 `SUCCESS` 后结清，核验 `FAIL`、`CANCELLED` 后才释放原执行占用。冲突的终态结果进入人工对账，已成功记录不被较旧通知降级。
- 主动查询覆盖最近 30 天转账单，长期异常转资金账单和商户平台核对。查询返回不存在、查询过期或没有通知均不能单独证明从未付款。

以上按新版确认模式执行。[微信官方：开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012715211)、[常见问题](https://pay.wechatpay.cn/doc/v3/merchant/4013778940)

通知处理保存原始请求体用于验签，核验平台公钥或证书、签名时间与重放条件，解密后核对商户、商户单号、渠道单号、OpenID、金额及本地执行绑定。通知不保证含 AppID，AppID 关联以执行快照为准。验签并完成持久化收件后在 5 秒内返回成功，资金账本异步幂等消费；非法签名与探测签名拒绝。通知丢失由主动查单补齐。[微信官方：转账结果通知](https://pay.wechatpay.cn/doc/v3/merchant/4012712115)

资金不足时进入待补资金或渠道原单核实状态，不能释放未知出款，也不能自动拆单绕过上限。关闭新出款开关只停止新指令，回调、查单、撤销及对账继续运行。

截至本轮核验，官方 FAQ 说明商家转账无手续费；用户收到微信零钱后再提现到银行卡属于独立操作。系统默认自身服务费为 0，平台费用变化通过新规则明示后处理。[微信官方：常见问题](https://pay.wechatpay.cn/doc/v3/merchant/4013778940)

## 8. 工程架构与一致性

### 8.1 支付出票、计佣、出款分别处理

```text
官网与个人中心 → PartnerModule：资格、名片、推广来源
下单事务       → 订单与不可变结算批次 → 支付尝试绑定批次
支付确认事务   → 支付事实 + 电子票 + PaymentSucceeded
退款确认事务   → 退款事实 + RefundSucceeded
                                      ↓
                        独立财务 Inbox 与事实核对
                                      ↓
                          佣金、冲正、释放、账本
                                      ↓
后台与个人中心 → PayoutModule：审核、确认、金额占用
                                      ↓
                       人工执行 / WeChatTransferService
                                      ↓
                        通知 Inbox、查单、资金对账
原有 Worker    → 通知、导出等任务，使用独立完成记录
```

支付出票事务继续保证原有可靠性，不调用计佣计算、海报或出款服务。财务消费者故障时购票和出票照常处理，收益页提示“正在同步”，新出款按积压范围暂停。订单与归因批次的一致性仍由下单事务保证，不能靠延迟关联猜测来源。

财务维护由现有 API 定时任务及 PostgreSQL 租约承载，不新增独立部署服务。财务收件箱以消费者与事件 ID 去重，与现有通知队列独立；不以 Outbox 的 `publishedAt` 或通知发送结果作为财务完成标志。扫描采用可重叠扫描及未消费事件核对，不能仅依赖时间游标或 UUID 排序，否则可能漏掉延迟提交事务。

事件清理必须检查财务消费完成与留存条件，未处理的资金事件不能按普通通知的过期时间删除。真实计佣、申请、审核和执行要求数据库持久化可用，不进入内存演示降级；数据库或关键凭据不可用时停止相应写操作，不能模拟记账成功。Redis 只承载短期流程和去重，不保存唯一账务事实。

财务消费在自己的事务中读取可信订单、支付、累计成功退款及异常状态，计算和提交账本与完成标记。退款先到、支付后到时按当前累计事实落账；不盲信通知中的 `fullRefund` 或通知接收人字段。重试失败保留持久化错误与受影响伙伴，达到阈值后告警，不能丢弃事件。

### 8.2 退款与出款的提交边界

**出款提交点**为最后核对完成后，数据库成功封存不可变执行记录并转入执行中。提交点之前发现退款或新的义务，取消或退回尚未执行的结算明细；提交点之后视为在途出款，先核实原单或撤销结果，再决定释放、冲正或追偿。

最后核对必须检查：来源订单当前支付与退款事实、伙伴全部已知未处理负向调整、退款申请与异常、规则等待期、结算暂停、身份与确认版本、活动执行、资金预算及商户配置。查询数据库事实，不能只相信前端余额或落后于退款的佣金汇总。历史合法佣金的结算不要求新推广资格仍然有效；任何已知的未处理负向事实立即阻止相关出款，不等待告警阈值到期。

新增组织级短事务结算协调锁，所有会改变结算资格的退款申请、确认、异常登记及新出款封存都使用它；这些入口只协调事实和提交边界，不执行计佣算法。既有微信配置锁仍先于订单锁。新增流程统一按以下顺序获取需要的锁：组织微信配置 → 组织结算协调 → 商户预算 → 涉及订单按 ID 排序 → 伙伴账本 → 提现与执行记录。不允许持有伙伴行后反向等待订单；数据库死锁和序列化冲突沿用现有有界重试机制。

财务消费者修改账本也遵循该顺序。候选佣金先只读选择，加锁后重新核对；集合或版本改变则重试。微信网络请求、银行操作、素材处理和通知全部在事务外进行，避免持锁等待外部系统。

针对暂停结算、账户封禁和资料注销等状态变更，同样在提交点使用一致的伙伴状态版本校验与锁，确保并发冻结能得到确定处理结果。已提交后的新退款属于追偿流程，不能假设资金尚未实际发出就允许第二次付款。

存在活动出款时，商户号、AppID 和收款绑定禁止直接替换。签名及加密凭据按版本轮换，为存量通知、查单及凭证解密保留所需的旧版本；配置修改继续通过现有组织级微信配置锁与退款义务检查，不因新增转账绕过原有保护。

### 8.4 API、授权和数据保护

| 接口面 | 路径方向与职责 |
| --- | --- |
| 公开展示 | `/api/v1/public/events/{eventId}/partners` 和详情；仅序列化已授权公开字段 |
| 推广入口 | Web `/r/{code}` 及必要同源确认；下单 API 服务端读取来源 |
| 伙伴个人中心 | `/api/v1/customer/partnerships/{eventId}` 下的资料、接受规则、素材、佣金与提现 |
| 提现确认 | 提交、确认结算明细、取消及详情；幂等键加请求内容哈希，校验本人及明细版本 |
| 微信绑定 | 独立绑定发起、固定 OAuth 回调、本人确认、撤销及短期接续 |
| 大会后台 | `/api/v1/admin/events/{eventId}/distribution` 下的规则、伙伴、佣金、提现和对账 |
| 转账通知 | 独立 HTTPS 通知路由，组织只是定位信息，实际以验签和商户绑定验证身份 |

个人写操作复用 Customer 会话、CSRF、限频和幂等；资料编辑带版本号。独立财务权限控制导出、审核与执行，规则变更、资金调整、隐藏、凭证下载都记录审计。AI 管理目录可以暴露已批准的只读或资料管理能力，本期不开放自动审批、自动出款或修改实付的工具权限。

伙伴只能看到脱敏订单标识、票种、金额、时间和状态，无权访问购票人的姓名、手机号、参会名片或支付凭据。财务 CSV 导出防公式注入；头像验证格式、大小、所属关系并标准化处理，简介采用纯文本或受限渲染。复制参会头像建立独立受控媒体关联，清理任务检查两类引用。

私密联系方式、银行账号、OpenID、实名和税务凭证加密存储，不写进日志、公开响应、链接、海报和规范快照。公开页使用明确的公开字段投影和可撤回缓存策略；编辑、收益、授权、接续和出款响应禁止公共缓存。财务数据保存期限由主办方按适用要求明确配置，暂未确定前不启用自动删除；技术访问数据按第 5.1 节短期保存。

用户注销前关闭新推广并下架公开资料，取消尚未执行申请；存在未结收益、追偿、税务未结事项或在途出款时转入结清流程，不能直接物理删除关系。最终结清后可解除登录身份并保留必要账务主体快照。普通用户、大会和组织的删除流程都禁止级联清除财务表；同手机号重注册不自动继承旧余额和微信绑定。

## 10. 分阶段交付与外部条件

### 阶段一：伙伴、推广、计佣、人工结算

实施顺序：增量模型与契约 → 资格与条款 → 资料及首页 → 来源与结算批次 → 财务消费、规则及退款 → 审核、确认及人工执行 → 对账、规范保护、回归与共享预览。

交付固定及订单数阶梯、个人比例、独立资料、链接海报、财务账本、税费明细、人工结算全流程。微信渠道明确显示尚未启用，可独立完成业务结算。真实推广启用前需要发布条款和比例，真实人工付款前也需要核定主体、税务与财务执行人。

### 阶段二：微信出款

实施顺序：商户及场景准备 → 收款绑定与微信页面 → 请求签名、提交及查询 → 通知与撤销 → 额度、资金及回单对账 → 真机小额验证 → 小范围试运行 → 启用。

两阶段整体粗估 16 至 24 个工程人日，覆盖开发、事务与并发验证、前后台联调和发布保护；不含商户审核、财税口径确认等待及未知外部整改。这是容量估计，实施拆解后按实际代码差异校准，不作为交付日期承诺。

| 外部事项 | 负责人 | 阻塞范围 |
| --- | --- | --- |
| 确定合作合同、佣金与退款追偿条款 | 主办方业务及财务 | 生产新推广启用 |
| 个人及企业结算、税期与项目口径、凭证保存规则 | 主办方财务 | 对应主体的真实人工与微信付款 |
| 商户主体、商家转账产品权限、佣金场景和批准额度 | 商户管理员 | 微信渠道启用 |
| AppID、OAuth 权限、商户绑定、授权及 JS 域名、HTTPS 通知与安全 IP | 商户管理员及工程 | 微信真机联调和启用 |
| 运营账户资金、财务预算、执行与核验人员 | 主办方财务 | 对应真实出款 |

公开规则已核验；本轮未登录真实微信商户平台，未验证产品审批、余额、实际限额或转账成功。这些条件不阻塞获批后的离线开发和模拟测试，系统能力上线与真实出款开关分别管理。
