## 1. 推荐决策

在现有普通用户账号上增加**大会级“合作伙伴”资格**，由管理员开通。合作伙伴可以维护独立公开名片、生成推广链接与海报、查看推广订单和佣金、申请提现。大会后台增加“分销管理”，组织后台的微信支付设置增加“商家转账”配置。

采用**一级推广、服务端订单归因、版本化佣金规则、不可变佣金流水、审核后出款**。继续使用 Nuxt、Vue、NestJS、PostgreSQL 和现有异步基础设施，新增独立领域模块，新增部署服务数为 0。

微信出款采用普通商户新版“商家转账”的**用户确认收款模式**。首版保留人工结算能力；商户权限审核或微信服务暂不可用时，资料、推广、计佣和财务核对可以继续工作。

本方案的关键前提是：大会主办方作为售票主体向自己的推广合作方支付佣金，现有部署采用普通商户直连接入。若业务变成多个独立商户共同收款、平台代收代付，需要重新评估平台型支付方案。当前商户的真实主体类型、转账权限及额度，本轮未登录商户平台核验。

### 代码核验结论

- `customer_users` 和 `customer_profiles` 是普通用户体系；`users`、`memberships` 承载运营员工身份。合作伙伴关联普通用户，不获得员工后台权限。
- `attendee_showcase_profiles` 强制关联报名，现有展示服务会检查订单、报名与票的有效性。合作伙伴可能未购票，因此不能直接用参会名片行承载资格。
- 订单已经区分购票人 `purchaserCustomerUserId` 与参会人，且支持按配置代他人购买。分销归属和自购判断以购票人为主要依据；后续参会人认领不改变佣金归属。
- `ConferenceRepository.confirmPayment` 在事务内写入支付事实、电子票及 `PaymentSucceeded`；退款服务在核验退款后写入 `RefundSucceeded`。这些是可信的计佣和冲正接入位置。
- 现有微信 OAuth 会话保存于 Redis，约 30 分钟有效，且绑定订单。它无法承担长期的合作伙伴收款账户绑定。
- 当前规范快照采用 `structured` 首页；退款配置为启用、窗口 7 天；额外购买默认关闭。以上为仓库快照事实，本轮未将其认定为生产实时配置。
- 已有“合作申请”收集合作意向。申请记录不自动生成佣金资格，仍由管理员在用户身份核对后开通。

## 3. 五个产品入口

### 3.1 大会首页：合作伙伴

- 新增 `home.partners` 区块，推荐放在现有合作机构区域附近，标题“大会合作伙伴”；导航增加“合作伙伴”锚点。
- 展示头像、展示名、公司、职位、简介摘要，点击进入独立介绍页。列表不直接输出联系方式。
- 首页最多展示 12 人，提供“查看全部”；目录每页 24 人，默认按管理员排序值、开通时间和稳定 ID 排序，不按佣金排名。
- 展示条件同时满足：大会允许展示、合作资格有效、用户同意公开、资料达到最低完整度、管理员未隐藏、普通用户账号正常。
- 最低完整度为展示名及一句介绍；头像可使用通用图形。用户隐藏姓名时，允许使用单独的公开展示名。
- 没有可公开伙伴时隐藏首页区块，后台保留配置入口。
- 已有合作机构 Logo 墙继续按机构配置维护，报名会员按报名资格维护。
- 公开伙伴页提供“通过我报名”按钮。普通浏览目录和介绍页不自动覆盖访客已有推荐来源；访客主动点击报名按钮后才激活该伙伴的推广链接。
- 当前结构化首页完整支持该区块。导入型 HTML 首页可配置到合作伙伴目录的普通链接，本轮不扩展 HTML 编译器的实时组件体系。

拟新增公开页面：`/partners?event={eventSlug}`、`/partners/{publicSlug}?event={eventSlug}`。同一页面的 canonical 不包含推广参数。

### 3.2 个人中心：合作伙伴中心

个人中心依据合作关系展示“合作伙伴中心”，即使没有任何购票记录也能进入。用户参加多场大会时可切换大会，各场资格、规则和收益独立。

中心包含四个标签：

| 标签 | 功能 |
| --- | --- |
| 我的资料 | 头像、展示名、公司、职位、行业、业务介绍、网址、电话、邮箱、微信号；公开预览与编辑 |
| 推广素材 | 复制推广链接、查看二维码、预览并下载合作伙伴海报、查看当前佣金规则 |
| 推广收益 | 访问次数、归因订单数、已支付订单数、退款金额、待结算佣金、可提现佣金、提现处理中、累计到账 |
| 提现记录 | 收款绑定、申请金额、税前／税费／实付明细、审核进度、微信确认收款、失败原因及结算凭证 |

隐私约定：

- 总公开开关默认关闭；电话、邮箱、微信号默认不公开。管理员开通资格不会替用户同意公开。
- 用户可以从常用资料或参会名片“复制资料”，复制后分别保存。联系方式由用户主动填写或主动选择复制。
- 管理员可以隐藏资料、要求修改；不能扩大用户允许公开的字段范围。
- 推广功能与公开展示分别控制：选择私密资料仍能推广和获得佣金。
- 生成海报前明确预览哪些身份字段会出现在图片上。默认不含联系方式、账户编号、佣金金额和收款信息；使用“大会合作伙伴”身份文案，不输出参会票证身份。
- 通用推广海报始终可用；个人信息海报只使用用户明确允许用于该海报的字段。改变线上公开权限后，后续生成图片同步变化；已下载传播的图片无法撤回。

海报二维码使用本站稳定推广地址，默认进入大会首页。资料私密或被隐藏时仍可正常推广；资格暂停后停止新增归因。

### 3.3 后台用户列表：快速开通

现有用户管理是组织级页面。新增“合作伙伴”列时必须同时显示或选择目标大会，避免一个全局勾选影响所有大会。

行内“开通合作伙伴”打开轻量抽屉，字段包括：目标大会、使用大会默认规则／个人固定比例、展示排序、内部备注。支持批量开通，提交前显示人数及目标大会，每条结果可核对。

用户详情增加各大会合作资格、公开状态、规则和收益摘要。开通、停用、重新开通及个人比例变更均记录操作者和原因。

开通后生成稳定推广码。用户首次进入伙伴中心确认合作条款与佣金规则后，推广归因生效；无需主办方再次审批。

资格状态为：待确认、有效、暂停、已关闭。普通“停用分销”停止新订单归因并隐藏公开资料；历史合法佣金、已申请提现和账务记录继续保留。发现异常时，通过单独的“暂停结算”及原因冻结出款，避免误把账号开关当作清零操作。

### 3.4 大会后台：分销管理

新增大会级主菜单“分销管理”，分成五个标签：

1. **概览**：推广订单、净成交额、应付佣金、可提现、提现处理中、累计到账、待处理异常。
2. **合作伙伴**：检索、开通、停用、资料预览、隐藏、排序、个人佣金覆盖和详情。
3. **推广订单与佣金**：订单归因、规则版本、比例、计佣基数、冻结到期日、退款调整和审计轨迹。
4. **提现与对账**：申请、审核、税费核对、微信出款、人工结算凭证、失败查单、差异处理和 CSV 导出。
5. **分销设置**：总开关、适用票种、固定／阶梯规则、归因期限、结算等待期、提现门槛、合作条款和海报文案。

后台正常业务操作采用明确按钮和原因输入。已经支付成功的订单不提供直接修改推荐人的操作；确需纠错时，财务以冲正和补记完成，原记录保留。

### 3.5 组织后台：微信出款配置

在现有“系统设置 → 微信支付”中增加“商家转账”分区，集中管理组织商户凭据和出款能力。大会页显示可用状态和分销规则，不复制商户密钥。

包括：转账开关、普通商户模式、AppID 绑定、已批准转账场景、出款 IP 配置提示、回调地址、渠道限额、配置核验记录、资金不足告警、停止新出款开关。

资金面板展示本系统待审核、待出款和处理中金额。首版运营账户余额由财务在微信商户平台核对，系统显示核对金额与时间并标明“人工核验，非实时余额”；不会把本系统佣金余额显示成微信可用资金。自动余额查询不作为首版依赖。

## 4. 分销与佣金的明确规则

### 4.1 一级推广与订单归属

推荐首版规则如下，均属于 TokEMS 产品建议：

| 项目 | 规则 |
| --- | --- |
| 分销层级 | 一级；伙伴获得本人直接促成订单的佣金 |
| 资格范围 | 组织 + 大会 + 普通用户；注册默认无资格 |
| 归因窗口 | 30 天；以服务端时间计算 |
| 归因方式 | 窗口内最后一次有效推广点击；自然访问不覆盖已有来源 |
| 归因锁定 | 创建订单时锁定；支付页跳转、换设备支付和支付渠道切换均沿用订单记录 |
| 订单复用 | 现有订单超时恢复或重复购买意图复用同一订单时，保留该订单首次锁定结果，包括“无归因”结果；只有新订单重新归因 |
| 佣金触发 | 服务端确认真实支付成功；页面点击、注册、待支付和模拟支付不产生可提现佣金 |
| 购票对象 | 本人购票、代购均按购票订单判断；参会人认领和名片变更不转移佣金 |
| 自购 | 合作伙伴本人作为购票人时不计佣，包括其为他人代购的订单；后台展示原因 |
| 免费与补录 | 免费票、测试单、历史订单默认不计佣；补记只通过财务受控调整 |
| 停用时间 | 停用后停止新归因；停用前已创建且有效归因的待支付订单按原规则处理，疑似欺诈另行冻结审核 |
| 跨大会 | A 大会的推广链接只对 A 大会订单生效 |

归因使用本站服务端控制的第一方机制，复用 HttpOnly 和 CSRF 安全习惯。具体入口为 `/r/{code}`：它只接受已存在的随机推广码，目的地由服务端绑定，只能跳往本站对应大会。

推广地址不携带用户手机号、OpenID、佣金比例或收款凭证。服务端产生不可猜测、可验证的访问标识，使用 HttpOnly Cookie 传递到下单 API；按大会独立保存来源。公开访问标识只用于推广效果和订单归属，无权访问账户。

未登录用户在同一浏览器内完成手机号登录可保留来源。首版不承诺跨浏览器、跨设备自动追踪；用户换设备后需重新打开推广链接或扫码。第三方平台去掉链接参数时，本站稳定 `/r/{code}` 路径仍携带来源。

点击数据做限频和短期去重，预览机器人不作为真实人数统计。访问量仅供运营参考，结佣只依据订单和支付事实。不建立长期设备指纹，也不向第三方统计提供订单身份。

### 4.2 固定比例与阶梯比例

后台支持两种大会规则：

- **固定比例**：所有适用订单使用一个百分比。首发建议值为 10%，这是待确认的商业参数。
- **阶梯比例**：按该伙伴在本大会累计有效已支付订单数分段计佣。示例为第 1–10 单 10%，第 11–30 单 12%，第 31 单起 15%。该示例用于配置与验收，不自动启用。

阶梯口径：每笔真实支付在数据库入账时，为同一伙伴加锁并分配顺序；当前订单计入该次档位。按入账顺序确定，不依赖可能延迟的浏览器事件。全额退款订单从后续档位统计中扣除；部分退款保留订单数并缩减该单计佣基数。

例如 20 笔每笔 1,000 元、无退款的有效订单，以上阶梯佣金为 10×1,000×10% + 10×1,000×12% = **2,200 元**。升档只影响对应的新订单，历史订单不统一追补到新比例。高退款率进入人工审核，防止利用退款反复冲档。

个人快速设置支持“继承大会规则”或“个人固定比例”。个人固定比例优先，适用票种排除规则始终有效。首版不同时建设按销售额阶梯、团队阶梯和多层分佣，减少结算解释成本。

规则版本在订单创建时绑定；支付时按该版本计算档位和金额。后续修改新增版本，不覆盖既有订单。个人比例覆盖也生成不可变快照。

金额全部使用整数分；比例使用万分位整数，避免浮点误差。原始佣金按计佣基数乘比例向下取整至分。

计佣基数采用**本订单核验成功的售票交易金额减累计成功退款金额**，以当前统一支付确认记录的金额口径为准，排除商户额外扣费和提现费用。现有平台级优惠、补贴若导致订单金额、支付确认金额与用户实际支付额不同，必须先建立明确的金额映射再允许该类订单结佣，不直接混用字段。

### 4.3 冻结、结算与退款

默认结算资格时间为：**支付成功后满 7 天，且订单快照约定的退款窗口结束后再经过 24 小时，两者取较晚值**。当前快照的退款窗口为 7 天，对应通常支付后第 8 天可申请提现。该等待期是产品建议，不是微信平台规定。

存在退款申请、退款处理中、支付结果不明、订单争议或风控暂停时继续冻结。退款窗口中提交的申请即使尚未完成，也不能因等待时间到期而释放佣金。

- 支付成功：创建待结算佣金。
- 等待期结束且资格复核通过：转为可提现。
- 申请提现：原子锁定申请金额，避免并发多次提现。
- 全额退款：该订单剩余应得佣金归零。
- 部分退款：根据退款后净交易金额重算该单应得佣金，再用差额冲正，避免多次部分退款的舍入累计误差。
- 已出款后退款：记录负向佣金调整，优先抵扣后续可提现收益；余额不足记录待抵扣金额，暂停新增提现并提交财务处理。
- 微信转账已成功后，系统不能承诺从个人零钱自动追回资金。追偿按合作条款和财务流程执行。

示例：1,000 元订单按 10% 计佣 100 元，后续累计退款 400 元，最终应得佣金为 60 元，冲正 40 元。冲正指向原订单和退款记录，不删除原始佣金。

退款与提现并发时按统一顺序锁定订单、伙伴账本和提现记录。尚未发往微信的提现可以取消并重新结算；已提交或结果不明的转账保持金额锁定，先完成查单／撤销，再决定释放或形成待抵扣金额。

大会取消仍可能产生已结算后的退款风险。主办方保留退款资金安排；短期结佣不能消除这项风险。确需全部大会履约后再结算时，可将大会分销的等待规则设置为大会结束后 7 天，存量规则变更须按版本与伙伴告知流程执行。

### 4.4 提现默认值

- 最低申请金额建议 10 元；余额不足 10 元且合作结束时允许财务办理最终结清。
- 申请金额为税前佣金。财务审核记录税费和实付金额，用户确认查看差异；首版平台服务费为 0。
- 每次提现人工审核，通过后进入对应出款渠道；不默认开放自动审批。
- 首版每位伙伴、每场大会最多一笔活动提现；拒绝或确定取消后释放金额。
- 申请时使用近期有效登录；微信绑定或更换收款账户要求重新验证手机号。存在活动出款时禁止切换收款人。
- 财务核定实付额超过微信当前渠道限额时，不自动拆单绕过限制；提示按批准额度调整申请或走人工结算。

## 5. 微信支付接入与资金规则

### 5.1 是否需要“沉淀资金”

需要安排**商户用于出款的运营资金**。微信商家转账从运营账户出资，官方提供扫码、网银、银行转账等充值方式。售票资金和本系统记账的佣金不会自动变成运营账户可用余额。[微信官方：充值](https://pay.wechatpay.cn/doc/v3/merchant/4013747269)

本次查阅的公开接入与充值文档未给出适用于所有商户的固定保证金或固定沉淀比例。具体商户的产品审核、额度和风险限制，以商户平台实际批准结果及协议为准。不要把“准备出款余额”表述为统一强制保证金。

推荐财务按“近期计划支付净额 + 业务缓冲”补足运营账户。例如本周计划支付 10,000 元，按内部 20% 缓冲准备 12,000 元；这只是预算示例。已被渠道锁定的在途款与账户可用余额分开核对，避免重复计入资金需求。售票退款资金按既有退款出资渠道另行管理。

资金关系：

```text
购票人 ── 微信购票支付 ──> 主办方收款账户 ── 按商户约定结算 ──> 主办方银行账户
                                                                    │
                                                         财务安排运营账户充值
                                                                    ↓
TokEMS 佣金账本 ── 审核通过的净出款指令 ──> 微信运营账户 ── 商家转账 ──> 伙伴微信零钱
       ↑                                         │
  支付／退款事实                            查单、回调、资金账单
       └──────────────── 对账与状态更新 ──────────┘
```

数据库的待结算、可提现和处理中金额代表主办方对伙伴的结算记录；真实资金仍在微信支付或银行体系内流转。

### 5.2 开通条件与场景

商家转账属于独立产品权限，已有 JSAPI／H5／Native 收款能力不能证明已经开通。官方要求良好信用记录并提交真实转账场景资料，目前暂不支持小微商户。[微信官方：开发接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4013740645)

大会推广佣金拟按“佣金报酬”申请，场景标识为 `1005`，报备内容包含“岗位类型”和“报酬说明”。描述采用真实的“大会推广合作伙伴”“某大会推广佣金”，最终以微信批准的业务场景为准。[微信官方：佣金报酬](https://pay.wechatpay.cn/doc/v3/merchant/4013774590)

新接入选择新版“商家转账”，使用 `/v3/fund-app/mch-transfer/transfer-bills`。首版采用用户逐笔确认；官方目前也支持用户授权免确认模式，后者作为明确的后续扩展，不作为首次上线依赖。[微信官方：产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4012711988)、[开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012715211)

### 5.3 收款绑定与用户体验

合作伙伴在已登录状态下，进入独立的微信收款绑定流程，通过商户绑定 AppID 的 OAuth 获取该用户 OpenID。绑定同时包含组织、普通用户、AppID、商户号与版本；不使用付款人的订单 OpenID 代替伙伴收款身份，也不从手机号码或手填微信号推导 OpenID。

微信内完成授权与收款确认；桌面及其他浏览器展示“使用微信扫码继续”。二维码携带短期一次性接续标识，需在微信页面再次验证对应账号，不能凭扫码接续标识修改收款人或提现金额。复用现有独立支付入口的跨域接续模式，新增 `/payout/` 页面及代理路径，并纳入敏感页面统计隔离。

微信要求收款账号实名认证。转账金额达到 2,000 元时须提交加密的收款人真实姓名；本方案在启用微信提现时收集并验证真实姓名，使用微信公钥加密传输。展示名和收款实名分别保存。[微信官方：发起转账](https://pay.wechatpay.cn/doc/v3/merchant/4012716434)

调用 `requestMerchantTransfer` 调起微信收款确认界面，前端回调成功仅代表界面调用结果；到账状态以服务器验签后的通知或主动查单为准。普通浏览器不能直接使用该微信内置能力。[微信官方：JSAPI 调起用户确认收款](https://pay.wechatpay.cn/doc/v3/merchant/4012716430)

提现用户状态：待审核 → 待出款／待补足资金 → 待微信确认 → 转账处理中 → 已到账；审核拒绝、已撤销、确定失败均显示原因。结果不明时显示“正在核实”，继续保留资金占用。

官方确认收款窗口通常为 24 小时；到时必须向微信核实最终关闭状态，不能仅凭本地计时器释放余额。查询接口支持最近 30 天的转账单，长期记录由本系统留存并以资金账单辅助核对。[微信官方：开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012715211)

### 5.4 税费、费用与对账

截至本次核验，微信官方 FAQ 说明商家转账无手续费；用户从微信零钱提现到银行卡属于后续独立操作，本系统不对其费用作承诺。[微信官方：常见问题](https://pay.wechatpay.cn/doc/v3/merchant/4013778940)

个人推广佣金可能涉及劳务报酬等税务处理，需要财务根据合同关系和收款主体确定。劳务报酬存在扣缴申报要求，支付产品接入不能替代税务办理。首版保存税前佣金、扣缴金额、实付金额、财务确认人及依据，并导出结算清单；税额由财务核定，不在未明确主体口径时硬编码统一税率。[国家税务总局：个人所得税扣缴申报管理办法](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5194838/content.html)

每日核对“佣金流水、提现单、微信转账单和运营资金账单”。未知状态持续保留在对账异常列表。对公合作方使用人工结算及凭证流程，本轮不增加企业银行账户自动打款接口。

### 5.5 与微信“分账”的比较

微信分账把某笔交易资金按指令分给接收方，涉及订单分账标记、资金冻结、期限及批准比例；普通商户文档描述通常在支付后 30 天内发起，默认最高分账比例为 30%。[微信官方：分账产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4012067962)

本项目需要累计佣金、退款等待期、个人申请提现、人工审核，以及独立于单笔支付的出款节奏，因此推荐“内部计佣 + 商家转账”。该方案保留现有购票收款链路，只在支付／退款确认处增加账务联动。若以后出现多方交易资金直接分配的业务，再评估分账方案及对应商户资质。

## 7. 工程架构

### 7.1 组件边界

```text
大会官网／个人中心 ──> PartnerModule ──────────────> 合作资格、名片、推广归因
运营后台 ───────────> PartnerModule / PayoutModule ─> 规则、审核、财务权限
                                                    │
既有支付确认事务 ───> CommissionService ────────────> PostgreSQL 佣金与流水
既有退款确认事务 ───> CommissionService ────────────> 冲正、冻结、待抵扣
                                                    │
API 定时维护与租约 ──> PayoutService ──> WeChatTransferService ──> 微信支付
                                          ↑                     │
                                  通知 Inbox、主动查单 <──────────┘
事务 Outbox ──> 既有 Worker ──> 通知与导出任务
```

- `PartnerService` 负责资格、资料和规则；`ReferralService` 负责推广码和订单归因；`CommissionService` 负责规则计算、释放与退款冲正；`PayoutService` 负责审核和资金占用；`WeChatTransferService` 负责微信协议。
- 计佣核心与现有支付／退款核验在同一数据库事务内提交，只做本地计算和数据库写入。事务中不请求微信、不渲染海报、不发通知。
- 合作伙伴资料、海报故障不影响购票。极少数账务事务失败允许可信支付 Inbox 重试，并触发积压告警；不能默默丢掉佣金事实。为此必须专测支付出票回归和重放修复。
- 微信转账的提交、回调恢复和查单沿用现有 API 定时维护 + 数据库租约方式，支持多实例安全运行；关闭新出款时继续回调、查单和对账。Worker 继续处理通知及导出，不直接引用 API 服务代码。
- 复用现有微信签名、验签、加密与凭据仓储。必要时抽取共用客户端，保持现有收款／退款对外接口不变，并运行原有支付测试。

### 7.2 新增持久化模型

预计新增 12 张业务表，结合现有 `audit_logs`、`outbox_events` 和 `idempotency_keys` 使用，不增加独立通用角色系统。

| 表 | 用途与主要约束 |
| --- | --- |
| `event_partner_program_versions` | 每大会不可变规则版本：固定／阶梯、票种、归因期限、结算规则、条款版本；有效版本指针保存在大会设置 |
| `event_partners` | 组织、大会、普通用户、资格、条款确认、个人比例覆盖、独立名片与逐字段授权；业务三元组唯一，保留结算暂停信息 |
| `partner_referral_links` | 随机推广码、伙伴、大会、渠道、绑定目标与启停状态；码全局唯一且不回收复用 |
| `partner_referral_metric_days` | 按大会、推广链接和日期保存访问聚合；短期去重由 Redis 完成，不保存长期设备指纹，访问统计允许小幅误差且不参与计佣 |
| `partner_order_attributions` | 每订单锁定归因结果，包括无归因结果、规则版本、创建时资格和购票人检查；订单唯一 |
| `partner_commissions` | 每订单佣金聚合：原金额、净基数、比例、档位、规则快照、释放时间；订单唯一 |
| `partner_ledger_entries` | 追加式金额流水：来源业务键、从／到资金分类、金额、原流水引用、原因；业务键唯一 |
| `partner_withdrawals` | 申请、税前额、核定税费、实付额、渠道、审核、金额锁定、结果和结算依据 |
| `partner_withdrawal_allocations` | 提现对应的佣金来源和分配金额，支持部分提现与退款并发；可追溯每一分 |
| `customer_wechat_recipients` | 组织内用户收款绑定：AppID、商户号、加密 OpenID／实名、版本和确认时间；防止同一收款身份被多个用户重复绑定 |
| `partner_transfer_attempts` | 提现的微信执行尝试、固定商户单号、渠道单号、凭据／收款版本、租约、查单时间和结果；每提现最多一个活动尝试 |
| `partner_transfer_notification_inbox` | 已验签解密通知的持久化去重和消费状态；按商户与通知标识唯一 |

规则、名片、订单与账本都使用组织／大会复合范围约束和索引。资金状态以追加流水为事实源，可重建汇总，禁止只改一个“余额”数值。

头像复用现有媒体上传和标准化处理，增加合作伙伴用途与归属检查。复制参会名片头像时建立新的受控媒体关联或派生资产，不直接绕过现有参会头像唯一绑定约束；清理任务同时检查两类引用。

流水资金分类覆盖待结算、可提现、提现占用、已结清、已冲正和待抵扣。提现扣缴税费与实付分别登记，但共同结清税前佣金；退款只能按有依据的调整记录处理，不能重复扣减。

`partner_withdrawal_allocations` 优先按释放时间、佣金 ID 消耗可提现佣金。同一笔佣金已分配金额不得超出剩余额，约束在伙伴行锁和同一事务内检查。

用户删除时先撤销推广资格、下架资料、取消未执行申请；活动出款未到终态前阻止物理删除。账务关系以必要快照保留，用户身份按最小化原则解除或去标识化，禁止级联删除佣金和出款历史。相同手机号重新注册不自动继承余额或收款绑定。

### 7.3 API 与权限接口

以下均为 `/api/v1` 下拟新增的接口面：

| 接口组 | 路径与职责 |
| --- | --- |
| 公开目录 | `GET /public/events/{eventId}/partners`、`GET /public/partners/{publicSlug}`；仅返回授权后的公开字段 |
| 推广接入 | Web `GET /r/{code}` 经同源服务器解析推广码、记录访问并跳转；订单接口由服务器读取签名归因上下文 |
| 我的伙伴资格 | `GET /customer/partnerships`、`GET /customer/partnerships/{eventId}`、`POST /customer/partnerships/{eventId}/accept` |

所有客户写操作使用现有 Customer 会话、CSRF、幂等键；资料修改使用版本号。资金与资格仅由服务端认定，提交体中的比例、用户 ID 或余额不作为可信事实。

新增员工权限：`event.partner.read`、`event.partner.manage`、`event.partner.rules.manage`、`event.partner.finance.read`、`event.partner.payout.manage`、`event.partner.finance.export`。组织管理员拥有全量权限；大会负责人默认拥有资料管理与查看权限，财务出款权限显式分配。个人中心权限由本人合作关系计算。

批量开通还需现有 `customer.read`；更改商户凭据沿用组织级支付设置权限。用户手机号、OpenID、税务凭证不进入公开响应、海报、普通佣金列表或公开审计摘要。合作伙伴看到脱敏订单标识、票种、金额和状态，不获得购买者联系方式。

现有 AI 管理接口需更新路由目录和契约校验；本次不赋予 AI 自动审批、自动出款或修改财务实付金额的权限。

### 7.4 资金一致性与故障恢复

- 订单、支付、退款和提现按稳定业务键去重；重复回调不重复产生佣金或到账记录。
- 每次出款先持久化尝试，再调用微信。请求超时、未知错误、回调乱序都先查原单，禁止换商户单号盲目重发。
- 只有明确的成功、失败或撤销终态才结清或释放相应占用；前端提示、本地超时、HTTP 200 均不能代替资金事实。
- 微信请求不持有数据库长事务；用带版本的租约防止旧任务回写覆盖新状态。
- 原转账结果不明时，禁止把同一提现切换成人工付款。确认旧单失败／撤销后，记录渠道变更原因才可执行备用结算。
- 一个商户下多大会共享实际出资和限额，出款调度按商户号串行占用／限速，同时按大会记账；避免各大会误认为独享全部额度。
- 有活动出款时禁止直接改商户号、AppID、收款绑定或删除所需旧密钥版本；凭据轮换必须保留足以处理存量单的旧版本。
- Redis 或微信异常时暂停新微信授权／出款，保留账本查询和人工处理入口。Redis 不保存唯一账务事实。
- 对账发现渠道已成功而本地未记账，执行幂等补记；发现本地已记账而渠道不一致，进入异常审核，不自动再付。

### 7.5 页面发布、统计与规范快照

合作伙伴首页区块、文案、海报通用样式和非个人默认设置进入规范模板；真实伙伴资料、推广码、个人比例、规则历史对应的交易事实、收益、税务和微信绑定全部属于运行数据。

规范同步时只更新允许同步的展示配置和版本化默认设置。不能覆盖已经生效的伙伴合同、订单计佣快照、出款状态或生产业务计数。分销启用、出款启用及财务额度作为运行开关保留在环境对应的受控配置中，复制大会模板后默认关闭。

规范快照只序列化默认规则的业务内容，省略本地规则表 ID；同步目标环境时按内容创建或复用新规则版本，已有订单引用保持原样。该处理需同步补齐导出、校验、种子和生产保护测试。

`/partners` 为公开页面；`/account`、`/payout`、`/pay`、后台和 API 为敏感页面；`/r` 采用无第三方脚本的同源跳转。同步更新前后端路径分类、反向代理、整页导航边界及真实 Head 验收。特别防止 `/partners`、`/payout`、`/r` 被现有单段大会 slug 路由误判。

推广记录由自有 API 完成。个人收益、提现页面不加载外部分销 SDK 或网站统计脚本。关闭公开资料后，列表、详情、头像访问和后续海报立即按新授权返回；公开资料响应使用不缓存或强制重新验证策略，不让 CDN 长期保存私密字段。

## 8. 实施边界、顺序与工作量

预计涉及超过 8 个文件，约 30–45 个源代码、配置和测试文件，另含数据库迁移与规范快照。这是跨前台、后台、交易、资金和运维的功能升级。

### 阶段一：合作伙伴、计佣与人工结算

交付完整五入口中的伙伴资料、公开展示、快速开通、分销后台和资金台账；包含链接归因、固定／阶梯规则、退款冲正、提现申请、财务审核及人工结算凭证登记。微信渠道显示“尚未启用”，人工支付由财务在线下完成并登记实际凭证。可独立上线并完成业务结算。

实施顺序：增量表与契约 → 大会伙伴权限与规则 → 订单归因与佣金／退款事务 → 资料和海报复用 → 前后台入口 → 提现审核与人工结算 → 验收与规范快照。

### 阶段二：微信自助提现

交付独立收款绑定、跨浏览器接续页、商家转账配置、审核后出款、用户确认、查单／撤销、资金账单对账和发布保护扩展。通过真实商户开通与小额验收后启用，阶段一的资料、链接及账本无需迁移重建。

实施顺序：共用微信协议能力整理 → 独立收款绑定 → 转账尝试／通知 Inbox → 出款维护和对账 → 收款确认页面及支付入口代理 → 异常与资金验收 → 受控启用。

粗略工作量为 13–20 个工程人日，阶段一约 7–10 人日，阶段二约 6–10 人日；包含回归和上线准备，属于当前代码阅读后的估计。商户审核、财务口径确认和外部联调等待时间单列，不承诺微信开通日期。最小版本可只交付阶段一；本次推荐确认完整两阶段范围。

## 10. 验收清单

### 权限与产品

1. 新注册用户没有伙伴资格；管理员为 A 大会开通后，B 大会仍未开通。
2. 未购票伙伴可以进入中心；参会人退款不自动撤销独立伙伴资格。
3. 总公开关闭时，列表、详情、头像和公开 API 无资料泄露；电话等字段逐项验证。
4. 停用伙伴立即停止新归因；历史合法佣金仍可查询和结算。
5. 用户列表跨大会切换、批量开通和并发编辑不会误改其他大会。
6. 海报标注合作身份、二维码可扫描；私密资料仍可下载通用推广海报。

### 归因与金额

7. A 链接 → B 链接 → 下单归 B；自然访问不覆盖；30 天到期、Cookie 不可用和未归因路径行为明确。
8. 首页目录自然浏览不触发抢归因；主动点击“通过我报名”才建立推广来源。
9. 重复下单、超时恢复、JSAPI／H5／Native 切换和代购认领均不改变已锁定归因。
10. 自购、免费票、模拟支付、全退订单不产生可提现佣金。
11. 阶梯第 10／11／30／31 单边界、并发入账、规则换版、个人比例覆盖都可重复验证。
12. 同一支付回调 100 次、退款回调重复或乱序，金额和票证数量均保持正确。
13. 多次部分退款的最终佣金与净交易金额公式一致，舍入差额不累积。
14. 冻结期内退款申请、退款完成、异常关闭和结佣任务竞争，均按真实状态释放资金。

### 提现与微信

15. 两个并发提现申请无法超额冻结；每笔提现可追溯到具体佣金分配。
16. 税前、税费、实付相加一致；人工凭证重复登记无法重复结清。
17. 微信绑定包含正确组织、用户、AppID 和商户号；跨账号扫码、伪造回调、过期 state 和更换收款人失败。
18. 余额不足、限额不足、姓名不匹配、用户取消和渠道风控显示可操作状态，系统不自动拆单规避限制。
19. 发起请求超时后恢复查单；提交成功但服务宕机、通知丢失、重复通知和旧租约回写均不会重复付款。
20. 前端返回成功但微信未到账时保持处理中；满 24 小时但渠道尚未关闭时不释放金额。
21. 退款与提现同时发生、提现已付后退款、人工渠道切换时都有正确的冲正和占用结果。
22. 关闭新出款后，现有转账继续查单和对账；凭据轮换不会切断存量转账。
23. 真机小额转账、主动撤销、超时关闭及资金账单对账在实际商户批准后验收，保存脱敏证据。

### 回归、性能与发布

24. 登录、购票、重复支付防护、电子票、退款、发票和现有参会名片全部回归。
25. 用独立测试浏览器验证 390、768、1440 宽度及键盘访问；不改变用户现有浏览器视口。
26. 新页面遵守公开／敏感整页边界，`/payout` 等路径无第三方统计，真实 Head 和导航均验收。
27. 1 万伙伴和 10 万推广订单规模下，分页命中范围索引、无逐条补查；专用验收环境读接口 P95 目标小于 500 ms。此为验收目标，尚未测量。
28. 规范导出不含个人身份、推广码、收益、凭据和运行开关；规范同步不改生产伙伴余额或已锁定规则。
29. 迁移保留存量报名、订单和用户；应用关闭入口后账务数据完整且可重新开启。

确认实施后运行现有 `pnpm check`、`pnpm test:persistent`、`pnpm test:operations`、`pnpm test:registration-experience`、`pnpm test:visual`、`pnpm test:tooling`，并把上述新增事务、提现并发和安全案例纳入对应包的测试套件。部分专项依赖隔离验收数据库；真实微信资金测试单独留存证据，不通过日常自动测试触发生产转账。

## 11. 发布、停用与回滚

按照现有项目规则，本地完成与验证后再更新主工作目录共享预览；临时分支或工作树不得接管 `127.0.0.1:8088`。用户授权推送时，执行规范导出、检查、PR 与 CI 流程，禁止直接推远端 main。

生产上线继续执行 [production-deployment-runbook.md](</Users/laoyao/AI Coding/01-Projects/Active/TokEMS/docs/production-deployment-runbook.md>)：已合并 PR 的目标 SHA、成功主分支 CI、完整镜像证明、数据库备份、回滚镜像、构建与迁移身份、容器及公网验收。

本次需扩展两项生产保护：

- 将伙伴资料、绑定、佣金、提现、规则历史和流水计数纳入生产数据保护校验，规范同步不能覆盖。
- 在既有支付结清门禁增加商家转账活动单和未消费资金通知检查。发版前停止新出款；存在 `WAIT_USER_CONFIRM`、处理中或结果不明的单据时，先完成查单或确认撤销，不带着未知出款执行普通迁移。开启新出款前恢复对账维护并通过验收。

应用级停用顺序：关闭新推广／新出款 → 保留历史查询、回调与查单 → 完成在途单核对 → 隐藏公开入口。资料和财务数据持续保留。

存在新版本转账在途时，不能直接回退到完全不认识商家转账的旧 API 镜像；优先关闭功能开关或修复部署，必要回滚先结清在途状态并按 Runbook 操作。已成功支付的佣金无法用数据库回滚撤销。

保留新账务能力的兼容版本作为首选回滚基线。若必须暂时运行尚无计佣能力的旧版本，停止新推广和所有新结算；既有支付与退款事实继续保存在原业务表。重新启用前，按订单逐项对比成功支付、累计成功退款和佣金流水，通过唯一业务键补齐差异，全部核对通过后再开放提现。不能仅恢复页面开关后立即付款。

数据迁移采用增量兼容方式，不删表、不清库，不通过恢复旧数据库覆盖新的转账事实。
