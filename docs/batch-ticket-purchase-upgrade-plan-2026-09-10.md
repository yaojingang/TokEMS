# 多名额购票与统一支付优化方案

日期：2026-09-10  
状态：需求与设计评审稿，待用户确认后实施。  
依据：用户描述与截图、本地 `main` 当前代码和已有未提交支付恢复改动、本地共享预览的公开大会接口、现有报名与退款设计，以及文末官方资料。

## 1. 建议确认的方向

将「允许购票人继续增加名额」升级为「允许一次购买多个名额及后续增购」。开启后，首次购买和后续增购共用一个流程：**选择票种 → 选择本次数量 → 逐位填写参会人 → 确认总额 → 一次付款 → 每人独立出票**。

推荐采用 **一个购票订单 + 多个参会名额 + 一次总额支付**。购票人统一管理订单、支付和发票；每位参会人拥有独立报名记录、认领入口、电子票和核销状态。

以本地当前大会通票 ¥399 为例：首次选 5 个名额，填写 5 位参会人的资料，支付 ¥1,995。购票人可以包含自己，也可以全部为他人购买。已买 1 个名额且累计上限为 5 时，本次最多增加 4 个，新增订单金额为 ¥1,596。

### 推荐产品决定

| 项目 | 本次推荐口径 |
| --- | --- |
| 开关 | 沿用现有开关，同时控制首次多人购买、为他人购票和后续增购 |
| 数量 | 默认 1；提供减号、数字输入、加号，以及可用范围内的快捷数量 |
| 票种 | 首版一单一种票，同一订单内每个名额单价相同 |
| 名额上限 | 沿用每位购票人在本大会的累计有效名额上限；默认 5，后台现有配置范围 1–20 |
| 参会资料 | 付款前填写完整；本人可带入资料，其他参会人逐位填写 |
| 付款 | 一个订单号，一次按总额付款；重试复用原订单和支付协调机制 |
| 后续增购 | 已付款订单保留原明细，新增名额创建新的批量订单 |
| 退款 | 购票人选择需要退的参会名额，可选一位、多位或全部；审核后原路退款 |
| 发票 | 按订单申请，展示人数、票种和净可开票金额 |
| 人工审核 | 多人订单整体审核；整单通过后统一支付，整单驳回后允许带回资料重新提交 |

本次覆盖付费与免费票、本人和纯代购、自动确认与人工审核。混合票种、团购折扣、Excel 导入、先买空白名额再补资料、跨大会合并付款和不同发票抬头拆票申请，留在本次范围之外。候补邀请继续限定本人一个名额。

## 2. 已核实的现状

| 当前事实 | 对方案的影响 |
| --- | --- |
| 后台已有 `additionalPurchaseEnabled` 与 `maxActiveSeatsPerPurchaser` | 复用现有管理入口，无需再增加一组重复开关 |
| 报名表单与 `CreateRegistrationSchema` 只接受一个参会人 | 需要增加参会人数组及按卡片定位的校验错误 |
| `orders.registrationId` 为必填且唯一；票也按报名唯一 | 多人订单涉及订单与报名关系调整，改动超过 8 个文件 |
| 库存预留已有 `quantity`，下单实际固定为 1 | 可复用库存机制，统一按本次人数占用与结转 |
| 当前名额汇总按订单数计算 | 必须改成按有效名额计算，订单数独立统计 |
| 同一购票人同一大会已有待处理订单时，新下单会被阻止 | 保留“一次只处理一个待审核或待支付订单”，提供明确的继续支付和取消入口 |
| 微信已有支付尝试、查单、关单、通知收件箱和恢复机制 | 沿用现有支付通道，将核验金额改为整单金额，履约改为所有名额 |
| 退款服务、发票关联、报名详情和通知仍有单人假设 | 必须随多人购票一起完成适配后开放 |
| 同大会有效手机号与已关联参会账号有唯一约束 | 每人独立手机号；不能使用购票人手机号占据多个名额 |

本轮读取的本地公开接口为 `http://127.0.0.1:8088/api/v1/events/tokems26`：通票 ¥399，名额上限 5，追加购买开关关闭，人工审核关闭。当前必填字段为姓名、手机号、公司/机构；职位、城市可选，邮箱未启用。用户截图用于说明目标设置场景，方案按开启后的体验设计；本轮未保存或切换设置。

工作区已有支付恢复、订单权限和后台操作的未提交修改。实施时以当时工作区为准核对差异，保留这些修改，避免覆盖已完成工作。

## 3. 后台报名设置

开关文案建议改为：

> **允许一次购买多个名额及后续增购**  
> 开启后，购票人可在首次报名或后续增购时选择多个名额，填写各位参会人信息后统一付款。

上限字段改为「每位购票人累计最多有效名额」。说明：

> 包含本人和代购名额。待审核、有效待支付、支付确认中和已生效名额均占用额度；完成取消或全额退票的名额释放额度。

后台同时显示「按当前设置，首次最多可购买 5 个名额」的解释，以及设置保存后的生效说明。

- 开关关闭：新申请保留本人单名额报名；已创建订单的支付、认领、退款和票证继续按订单状态处理。
- 已报名用户没有剩余额度：前台展示已占用数量与上限，隐藏可执行的增购动作。
- 降低上限：保留已创建的合法名额，后续新购按新上限计算；已有数量超过上限时显示超出原因。
- 关闭报名或改变开关：阻止不符合新规则的新建订单；旧订单按原有效期履约，不静默取消。
- 上限为 1 且开关开启：允许替一位他人购票，页面明确显示当前可购买 1 个名额。

## 4. 报名页交互

### 4.1 选择数量与展示金额

数量选择紧接票种卡片。默认选中 1，支持直接输入正整数，快捷项建议为 1、2、3、5，并按当前可购买数量过滤。按钮必须有可读标签，可用键盘操作。

始终明确显示：

- 本次购买数量。
- 本大会已占用名额和剩余额度。
- 票种单价、数量、小计和应付总额。

可新增数量取「购票人剩余额度、票种实际可售库存」的较小值。存在待处理订单时，先展示该订单及恢复操作。库存、名额上限与金额最终由服务端复核。

页面建议结构：

```text
大会通票                         ¥399 / 人
本次购买        [−]   5   [+]     快选 1  2  3  5
已占用 0 / 5 个名额，本次可购买 5 个

购票人：已登录手机号                订单和发票归此账号
☑ 本次包含本人参会

参会人 1 · 本人                    资料已带入，可核对
参会人 2                           姓名 / 手机号 / 公司…
参会人 3                           姓名 / 手机号 / 公司…
参会人 4                           姓名 / 手机号 / 公司…
参会人 5                           姓名 / 手机号 / 公司…

已完成 3 / 5 位
大会通票  ¥399 × 5                合计 ¥1,995
□ 同意报名条款并确认获得代报名授权
[确认 5 位参会人信息并支付 ¥1,995]
```

这是信息结构示意；实施时沿用项目已有字体、配色、票种卡片和表单样式。

### 4.2 本人和其他参会人

- 登录购票人信息只显示一次，不要求重复登录或让全部参会人现场获取验证码。
- 首次普通报名默认「包含本人」；从增购入口进入时默认全部为其他参会人。没有本人名额的购票人可手动选择包含本人。
- 已有有效本人报名时，不再添加第二张本人票；在页内提供现有门票入口。
- 包含本人时，第一张卡片带入本人资料，手机号使用已验证号码；纯代购时全部显示独立参会人卡片。
- N 个名额对应 N 份资料，包含本人时是本人 1 份加其他人 N−1 份。
- 每张卡片使用大会已发布的报名字段及必填规则，不重新硬编码一份表单。
- 提供「沿用上一位的公司/机构」操作；不复制姓名和手机号，操作不覆盖已填写的其他字段。
- 完成的卡片可折叠，标题展示姓名、手机号尾号、填写状态；错误卡片自动展开并定位首个错误。
- 增加数量保留原资料；减少数量时优先移除末尾空白卡，涉及已填资料时让用户选择删除对象，保留本次操作的撤销入口。直接删除卡片同步减少数量和金额。

### 4.3 草稿、校验与条款

- 草稿保存数量、票种、本人标记、稳定卡片 ID 和每位参会人的回答；刷新、登录中断后能够恢复。
- 复用现有草稿隔离与过期机制，按组织、大会、购票账号和购买意图区分；旧单人草稿升级为一个参会人条目。
- 退出或切换账号时清空当前界面；不得把前一购票人的多人资料展示给下一账号。
- 本次填写的手机号先规范化，再检查重复；与现有有效报名冲突时提示冲突卡片，不暴露其他购票人的身份或订单。
- 曾取消的报名按既有身份归并规则安全处理；新多人订单使用新的报名记录并保留旧历史，不复用旧订单金额与支付流水。
- 任一必填项无效时整批不提交，保留所有已填资料；服务端错误返回卡片 ID 与字段路径。
- 条款和代报名授权一次确认，写入各参会名额的提交快照；营销订阅和公开名片授权继续各自独立，代购不替他人开启公开展示。
- 手机端采用单列卡片和底部金额/提交区，提交区避开软键盘与安全区，不遮挡最后一项内容。

## 5. 订单、支付、出票与增购

### 5.1 一次支付的边界

一批人数形成一个订单号、一份价格快照和一个总额。标准状态流为：

```text
报名表单 → 服务端校验 → 数据库事务：订单 + N 份报名 + N 个名额明细 + 库存预留
                                ↓
                         现有微信支付入口
                                ↓
                    验签通知 / 主动查单确认总额
                                ↓
          数据库事务：支付入账 + 全部名额生效 + N 张电子票 + Outbox
                                ↓
                    Worker：购票通知 / 逐人认领与票务通知
```

沿用现有微信 Native、JSAPI、H5 路径。普通下单接口可提交整单总额，商品明细支持数量；本方案据此采用当前普通商户支付模式，无需新增支付产品或第三方账号。[微信官方下单文档](https://pay.wechatpay.cn/doc/v3/merchant/4012791897)

数量选择只更新预览。正式提交时服务端复核当前发布的票价、表单版本和有效名额，按整数分计算总额；价格或条款变化时返回更新内容，让购票人重新确认。

创建订单后，价格、数量和名额对应关系固定。修改待支付订单的人数时，先安全关闭原交易与订单，再带回草稿重新确认。渠道状态未知时保留原单并继续查单，避免创建另一笔可付款订单。

### 5.2 支付成功与异常恢复

- 支付成功核对整单金额、币种、商户、订单和支付流水，全部名额在同一个本地事务中出票。
- 微信通知已经持久化且本地事务失败时，保留通知并重试；页面显示「支付结果确认中」，不要求再次付款。
- 重复提交、双击、通知重放、查单和回调同时到达，只能生成一个订单和每位一张票。
- 同一购买意图携带不同人数或人员内容时返回冲突；修改后使用新的意图，不能把第一次提交的响应错误复用于新的 5 人名单。
- 支付倒计时沿用当前普通订单 15 分钟。到期或取消时先完成渠道查单与关单，再原子释放整批预留与额度；支付结果未知期间继续保护库存。
- 免费票总额为 0，提交成功后完成整批报名和出票，按钮使用「确认 5 个名额」，无需进入微信支付。

### 5.3 成功页与个人中心

成功页展示「已成功购买 5 个名额」，下方列出每位参会人及认领/出票状态。购票人可逐位复制认领邀请、查看可管理资料；本人有票时提供本人门票和后续参会资料入口。其余参会人通过各自独立凭证认领本人的名额。

个人中心以订单卡片呈现「大会通票 × 5」「实付 ¥1,995」「5 个名额」，展开后看到参会人列表。订单详情同时显示有效名额数、已退名额数、核销情况和对应操作。历史单人订单显示为 1 个名额。

财务与整体订单权限属于购票人；参会人认领不转移付款、退款和发票权限。购票人在未认领名额上编辑参会人时沿用手机号校验与认领令牌轮换；认领后保留现有编辑边界。所有编辑明确指定目标名额。

### 5.4 人工审核和候补

多人订单按整体审核，后台显示全部参会人，操作明确标为「通过这 5 个名额」或「驳回本次报名」。通过时重新核对足量库存，统一进入支付状态；免费订单则整批出票。驳回保留原因和资料，关闭整单并释放预留，购票人可带回资料调整后重新提交。首次版本不在审核中自动删人或修改已确认金额。

保留现有待审核预留期限 30 天；新增多人订单在到期清理中整体关闭并通知。审核通过后，付费订单统一获得 15 分钟支付窗口。库存不足时保持待审核，显示不足数量，不部分通过。老订单继续按既有审核入口处理。

候补报名和邀约保持「本人一个名额」。从候补邀请进入时，页面明确提示数量固定为 1，服务端拒绝将邀请用于多人购买。

## 6. 退款、发票、通知与统计

### 6.1 按参会名额退款

退款页先选择参会人，系统计算选中名额剩余可退金额。已核销、已退、正在退款或不符合现有退款窗口的名额显示具体原因。购票人可选择一个、多个或全部可退名额，一次提交一份申请。

示例：¥399 × 5 已付，选择其中 2 位申请退款，申请金额 ¥798。审核通过后只暂停这 2 张票；渠道确认成功后只取消这 2 个名额，另外 3 张票保持有效，订单显示「部分退款」，净金额为 ¥1,197。

- 沿用现有同一订单最多一份未结束退款申请的约束；一次申请可以包含多个名额。
- 申请时保存选中名额、金额、规则、核销状态和权益处理方式；审核时锁定对应票再次检查。
- 待审核期间继续沿用现有票务规则；批准取消名额后暂停选中票，直到退款完成或已有异常处理流程明确处置。
- 名额成功取消并退款后才释放购票额度及可释放库存。仅发生补偿性部分退款且票仍有效时，名额继续占用。
- 管理员金额型退款必须明确分配至名额，并显式选择保留或取消权益；不能只看整单退款比例猜测应取消哪张票。
- 原路退款使用原支付交易的整单金额作为渠道原单金额，本次退款使用已批准的选中名额金额；失败和未知状态沿用原退款单处理。[微信官方退款文档](https://pay.wechatpay.cn/doc/v3/merchant/4013070371)
- 外部退款或优惠分摊无法映射名额时记录真实资金事实并转人工核验，停止新的冲突资金动作，保留现有票务状态直至有明确处理依据。

### 6.2 发票与通知

发票按一个购票订单申请，展示「大会通票 5 人」和净可开票金额。退款后按已成功退款更新可开票金额；已经开具的发票进入现有调整处理流程，不直接修改已开文件。一个订单的发票金额不得在每位参会人的统计中重复累计。

购票人收到一次订单提交、支付和退款汇总通知；每位参会人接收自己的认领邀请、电子票及参会通知。财务通知不进入其他参会人账户。通知失败沿用 Outbox 恢复，不影响支付与出票；投递去重按订单事件及目标报名区分。

### 6.3 后台与报表

| 页面/指标 | 迭代后口径 |
| --- | --- |
| 订单列表 | 一次购买一行，显示人数、原金额、已退金额、净金额、有效名额数 |
| 订单详情 | 整单支付/退款/发票区域 + 每位参会人的报名、票务、认领状态 |
| 报名列表 | 每位参会人一行，关联统一订单号，显示本名额金额 |
| 报名详情 | 本人名额操作明确定位；整单资金操作展示影响人数和金额 |
| 订单数 | 一次购买 5 人计 1 单 |
| 参会名额/售票数 | 一次购买 5 人计 5 个名额，退票后分别展示总购买与当前有效数量 |
| 收入 | 每笔成功支付计一次；净收入扣除成功退款 |
| 购票人数 | 按购票账号去重，与参会人数分别统计 |
| CSV/导出 | 分清订单级与名额级；名额级默认输出分配金额，避免把整单总额重复加总 |

参会名片、需求收集、签到和公开会员资格都依据对应名额与票券状态。订单处于部分退款时，仍有效的其他参会人继续保有服务入口。

现有合作伙伴分销方案尚在设计文档中。本次为整单和名额保留明确金额及事件边界；该方案后续实施时按真实支付计佣并按退款明细冲正，阶梯订单数将 5 人同单计为 1 单。

## 7. 推荐实现与兼容设计

### 7.1 方案取舍

最小可上线选项：仅在自动确认大会开放同票种多人订单，并只允许整单退款；仍需完成真实一次支付、全部出票、权限、库存和发票适配。

推荐本稿的完整闭环，同时支持整单审核和按名额退票。5 人订单发生其中 1 人无法到场时可以直接处理售后，避免运营人工拆解整单资金。

另一条可行路线是保留每人一个订单，增加合并付款批次。该路线复用单人订单较多，但增加付款金额分配、跨子单退款、发票归属和重复通知的长期协调成本。本项目推荐将订单直接扩展为多个名额。

### 7.2 数据结构

复用 `orders`、`payments`、`registrations`、`tickets`、库存预留和退款执行表。新增核心持久化结构限定为两张表：

| 结构 | 职责与约束 |
| --- | --- |
| `order_items` | 一行一个参会名额，保存订单 ID、报名 ID、组织/大会、顺序、票种与价格快照、分配金额；报名 ID 唯一，订单内顺序唯一，金额为非负整数分 |
| `refund_request_items` | 保存退款申请选中的名额、申请及批准金额、权益处理、已履行金额；校验申请与名额属于同一订单/组织/大会，每份申请内名额唯一 |

订单增加模型版本和原始购买数量。新多人订单由 `order_items` 承载全部报名关系；将 `orders.registrationId` 改为可空，仅保留旧模型和兼容单人订单引用。多人订单不设置虚构的主参会人。

发票保留订单唯一约束，将 `invoice_requests.registrationId` 改为可空，订单范围外键改为订单 ID + 组织 + 大会；旧报名引用保留历史查询用途。`order_items` 分别以复合外键保证报名和订单的组织、大会一致。

所有历史订单补齐一个明细，不改变原订单号、金额、支付记录、归属和票码。退款历史只映射到原来唯一名额，不推测额外人员或退款权益。处于已取消、已退款、已归并状态的记录也保持原历史。

库存预留数量为本单人数；支付结转按人数增加销量，退款释放按明确取消的名额数处理。明细数量和金额加总与订单快照在创建事务中检查。已提交订单的价格和数量不原地改变。

退款明细以已审批申请的映射为基础，同一申请的重试复用同一分配；不能把同一笔渠道退款重复分配。金融事实在原支付和退款表记录，参会权益继续在对应报名与票券记录中维护。

### 7.3 API 与页面接口

以下路径均相对于现有 `/api/v1`：

| 接口 | 变更 |
| --- | --- |
| `POST /registrations` | 保留现有单名额输入，适配到统一下单逻辑 |
| `POST /registration-batches/quote` | 新增登录后报价预检，输入大会、票种、数量；返回单价、总额、可购数量、发布及表单版本；不占库存 |
| `POST /registration-batches` | 新增批量提交，包含数量、带稳定 ID 的参会人数组、是否本人、表单/条款版本、授权、购买意图和报价版本；数量必须等于人数 |
| `GET /customer/events/:eventId/purchase-context` | 名额按明细计算，返回已付、预留、剩余数量、待处理订单及原因 |
| 订单与支付详情、支付完成响应 | 增加数量、明细列表、逐人票务/认领状态；旧单名额字段只对单人订单返回 |
| `GET /customer/orders/:orderId` | 新增登录购票人的完整订单详情，服务端检查组织和财务所有权 |
| `PATCH /customer/orders/:orderId/items/:itemId/attendee` | 精确修改某个未认领名额；保留版本校验与令牌轮换 |
| 现有订单退款接口 | 扩展选中名额 ID 列表及退款预览；老单未传列表时沿用单名额行为，多人订单必须明确选择 |
| `POST /admin/events/:eventId/orders/:orderId/review` | 多人订单整单审核；从名额详情进入时展示完整审核范围 |

旧的单人修改、审核与代理工具如果遇到多人订单，必须显式拒绝并给出支持的整单或名额入口，不默认操作第一位参会人。现有支付访问凭证继续绑定订单，独立参会认领凭证仅授予对应报名与票证权限。

报价预检提供界面解释，提交事务再次校验。前端总额、传入数量、价格快照或旧报价均不能直接授权扣款。

### 7.4 并发与故障

- 下单按购票人/大会锁定购买资格，再按稳定顺序锁定关联订单、票种和规范化参会身份。所有入口统一锁顺序；唯一约束作为重复身份与购买意图的最终保护。
- 一次请求整体成功或整体失败，不留下前 3 位已占库存、后 2 位失败的半批结果。
- 退款审批与核销共用订单、目标票的锁定顺序；只允许先取得状态的一方完成有效变更。
- 单批最多沿用配置上限 20；不因批量购买新建后台服务或额外任务队列。数据库操作批量执行，避免每位参会人反复独立查单。
- 通知条数随人数增长，使用现有 Worker 限流和幂等任务，不把短信调用放入支付事务。
- 外部支付不可用时保留待支付订单和有效预留；超过有效期后依现有支付协调规则结清。退款异常保留已批准义务，不用新订单或第二笔退款绕过未知结果。

本方案最需要验证的前提是：订单周边的所有业务都能切换到名额明细。如果仍有入口把一个订单视为一个参会人，可能漏出票或误取消其他人的票。为此先交付兼容所有明细的基础版本，再开放多人写入；故障回退只能退到该基础版本。

## 8. 实施顺序与工作量

涉及前台、后台、API、Worker、契约、数据库和部署验收，预计 30–45 个文件，新增部署服务 0，新增第三方账户/密钥 0，新增必填环境变量 0。按一名熟悉项目的工程师估算约 8–12 个工作日，属于排期估算；真实支付验收安排单独计算。

| 可独立合并阶段 | 交付结果 | 预估 |
| --- | --- | --- |
| A. 明细与兼容基础 | 增量迁移及历史补写；订单读取、支付入账、逐人出票、审核、认领、退款、发票、导出和通知均能处理名额数组；新购入口仍只创建单名额订单，现有功能可正常使用 | 4–6 天 |

## 9. 验收标准

核心成功标准：**一次购买 5 人，生成 1 个订单、5 条报名、5 个名额明细，一次实际支付 ¥1,995，生成 5 张独立电子票；收入只计 ¥1,995。**

| 场景 | 必须通过的结果 |
| --- | --- |
| 首次购 1 / 2 / 5 个名额 | 数量、卡片数、应付金额、报名数、库存变动、出票数一致 |
| 纯代购 / 包含本人 | 购票人与参会人权限正确，本人手机号只绑定一次 |
| 已买 1 个再增购 4 个 | 新增一单支付 ¥1,596；再购 1 个被累计上限阻止 |
| 5 改 3，再改 5 | 金额正确，原资料按约定保留/删除并可撤销，无卡片串人 |
| 某位信息缺失或手机号重复 | 整批不建单，定位对应卡片，其他输入保留 |
| 有待支付订单 / 连点提交 / 两个浏览器并发 | 引导恢复原订单；不会创建超额名额或重复可支付订单 |
| 报价后改价、改表单、改上限或关闭开关 | 重新校验并明确提示；已有效创建订单按原规则履约 |
| 库存仅剩 3 个却提交 5 个 | 全部失败，提示库存，不生成半批报名 |
| 10 倍并发抢最后一批库存 | 售出与有效预留不超过库存，账号累计不超限 |
| 付款取消、超时、未知、迟到通知和通道切换 | 真实资金先结清；预留准确释放；已付款批次仅出票一次 |
| 支付入账事务失败 / Worker 停止 / 通知重放 | 恢复后补齐全批票，无重复扣款、无重复出票，通知可补发 |
| 免费 5 人订单 | 一次提交完成 5 位，不调用付费下单 |
| 多人整单审核通过、驳回、超时、库存不足 | 全部状态一致，审核通过后一次支付，驳回可恢复资料 |
| 候补邀请提交数量 2 | 前端解释限制，服务端明确拒绝 |
| 5 人中选择 2 人退票 | 申请 ¥798，成功后只取消 2 张票，剩余 3 张可核销 |
| 选中一张已核销票 / 退款审批与核销并发 | 不批准违反当前退款规则的操作；其余票权益不被误改 |
| 退款重放、余额不足、未知结果、外部退款 | 保留正确退款预留与责任，不重复执行、不自动猜测取消对象 |
| 部分退款后开票 / 已开票后退款 | 可开票金额正确，已开票进入既有调整状态 |
| 购票人、参会人、其他用户、跨大会管理员 | 返回数据与动作权限各自正确，无整单财务或他人资料泄漏 |
| 历史已付/待付/退款/认领中的单人订单 | 迁移前后仍可操作，原单号、票码、支付与发票可追溯 |
| 手机、桌面微信、桌面浏览器 | 合适的支付入口，表单不遮挡、可键盘访问、恢复后人数准确 |
| 公开首页进入报名/支付/账户与返回 | 全页边界正确；敏感流程真实 Head 无统计脚本 |

自动检查以现有 `pnpm check` 为全量门禁，增加订单明细、批量下单并发、按名额退款和迁移集成测试；执行 `pnpm test:registration-experience` 与 `pnpm test:payment-resume` 回归。浏览器模拟付款只能证明页面与状态衔接；真实微信收款和原路退款需要在验收授权范围内单独核验，并明确记录证据。

## 10. 发布与回退

确认方案后的实施先核对当前工作区和正在进行的修改。较大实验需要隔离预览时，使用独立 Compose 项目、镜像、端口和数据卷；不接管主目录 `8088` 共享预览。完成整合后再更新共享预览并验收。

发布之前执行 `check` 技能审查，覆盖所有名额维度入口和历史兼容。数量相关前台文案、后台设置或规范模板变更完成后，运行 `pnpm canonical:export`，提交完整及前台派生快照；每次获授权推送前运行 `pnpm canonical:check` 并遵守仓库 PR 流程。

生产发布另按 `docs/production-deployment-runbook.md`：目标来自已合并且 CI 通过的远端 `main`，具备成功主分支 CI 和完整镜像证据；先备份并记录版本，完成交易结清、预构建镜像与迁移核验后发布。部署预检和已付缺票核验要改为核对每单应有名额数，避免用旧的“每单一张票”口径误判。

增量结构和历史数据保留。阶段 B 出现故障时停止新的多人下单并回退到阶段 A 的兼容版本；持续处理已存在多人订单的支付回调、票证、退款、发票和查询。已产生多人订单后，不允许直接回退到只识别一个报名的旧版本。回退不清库、不覆盖备份、不删除名额与支付事实。

本轮只生成方案文档；未修改业务代码、数据库、后台开关或共享预览，未执行支付、退款、提交、推送或发布。

## 11. 对标与资料

参考只提取与本次目标直接相关的机制：

- [Ticket Tailor：结算表单](https://help.tickettailor.com/en/articles/950989-how-to-edit-your-checkout-form)：购票人问题按订单填写一次，参会人问题按每张票填写。本方案采用这种信息分层。
- [pretix 订单模型源码](https://github.com/pretix/pretix/blob/master/src/pretix/base/models/orders.py)及[官方订单明细接口](https://docs.pretix.eu/dev/api/resources/orders.html)：一个订单关联多个 position，每个明细有独立参会人和金额；付款后可按参会人分发通知。本方案采用订单与名额分离，并保留 TokEMS 现有账号认领和微信支付机制。
- [微信普通商户下单](https://pay.wechatpay.cn/doc/v3/merchant/4012791897)：订单总额与商品数量的接口基础。本方案中的“单订单总额付款”为据此作出的设计选择。
- [微信普通商户退款](https://pay.wechatpay.cn/doc/v3/merchant/4013070371)：部分退款及原交易金额基础。具体退款结果继续由可信通知和查单确认。

本轮完成公开文档与本地接口读取，未调用带商户凭据的交易接口。方案复用现有账号、微信商户、短信和任务基础设施，无需在实施中另行索取一套凭据。
