# 发票短信通知实施记录

依据：[2026-09-10 最终方案](./invoice-sms-direct-download-plan-final-2026-09-10.md)。本记录对应本地 `main` 工作区的功能变更，起点为 `34ddc59055beaa7b04d83e1e35fbb62dedb71a98`，尚未提交、推送或发布生产。

## 使用流程

1. 管理员打开「系统设置 → 短信服务」，保存短信签名、凭据及「发票短信通知」模板 CODE。发票开关默认关闭。
2. 模板包含固定本站域名、`/invoice/file/` 路径，以及 `eventName`、`expiresAt`、`fileToken` 三个变量。`fileToken` 固定为 24 位字母数字；需以实际场景完成渠道审核。
3. 选择发票测试场景，填写内部手机号，确认真实短信测试。系统使用无客户信息的样例 PDF，先检查同一公开入口的 HEAD/GET，再提交短信。
4. 收到渠道的实际送达回执且文件检查通过后，管理员才可开启并保存发票短信通知。测试受理本身不会解锁开关。
5. 财务上传并成功登记发票文件后，系统自动向购票人排队发送短信。后台发票详情和个人中心显示发送结果、脱敏号码及可补发状态。
6. 用户打开短信链接即可获取文件，无需登录。PDF 支持浏览器预览和 Range 请求；OFD 作为文件下载。

短信正文参考：

> 【已审核签名】您的${eventName}电子发票已开具，请于${expiresAt}前查看及下载：https://本站域名/invoice/file/${fileToken}。请妥善保管领取链接。

大会优先使用后台简称；到期时间按大会时区显示明确日期和时间。模板及各变量的可用长度、最终拆分计费以实际获批渠道为准。

## 行为边界

- 本功能仅发送开具成功短信。原有补充资料提醒、订单访问恢复继续沿用既有业务方式。
- 组织短信总开关与发票场景开关共同控制发送。关闭不会破坏已发出的有效链接，重新开启不会补发历史发票。
- 签名、密钥、模板、参数模式或公开域名变化会使验证证据失效，关闭发票通知，并取消旧启用批次的待发任务。
- 只在文件校验及发票登记事务成功后创建通知任务；失败上传、重复登记和回滚均不会多发短信。
- 收件人优先为已验证购票人；发送前再次检查手机号、账号状态、发票版本和退款状态。无手机号时保留具体未发送原因。
- 普通人工补发每申请冷却 10 分钟，跨文件版本计算，滚动 24 小时最多 5 次；新文件自动通知保留冷却豁免。未知结果持续查询回执；从实际尝试起等待超过 30 分钟，财务可填写原因确认再次发送。
- 已受理、结果未知的短信不会按网络错误自动重发。明确临时拒绝最多尝试 5 次，间隔 30/60/120/240 秒；准备失败用尽任务重试后落为失败。重复任务在取得交付锁后再次校验重试时间，避免等待期间的状态变化导致提前重发。
- 正式文件链接从首次发送准备起有效 30 天，同一文件和收件人的未过期链接可复用；测试链接有效 24 小时。
- 有效链接独立于最新短信任务查询；补发等待、取消或失败时仍可撤销旧有效链接。新建正式链接和明确撤销会推进发票版本，旧页面须刷新后才能再次确认；复用同一链接及回执更新保持版本。
- 发送状态对应实际接收号码；当前号码变化时另行显示下次补发号码。短信送达事实与链接有效期分别展示，撤销或过期后引导用户在个人中心下载。
- 替换、作废、取消、退款后进入调整状态及人工撤销，均使旧链接失效。退款待审核时保留既有下载；批准执行或资金核验期间暂停文件读取，返回「发票正在处理中」。新开票和恢复仍受退款申请保护。
- model 2 批量订单按整单通知购票人，支持空报名关联；额外重复付款的原路返还不扣减原成交发票净额。

## 实现与安全边界

- 增量迁移 `0066_invoice_sms_direct_download.sql`，承接并行购票任务已完成的 `0065` 数据基础；新增凭证表与交付关联字段，迁移关闭旧发票场景并取消旧的待发开具消息。
- 使用现有 PostgreSQL outbox、BullMQ、Redis、阿里云短信及私有对象存储。没有新增生产环境变量或外部服务。
- 新事件 `InvoiceSmsDeliveryRequested` 仅携带交付 ID，数据库中保存随机令牌哈希和加密密文。文件链接、存储签名不进入普通列表、事件正文及审计。
- 下载经本站网关和 API 流式返回，限制单一 Range，校验内容长度和文件身份，支持客户端断开与存储超时；审计写入失败时立即取消上游读取并关闭流；完整读取同步校验文件摘要。
- 下载响应禁止缓存、引用来源传递和索引，不加载统计脚本。下载审计只记录资源 ID、时间与请求结果，无法据此判断本人阅读。
- API、网关和外层 Nginx 模板对文件路径脱敏或禁记日志；支付 API 别名明确拒绝。Nginx 显式返回 `no-referrer`，避免父级响应头覆盖。
- 设置页和整体集成状态读取同一组实际发票验证证据，整体可用状态同时检查业务开关。配置更新使用 `expectedUpdatedAt` 版本校验；测试回执只合并同一配置的验证信息，不能恢复业务开关或覆盖其他管理员修改。
- 发票测试及配置需要 `org.settings.manage`；财务补发和撤销沿用 `event.read + org.invoice.manage`。新增主动发送及撤销接口保持人工专属。

## 验证方式与证据范围

本轮使用一次性 PostgreSQL、Redis、隔离浏览器和 Nginx 容器；短信 SDK 与对象存储使用可控测试替身。没有发送真实短信，没有读取生产客户记录，没有替换共享预览。

- API 集成：实际登记事务、开关开/关、重复登记、匿名 PDF、HEAD、Range、失效凭证、跨发票关联、退款暂停与历史恢复、配置版本及验证、撤销并补发回滚、额外付款返还口径。
- Worker 集成：并发去重、发送许可、未知结果不重放、确定拒绝重试、回执竞态、准备失败终态、手机号与启用批次变化、链接复用/撤销/到期、样例测试、晚到证明。
- Redis：100/1000 个并发许可请求验证组织限流与组织间隔离。
- 真实 Chrome：首次关闭状态配置模板、送达前开关禁用、测试后开启、未保存修改后的明确恢复入口。
- 真实 Nginx：两类域名及两条文件路径的响应头、内部路径映射、Referer 清除、支付别名拒绝、日志不含令牌。
- 隔离工作树从上述 HEAD 创建，显式纳入发票文件及 `0065` 所需 schema/退款适配前置补丁。包构建和发票 API/Worker 集成在该环境另行运行，避免其余工作区修改掩盖本功能依赖。

## 启用与发布

代码完成后仍保持发票通知关闭。正式启用需实际模板审核、管理员授权的内部真实短信测试、送达回执及公网文件验证；本次自动测试不代替这组证据。

生产发布时须同时安装新版网关规则和 `docker/external-entry.nginx.conf.example` 对应的外层站点规则；使用独立支付入口时同时更新 `docker/payment-entry.nginx.conf.example`，按生产 Runbook 验证公网响应头与日志，再考虑开启功能。仅更新应用容器无法完成外层站点的日志保护。

出现渠道问题时优先关闭功能开关，已送达链接继续有效。回滚到旧应用镜像可能使新链接失效或恢复旧通知路径，须按专项回滚方案执行。
